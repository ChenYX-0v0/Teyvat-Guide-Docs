# 01 · 项目总览与架构

## 1. 产品定位

「AI 提瓦特向导」是一个面向《原神》玩家的智能助手工具站，核心能力：

1. **智能问答**：角色配队、圣遗物选择、养成优先级、活动攻略等。
2. **玩家档案查询**：UID 查询展柜角色、武器、圣遗物、推荐词条（Enka.Network 数据源，映射数据存 MySQL）。
3. **图鉴速查**：角色 / 武器 / 材料结构化检索（预留）。
4. **路线规划**：按目标生成采集 / 刷本路线（预留）。

## 4. 分层职责

| 层 | 目录 | 职责 | 禁止 |
| --- | --- | --- | --- |
| Router | `internal/router` | 路由与中间件装配 | 写业务逻辑 |
| Handler | `internal/handler` | 参数绑定、调用 service、封装响应 | 直接操作 DB |
| Service | `internal/service` | 业务编排、事务边界、外部调用 | 感知 HTTP 细节 |
| Repository | `internal/repository` | 数据读写封装 | 写业务规则 |
| Model | `internal/model` | 数据表结构 | 含业务逻辑 |
| DTO | `internal/dto` | 出入参结构 | 与 model 混用 |
| Pkg | `internal/pkg` | 日志 / 响应 / 数据库等基础设施 | 依赖上层 |

## 5. 数据流（以对话为例）

1. 用户在 `ChatInput` 输入 → `useChatStore.sendMessage()`
2. Store 立刻插入用户消息 + 一条 `pending` 占位消息（乐观更新）
3. `api/chat.ts` 的 `stream()` 用 `fetch` 发 `POST /api/chat`（`stream=true`，SSE）
4. Vite 代理转发到 Gin → `ChatHandler` → `ChatService.AskStream`
5. Service 落库提问 → `buildHistory` + 注入玩家上下文 → 调 `AIClient.CompleteStream`，增量逐段回写 SSE
6. 前端逐字追加到占位消息；`done` 帧带回 `sessionId / tokens / elapsedMs`（中断走 `error` 帧，已产出内容保留在气泡里）

> 非流式路径（`stream` 缺省/false）与之等价：`api/chat.ts` 的 `send()` → `ChatService.Ask` → 统一信封一次性返回。
> 帧格式、降级语义与历史组装规则见 `docs/04-API接口文档.md` §2。

## 6. 约定

- 所有后端响应统一为 `{ code, message, data }`，`code === 0` 视为成功。
- 前端接口层统一拆箱，页面只关心业务数据。
- 时间字段统一 RFC3339；金额/数值不做隐式单位转换。
- 配置优先：环境变量 > `config/config.yaml` > 代码默认值。

## 7. 长期架构规划（服务拆分路线）

> 结论先行：**当前规模不拆分**。保持模块化单体，按触发条件演进，避免过早微服务化。

### 7.1 目标拓扑（三个服务 + 网关）

```
                        ┌──────────────┐
  React SPA ──/api──►   │  API 网关     │  （路由 / 鉴权 / 限流 / 聚合）
                        └──┬───┬───┬───┘
           ┌───────────────┘   │   └───────────────┐
           ▼                   ▼                   ▼
   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ User 服务     │   │ Dictionary 服务│   │ AI 服务       │
   │ 注册/登录/JWT │   │ 游戏字典映射    │   │ LLM 对话      │
   │ 账号↔UID绑定  │   │ Enka 翻译代理  │   │ RAG/会话      │
   └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
          ▼                  ▼                  ▼
      users 库          字典库(只读+缓存)     会话库 + LLM API
```

| 服务 | 职责 | 数据 | 特征 |
| --- | --- | --- | --- |
| User | 注册/登录/JWT、账号↔UID 绑定 | `users` | 数据量小，最后拆 |
| Dictionary | 游戏字典映射、Enka 翻译代理、玩家档案查询 | `asset_*` 映射表 | 纯只读、缓存友好，第二个拆 |
| AI | LLM 对话、会话历史、RAG/知识库 | `chat_*` + LLM API | 外部依赖慢、需独立降级，**最先拆** |

### 7.2 演进阶段与触发条件

| 阶段 | 形态 | 说明 |
| --- | --- | --- |
| ① 现在：模块化单体 | 单进程，模块间只走接口 | 出现触发信号再进入 ② |
| ② 按需拆分 | 先拆 AI（隔离外部依赖），再拆 Dictionary（只读扩容） | 信号持续 2 周以上且影响体验 |
| ③ 完整微服务 | 三服务 + 网关 + 注册发现 + 消息队列 | 多团队并行 / 多产品线复用 |

**拆分触发信号**（满足才拆，避免为了拆而拆）：

- AI 调用超时/排队拖累玩家查询等轻接口（进程内资源争抢、连接池打满）；
- 字典读 QPS 需要独立缓存层 / 多实例扩容，主服务不想跟着扩；
- AI 需要独立的成本与配额管控（独立计费、密钥、限流）；
- 多人团队按模块分工，发布互相阻塞。

### 7.3 现在就做的准备（成本低，拆分时收益最大）

1. **模块边界焊死**：service 内按 auth / asset / enka / ai / player 分包，模块间只通过 Go interface 调用，禁止跨模块直接引用对方 struct/repo。
2. **数据按前缀隔离**：表名沿用 `asset_*` 前缀；禁止跨模块 JOIN，关联查询在 service 层组装。
3. **接口先行**：模块对外能力先定义为 interface（`AIClient` 已是），未来拆分 = 换成 RPC 实现，业务代码不动。
4. **无状态化**：进程不落本地状态，保证可水平复制。
5. **配置即边界**：各模块依赖（库、URL、密钥）在 config 中独立成组，拆分时直接迁移。

### 7.4 拆分时需引入的基础设施（阶段②起）

- API 网关：Nginx / APISIX 即可，初期不必上 Kong
- 服务间通信：先 HTTP + JSON，出现瓶颈再上 gRPC
- Redis：字典缓存 + 会话共享
- 消息队列（可选）：AI 异步任务 / 日志解耦
- 可观测性：统一 Trace ID 贯穿三服务（pkg/logger 已具备，补中间件透传）

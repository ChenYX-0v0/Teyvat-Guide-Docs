# 08 · AI 服务接入规格（交接文档）

> **读者**：负责实现「AI 服务」的 AI 代理或开发者。
> **目标**：建设一个独立的 AI 服务，并接入现有的 `teyvat-guide` 主服务，替换当前进程内的简易 LLM 调用。
> **前置阅读**：根目录 `AGENTS.md`（项目规范，强制）、`docs/01`（架构与拆分规划）、`docs/04`（API 文档）。
> **一句话**：主服务负责业务与会话持久化，AI 服务负责模型调用与（后续）知识检索；两者通过 HTTP 契约解耦。

## 1. 现状事实（先读，避免重复造轮子）

### 1.1 主服务（已有能力，不要重写）

## 2. 目标架构

```
                    ┌──────────────────────────────┐
  React SPA ─/api─► │  teyvat-guide 主服务 (:8080)  │
                    │  ChatService / PlayerService │
                    │  Auth / 会话持久化 / 业务编排  │
                    └───────────┬──────────────────┘
                                │ HTTP（AIClient 的 remote 实现）
                                │ X-AI-Key 鉴权
                                ▼
                    ┌──────────────────────────────┐
                    │  AI 服务 (:8090，独立进程)     │
                    │  · 模型调用（多供应商可切换）    │
                    │  · 提示词编排 / 上下文裁剪      │
                    │  · RAG 检索（阶段 P2）         │
                    │  · 流式输出（阶段 P3）         │
                    └───────────┬──────────────────┘
                                ▼
                        LLM API（OpenAI 兼容 / 本地模型）
```

**为什么独立**：见 `docs/01` §7 —— AI 依赖外部 LLM，慢、会超时、需独立限流与成本管控，不能和毫秒级的玩家查询/字典查询抢同一个进程资源。AI 服务是**第一个**该拆出来的服务。

**职责边界（关键，别越界）**：

| 归主服务 | 归 AI 服务 |
| --- | --- |
| 用户注册/登录/JWT、UID 绑定 | 提示词编排、上下文裁剪 |
| 会话与消息持久化（`chat_*` 表） | 模型调用、重试、超时、模型路由 |
| 对前端的 API 契约 | token/成本统计、内容安全过滤 |
| 业务数据（玩家档案、字典） | RAG 索引与检索 |

> AI 服务**无状态**：不落业务库、不建用户体系、不管会话存储。重启即恢复，可水平复制。

## 3. 接口契约（AI 服务必须提供）

### 3.1 健康检查

`GET /health` → `{"code":0,"data":{"status":"up","version":"0.1.0"}}`

### 3.2 补全（P0 必须）

`POST /v1/complete`

请求头：`X-AI-Key: <AI 服务密钥>`

```json
{
  "system": "",
  "history": [
    { "role": "user", "content": "胡桃怎么玩？" },
    { "role": "assistant", "content": "胡桃是火元素主C……" }
  ],
  "prompt": "那圣遗物怎么选？",
  "options": { "model": "gpt-4o-mini", "temperature": 0.7, "maxTokens": 1024 }
}
```

响应（与主服务同一信封）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "reply": "……",
    "model": "gpt-4o-mini",
    "tokens": { "input": 812, "output": 233, "total": 1045 },
    "finishReason": "stop",
    "elapsedMs": 1840
  }
}
```

**约定**：

- `history` 只允许 `user` / `assistant` 两种 role；`system` 由独立字段传，不要在 history 里混入
- 单个 `prompt` ≤ 4000 字符（主服务已校验）；AI 服务需自行防护超长输入
- 超时：AI 服务建议 60s 上限；主服务侧调用超时设 65s 并做降级
- **幂等**：同一请求重试不得产生重复计费副作用（无状态实现天然满足）
- 错误：4xx = 入参/鉴权问题（不可重试）；5xx / 超时 = 上游模型问题（主服务可重试 1 次）
- 统一错误响应：`{"code":503,"message":"上游模型限流","data":null}`

**可选 `context` 字段（个性化上下文）**：请求体可带 `context`，`null`/缺省表示无上下文（旧契约行为不变）。
当前主服务下发的结构（**以 `shared-docs/03-主服务对接说明.md` §6 为契约来源**）：

```jsonc
"context": {
  "goal": "character_build",           // general | character_build | team_build | exploration
  "summary": "其余 2 个展柜角色因体积预算已省略",   // 可选，渲染时置于档案之前
  "player": {
    "uid": "197794747", "nickname": "可以黑白熊", "level": 60, "worldLevel": 8,
    "characters": [                    // 展柜角色（≤8）：全部给概览
      {
        "name": "芙宁娜", "level": 90, "constellation": 2,
        "talents": { "normal": 8, "skill": 10, "burst": 10 },
        "weapon": { "name": "静水流涌之辉", "refine": 1, "level": 90 },
        "artifacts": [                 // 展开条件：提问点名 或 养成/配队意图
          { "set": "黄金剧团", "count": 4, "mainStats": { "生之花": "生命值", "理之冠": "暴击率" } },
          { "set": "昔日宗室之仪", "count": 1 }   // 非展开时为概览：仅 set + count
        ]
      }
    ]
  }
}
```

**schema 约束（AI 服务侧强校验，违反即 400）**：

- `characters[].weapon` 必须是**对象**（传字符串会 400），字段名用 `refine`
- `artifacts[].mainStats` 的 **key 是中文部位名**（生之花 / 死之羽 / 时之沙 / 空之杯 / 理之冠），value 是词条名（不含数值）
- `characters` 是数组，元素为对象；`talents` 为 `{normal, skill, burst}` 三个整数

### 3.3 流式补全（P3，协议先定好，实现可后置）

`POST /v1/complete/stream`（`text/event-stream`）

```
event: delta   data: {"text":"胡桃"}
event: delta   data: {"text":"是火元素"}
event: done    data: {"tokens":{"total":1045},"finishReason":"stop"}
event: error   data: {"message":"上游超时"}
```

主服务侧对应 `POST /api/chat` 的 `stream=true`（**已实现**，契约见 `docs/04-API接口文档.md` §2.2；`dto.ChatRequest.Stream` 不再是"预留"）。

## 7. 强制规范（继承 `AGENTS.md`）

1. **所有业务数据入数据库，禁止硬编码**——提示词、模型清单、场景配置、限流阈值一律进表或配置
2. 分层严格：Handler 不碰 DB、Service 不感知 HTTP、`pkg/*` 不依赖业务
3. 错误必须显式处理并记日志（`logger.L().Errorw`），**禁止用 `_ =` 吞错**
4. 统一响应信封与错误码；不向前端暴露内部错误细节
5. 密钥只通过环境变量注入，禁止入库/入仓
6. 前端不得直连 AI 服务（统一经主服务 `/api`），AI 服务不得暴露到公网
7. 提交前必须通过：`npm run lint` / `npm run build`（前端）、`go build ./...` / `go vet ./...`（后端）

**AI 专属禁止项**：

- ❌ 在 AI 服务里实现用户注册/登录/JWT（那是主服务的职责）
- ❌ AI 服务直接写 `chat_*` 业务表（会话持久化由主服务负责）
- ❌ 把 LLM 的原始错误或 API Key 透传给前端/日志
- ❌ 无鉴权暴露 `/v1/*`
- ❌ 同步请求链路上做「重试 + 长超时」叠加导致主服务连接被占满（重试 ≤ 1 次，总耗时需有上限）

## 8. 落地建议

- **代码位置**：若与主服务同仓，建议 `server/cmd/ai-service/` 或独立仓 `teyvat-ai/`；同仓可复用 `pkg/logger`、`pkg/response` 等基础设施（注意不要跨服务 import 业务包）
- **本地联调**：AI 服务 8090，主服务 8080，前端 5173；根目录 `npm run dev` 已能拉起前两个，AI 服务建议追加一条 `npm run dev:ai`
- **测试基线**：`curl -H "X-AI-Key: $KEY" -X POST http://127.0.0.1:8090/v1/complete -d '{...}'` 返回 `code:0`；再做一遍「停掉 AI 服务」的降级测试

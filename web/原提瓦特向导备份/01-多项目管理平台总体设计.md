# 01 · 多项目管理平台总体设计

> 状态：已评审
> 背景：本后台（CodeLog 管理系统）的定位从「单项目管理后台」升级为「多项目统一管理平台」，各业务项目的后台管理能力统一收口到本系统。首个接入项目为「AI 提瓦特向导」（见 `02-提瓦特向导后台接入设计.md`）。

---

## 1. 目标与原则

### 1.1 目标

1. 一个后台管理多个业务项目，登录一次、管理所有项目。
2. 接入新项目时，不改 AdminShell 骨架代码，只加配置与适配。
3. 各项目凭证（密钥、Token）不暴露到浏览器。
4. 权限统一收口在本系统，业务项目无需感知「谁在操作」。

### 1.2 核心原则

| 原则 | 说明 |
| --- | --- |
| 项目注册表驱动 | 接入一个新项目 = 注册表加一条配置 + 一个网关适配 |
| 密钥不出服务端 | 业务项目的凭证只存本系统服务端，浏览器只持有本系统的 Session |
| 权限收口在本系统 | 本系统校验管理员身份后才代理请求到业务项目 |
| 异构系统走 HTTP | 各项目保持独立技术栈与数据库，不共库直连 |

---

## 2. 总体架构

```
AdminShell（本系统，Next.js）
    │  Session 鉴权（沿用现有管理员登录）
    ▼
┌─────────────────────────────────────┐
│  项目接入层（新增）                    │
│  ProjectGateway：项目注册表 + 服务端代理 │
└──────┬──────────────┬───────────────┘
       │              │
   teyvatGuide    （未来的其他项目…）
   /api/admin/*
   凭证存服务端
```

- **AdminShell**：现有管理后台外壳，菜单按「系统管理 + 项目接入」两大分组组织。
- **ProjectGateway**：统一的 Route Handler（`/api/gateway/[project]/*`），负责凭证注入、转发、响应归一化。
  （是否需要把它抽成**独立的中转网关服务**：**暂缓**，触发条件见 `05-中转网关项目设计.md` §2.1；当前形态对单消费者场景已经够用。）
- **业务项目**：保持独立部署、独立数据库，仅暴露管理 API。

## 3. 数据模型

### 3.1 managed_projects（项目注册表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | PK | 自增主键 |
| code | VARCHAR 唯一 | 项目标识，如 `teyvat-guide` |
| name | VARCHAR | 显示名，如「AI 提瓦特向导」 |
| base_url | VARCHAR | 服务地址，如 `http://127.0.0.1:8080` |
| auth_type | VARCHAR | 鉴权方式：`header-key` / `bearer` / `none`（预留扩展） |
| auth_header | VARCHAR | `header-key` 方式使用的请求头名，如 `X-Admin-Key` / `X-AI-Key`（默认 `X-Admin-Key`） |
| auth_config | VARCHAR | 凭证（如 X-Admin-Key），建议加密存储 |
| health_path | VARCHAR | 健康检查路径，如 `/api/health` |
| status | VARCHAR | `enabled` / `disabled` |
| created_at / updated_at | DATETIME | 时间戳 |

未来接入新项目只新增一行数据 + 一个页面适配，不动框架代码。

## 4. 集成方式选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 服务端网关代理 | Route Handler 转发到目标项目，服务端注入凭证 | **采用** |
| B. 浏览器直连 | 前端直接调业务项目，密钥放前端 | 否：密钥泄露、跨域、无法控权 |
| C. 共库直查 | 本系统直接读业务项目数据库 | 否：Schema 耦合，对方改表即断，违背多项目定位 |

网关代理统一职责：

1. 校验本系统管理员 Session；
2. 按 `code` 查注册表，注入凭证（如 `X-Admin-Key`）；
3. 转发请求到 `base_url + path`；
4. 统一拆解业务项目响应体 `{ code, message, data }`；
5. 错误归一化（404 / 502 / 503 等映射为本系统可读提示）。

附带好处：浏览器不直连业务项目，天然无跨域问题，业务项目无需配置 CORS。

## 6. 实施节奏

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| M1 | `managed_projects` 表 + 网关代理 Route Handler + 健康检查页（✅ 已完成） | 打通链路，工作量最小 |
| M2 | 直连业务库维护映射数据（数据直连 + reload 走网关的混合模式），见 `02-提瓦特向导后台接入设计.md` §3.1 | 同实例可直连为前提 |
| M3 | 业务项目补管理接口 → 用户/对话管理页 | 需要业务项目侧配合 |
| M4 | 沉淀「新项目接入规范」 | 注册表配置 + 网关适配器 + 页面模板，供未来项目复用 |

---

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 响应体风格不一致 | 业务项目普遍采用 `{ code, message, data }`，网关层统一归一化为本系统风格 |
| 大 payload 导入超时 | 导入页支持分段导入 + 明确超时与进度提示 |
| 业务项目下线 | 健康检查探测失败时页面明确提示「服务不可达」，禁用相关操作入口 |
| 凭证轮换 | 凭证集中在注册表 `auth_config`，轮换只改配置 |

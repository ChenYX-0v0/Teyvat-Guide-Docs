# 09 · AI 上下文与成本优化（待办）

> 状态：**暂缓，待排期**。本文件记录已识别的问题与既定方案，避免遗忘。
> 背景：AI 派蒙服务接入后，单次对话 token 消耗偏高（实测最高 **5516**），需要做上下文与历史裁剪。
> 相关代码：`server/internal/service/chat.go`、`server/internal/service/ai_context.go`；对接契约见 `docs/08`、`03-主服务对接说明.md` §6。

---

## 1. 实测数据（2026-09-10 ~ 09-11）

| 场景 | 实测 tokens | 说明 |
| --- | --- | --- |
| 匿名闲聊（无上下文） | 625 ~ 673 | 仅 system + 单轮 prompt |
| 登录 + 绑定 UID，养成类问题 | **5516** | 含玩家上下文 + 20 条历史 + 思考模式输出 |
| 登录，同一会话续问 | 1514 | 上下文 + 历史累积 |

结论：**上下文与历史都缺少预算控制**，且历史里存在冗余内容（见 §2）。

---

## 2. 待办清单

### P1 · 历史按 token 预算裁剪（替代固定 20 条）

- **现状**：`chat.go` 固定取最近 `historyLimit = 20` 条，长对话会线性推高输入 token。
- **方案**：改为「条数上限 20 + token 预算 1200」双限制，从最近往前累计，超预算即截断；**始终保留最新一条**。
- **改动点**：新增 `buildHistory(msgs, question, budget)`，替换 `Ask` 中的历史组装；`roughTokens` 可直接复用。
- **预期收益**：长会话输入 token 下降 50%~70%。
- **验收**：构造 20 轮长会话，观察 tokens 稳定在预算附近不再增长。

### P1 · 历史中「当前提问」重复发送（疑似 bug，建议优先修）

- **现状**：`Ask` 先 `AppendMessage(用户提问)` 落库，紧接着 `ListMessages` 取历史 → **历史最后一条就是本次提问**，而它又通过 `prompt` 字段单独传了一次 → **同一句话发两遍**。
- **影响**：重复计费 + 语义重复，可能干扰模型（实测中模型偶发复读倾向）。
- **方案**：组装历史时丢弃尾部与 `question` 相同的那条 user 消息。
- **验收**：抓 AI 服务请求日志，确认 `history` 末条不是本次提问。

### P2 · 降级兜底文案进入历史

- **现状**：`aiDegradeReply`（"派蒙现在有点晕乎乎的…"）失败时仍落库，后续会作为 assistant 消息进入历史。
- **影响**：污染上下文，模型可能模仿；且它不承载有效信息。
- **方案**：`buildHistory` 中过滤 `content == aiDegradeReply` 的消息（落库保留，仅不参与上下文）。

### P2 · 上下文预算与附带策略

- **现状**：`ctxTokenBudget = 1500`，且养成/配队意图一律附带 6 条 `otherCharacters` 摘要。
- **方案**：
  1. 预算下调至 **900**；
  2. 摘要仅在真正需要全局视角时附带——配队意图，或养成意图但**未命中具体角色**时；已命中角色的提问不再推摘要。
- **预期收益**：上下文体积下降约 40%，且不影响命中角色的回答质量。
- **验收**：`ai context attached` 日志（如需可加 `tokens` 字段观测）单次 ≤ 900。

### P3 · 可观测性：无 token / 成本指标

- **现状**：只有 AI 服务返回的 `tokens.total` 落库到 `chat_messages.tokens`，无按用户/会话的聚合视图，也没有上下文体积日志。
- **方案**：日志补 `historyTokens` / `contextTokens`；后续在管理端做「按用户 / 按会话 / 按天」的 token 与成本统计。
- **归属**：与 `docs/08` §5 的 P4（成本与配额）合并推进。

### P4 · 模型档位与提示词前缀稳定化（AI 服务侧）

- 简单闲聊走便宜档、养成分析再升档（AI 服务已有 `analysis` 升级能力，需确认触发口径）。
- system 提示词前缀保持稳定以命中上游缓存（`ai.system` 留空时由 AI 服务负责，主服务的动态区不得插在人格之前）。

---

## 3. 暂缓原因与重启条件

- 当前处于功能联调阶段，优先保证**回答质量与契约稳定**，不在此时引入裁剪逻辑（裁剪会改变上下文，需重新验证回答质量）。
- **重启条件**：AI 对话进入日常使用、或出现成本/延迟压力时，按 P1 → P2 → P3 → P4 顺序推进（P1 两项改动小、收益大，建议打包一起做）。

---

## 4. 实施注意

1. 裁剪策略变更后必须**回归回答质量**：验证「结合我面板说」类问题仍能读到正确面板（对比 `docs/08` §6 的实测记录）。
2. `roughTokens` 是粗估（中文 1 字符 ≈ 1 token），仅用于预算控制，不可当作计费依据。
3. 任何裁剪都不得让「最新一条问题」丢失。

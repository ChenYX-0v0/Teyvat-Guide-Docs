## 1. 实测数据（2026-09-10 ~ 09-11）

| 场景 | 实测 tokens | 说明 |
| --- | --- | --- |
| 匿名闲聊（无上下文） | 625 ~ 673 | 仅 system + 单轮 prompt |
| 登录 + 绑定 UID，养成类问题 | **5516** | 含玩家上下文 + 20 条历史 + 思考模式输出 |
| 登录，同一会话续问 | 1514 | 上下文 + 历史累积 |

结论：**上下文与历史都缺少预算控制**，且历史里存在冗余内容（见 §2）。

> 上表为**改前**数据。§2 的 P1 落地后，历史已有明确上限（20 条 / 1200 tokens 预算）且不再重复发送本次提问；
> 上下文（`ctxTokenBudget = 1500`）与「附带 6 条 otherCharacters 摘要」的策略未变，真实 token 曲线待补测。

## 2. 待办清单

### ✅ P1 · 历史按 token 预算裁剪（替代固定 20 条）——已完成（2026-09-12）

- **现状（改前）**：`chat.go` 固定取 `historyLimit = 20` 条，长对话会线性推高输入 token。
- **落地**：`buildHistory(recent, question)` 实现「条数上限 20 + token 预算 1200」双限制，从最近往前累计，超预算即截断；**始终保留最新一条**（复用 `roughTokens` 粗估）。
- **顺带修掉的两个问题**：
  1. 原来用 `ORDER BY created_at ASC LIMIT 20`，取到的是**最旧的 20 条**——长会话永远停在开头。已改为 `ListRecentMessages`（`created_at DESC, id DESC` 取最近 N 条后反转为正序；`id` 作为同秒内的次序兜底）。
  2. 历史里若混入 role=`system` 的脏数据会被 AI 服务 400，现只按落库的 user/assistant 组装。
- **单测**：`server/internal/service/chat_history_test.go`（5 例：去重、过滤降级文案、预算截断、超预算仍保留最新、空历史）。
- **待补**：长会话真实 token 曲线（构造 20 轮）尚未实测记录，重启条件见 §3。

### ✅ P1 · 历史中「当前提问」重复发送——已完成（2026-09-12）

- **现状（改前）**：`Ask` 先 `AppendMessage(用户提问)` 落库，紧接着取历史 → **历史最后一条就是本次提问**，而它又通过 `prompt` 字段单独传了一次 → **同一句话发两遍**。
- **影响**：重复计费 + 语义重复，可能干扰模型（实测中模型偶发复读倾向）。
- **落地**：`buildHistory` 丢弃尾部与 `question` 相同的那条 user 消息（仅在**尾部**比对，避免误删历史中内容相同的真实提问）。
- **验收**：单测 `TestBuildHistoryDropsCurrentQuestion` 覆盖。

### ✅ P2 · 降级兜底文案进入历史——已完成（2026-09-12）

- **现状（改前）**：`aiDegradeReply`（"派蒙现在有点晕乎乎的…"）失败时仍落库，后续会作为 assistant 消息进入历史。
- **影响**：污染上下文，模型可能模仿；且它不承载有效信息。
- **落地**：`buildHistory` 中过滤 `content == aiDegradeReply` 的消息（**落库保留**，仅不参与上下文）。
- **验收**：单测 `TestBuildHistoryFiltersDegradeReply` 覆盖。

### P2 · 上下文预算与附带策略

> **注（2026-09-12）**：V2 资料查表（`referenceTokenBudget = 400`）已加入同一上下文预算池，
> 本项调整时要把「玩家档案 1500 + 资料 400」一起算，别让资料把面板挤掉（AI 服务超预算会整条丢弃末尾角色）。

- **现状**：`ctxTokenBudget = 1500`，且养成/配队意图一律附带 6 条 `otherCharacters` 摘要。
- **方案**：
  1. 预算下调至 **900**；
  2. 摘要仅在真正需要全局视角时附带——配队意图，或养成意图但**未命中具体角色**时；已命中角色的提问不再推摘要。
- **预期收益**：上下文体积下降约 40%，且不影响命中角色的回答质量。
- **验收**：`ai context attached` 日志（如需可加 `tokens` 字段观测）单次 ≤ 900。

### P3 · 可观测性：无 token / 成本指标

- **现状**：只有 AI 服务返回的 `tokens.total` 落库到 `chat_messages.tokens`，无按用户/会话的聚合视图，也没有上下文体积日志。
- **方案**：日志补 `historyTokens` / `contextTokens`；后续在管理端做「按用户 / 按会话 / 按天」的 token 与成本统计。
- **归属**：与 `docs/08` §5 的 P4（成本与配额）合并推进。

### P4 · 模型档位与提示词前缀稳定化（AI 服务侧）

- 简单闲聊走便宜档、养成分析再升档（AI 服务已有 `analysis` 升级能力，需确认触发口径）。
- system 提示词前缀保持稳定以命中上游缓存（`ai.system` 留空时由 AI 服务负责，主服务的动态区不得插在人格之前）。

## 3. 排期与重启条件

- **曾暂缓的原因**：裁剪会改变上下文、需重新验证回答质量，功能联调期不宜扰动。
- **已重启（2026-09-12）**：落地 §2 的两项 P1（改动小、收益大，打包同批做），并借流式改造把历史组装收敛为**流式/非流式共用的 `buildHistory`**，避免两条链路行为漂移。
- **仍需推进**：AI 对话进入日常使用、或出现成本/延迟压力时，按 P2（上下文预算与附带策略）→ P3（可观测）→ P4（档位与缓存）顺序继续。

---

## 4. 实施注意

1. 裁剪策略变更后必须**回归回答质量**：验证「结合我面板说」类问题仍能读到正确面板（对比 `docs/08` §6 的实测记录）。
2. `roughTokens` 是粗估（中文 1 字符 ≈ 1 token），仅用于预算控制，不可当作计费依据。
3. 任何裁剪都不得让「最新一条问题」丢失。

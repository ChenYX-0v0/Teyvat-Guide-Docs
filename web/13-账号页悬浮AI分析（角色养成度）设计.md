# 13 · 账号页悬浮 AI 分析（角色养成度）

> **状态**：**设计已定，待实现**（2026-09-26 成文）
> **一句话**：账号页右下角常驻一个悬浮按钮；点开是与派蒙的对话面板，并**立刻针对当前选中的角色**做一次「养成度体检」。
> **每个角色只自动体检一次**；**强制刷新档案（`refresh=true`）成功后解锁重做**。
> **关联**：`04-API接口文档.md` §2.1（对话接口）/ §2.6（配额）、`../shared/07-前端埋点与使用统计.md`（事件字典）、
> `02-前端开发规范.md` §5.1（移动端硬性要求）、`../ai/05-开发路线图.md`（提示词场景与资产数据）、`12-C端UI优化方案.md`（C 端视觉基线）。

## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 判断标准 |
| --- | --- | --- |
| 1 | **不跳页就能问**：看档案时冒出的疑问，就地解决 | 从账号页任意位置 ≤1 次点击进入对话 |
| 2 | **开箱即分析**：不用想"该怎么问"，点开就得到该角色的养成体检 | 打开面板后 3 秒内开始出字 |
| 3 | **不重复烧额度**：同一角色的自动体检只发生一次 | 反复开关面板不会重复消耗 token |
| 4 | **数据变了能重查**：用户强制刷新档案后，可以重新体检 | 刷新成功后同一角色可再次自动体检 |

### 1.2 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| 进页面就**全角色**批量体检 | 展柜可达 12 个角色 × 每次 1.5~3k token = 单次访问烧掉数万 token，纯烧钱且大部分结论用户没看 |
| 定时/后台自动分析 | 同上；且用户不在场时消耗额度不合常理 |
| 独立的"分析结果"存储与评分体系 | 复用对话链路即可（结论落在会话里、成本落在 `chat_messages`，后台本来就能查）——**不新增表** |
| 改动 AI 服务的人格与既有场景 | `paimon_base / rules / fewshot` 是前缀缓存的关键，动它会让全站缓存 miss 一次 |
| 把面板做成完整对话页（历史列表 / 改名 / 删除） | 面板是"就地快问"，完整管理回对话页 |

## 2. 现状事实（决定了方案怎么写）

| # | 事实 | 出处 | 对本设计的影响 |
| --- | --- | --- | --- |
| 1 | 对话是 `POST /api/chat`：`{sessionId, message, stream}`，SSE 帧序 `session → delta* → (done \| error)` | `04 §2.1`、`api/chat.ts` | 面板直接复用 `chatApi.stream`，无需新接口 |
| 2 | **强制登录**（匿名 401/403），且**配额与并发检查在建会话之前**，超限返回 429 `{reason, used, limit, resetAt}` | `04 §2.6`、`chat.go` | 自动体检要学会处理 429；且**不能**把失败算作"已体检" |

| 4 | **上下文是后端自动注入**的：`detectGoal(问题)` 关键词判意图（含"养成"→`character_build`）+ `mentionedNames(问题)` 命中角色名 → 给该角色展开**圣遗物明细**；V2 资产资料同样按**角色名**命中"推荐词条" | `service/ai_context.go` | 消息里带**角色名 + "养成"**即可命中现有链路 → **P0 零后端改动** |
| 5 | 玩家档案上下文有 **1500 token 预算**，超预算时**从尾部整条丢弃**并写"其余 N 个角色已省略" | `ai_context.go:82` | ⚠️ 目标角色若排在展柜靠后，**可能被裁掉**（分析对象错位）→ 见 §5 与 D6 |
| 6 | AI 服务只读 `paimon_base / paimon_rules / paimon_fewshot` 三个场景（`STABLE_SCENES`） | `shared/03 §5.2` | "新增分析场景"= **要改 AI 服务**（小改，但不是零改动）→ 放 P1 |
| 7 | 后台「对话记录」已能看每条的 token / 降级 / 耗时 / 是否注入过玩家档案与资产 | `admin/06`、`chat_sessions.has_player` | 自动体检的成本与命中情况**天然可观测**，不需要新看板 |
| 8 | 移动端：抽屉/浮层**不能**放在带 `backdrop-blur`/`transform` 的祖先里（Header 有 `backdrop-blur`）；无常驻底部导航；页面用 `h-dvh` + 安全区 | `02 §5.1`、`AppLayout`/`MobileNav` | 面板必须渲染在 **Header 之外**（与 `MobileNav` 同位置），并处理安全区 |

| 10 | 埋点体系已上线（14 个事件、白名单强校验） | `shared/07`、`usage.go` | 新事件必须**同时**加到后端白名单，否则被静默丢弃 |

## 3. 用户旅程

| 情形 | 期望行为 |
| --- | --- |
| **首次打开**（已登录 + 已绑定 UID + 该角色未体检过） | 面板打开 → 顶部显示角色头像/名字/等级 → 自动发出体检提问 → 流式出字 → 完成后标记"已体检" |
| **再次打开，同一角色已体检过** | 面板打开 → **不自动发问** → 直接展示该角色的历史分析（读会话消息）→ 底部输入框可继续追问 |
| **同一会话内换了角色**（面板里能切换/或回页面切换后重开） | 新角色未体检 → 自动体检；已体检 → 只展示历史 |
| **强制刷新档案成功后** | 清空该 uid 的"已体检"记录 → 当前角色可再次自动体检（用新数据重查一遍） |
| **配额不足（429）** | 展示服务端文案（含重置时间）+「明天再来」提示；**不计入已体检**，下次打开还能自动重试 |
| **上游/网络失败** | 展示可读错误 +「重试」按钮；**不计入已体检**；同一角色连续失败 2 次后本次会话不再自动重试（避免反复烧额度），手动重试不受限 |
| **未登录** | 面板显示登录引导（复用对话页口径），不做任何请求 |
| **已登录但未绑定 UID** | 悬浮按钮**置灰**，提示"先绑定游戏 UID 才能做养成度体检"（没有面板数据，分析只会是空话） |
| **绑定了但展柜为空** | 提示"该账号未公开展柜角色"（复用 `account.emptyShowcase` 口径） |

## 4. 触发与计数规则

### 4.1 状态定义

```
analyzed: Map<characterId, { at: number }>   // 按 uid 分桶：teyvat:analysis:done:<uid>
countedOnce(uid, charId) = analyzed[charId] != null
```

- 存 **localStorage**（P0；见 D2）：不新增后端表、不产生新的个人数据；
- 只记 **characterId + 时间戳**，不记结论内容（结论在会话里）。

### 4.2 自动体检的触发条件（全部满足才自动发问）

1. 面板被打开（用户显式点击悬浮按钮）；
2. 已登录（有 token）且已绑定 UID；
3. 当前选中角色存在，且 `countedOnce(uid, charId) === false`；
4. 当前没有正在进行的流式请求（避免与对话页的流并发撞 429）；
5. 当日自动体检次数未超上限（P0 建议 ≤ 20 次/人/日，纯前端计数；后端配额仍是硬闸）。

### 4.3 计数（"已体检"）的写入条件

> **只有收到 `done` 帧（流正常结束）才写入 `analyzed`**。
> 429 配额、网络失败、流中断、用户中途关闭 —— **一律不写**，下次打开可重试。

配套：同一 `(uid, charId)` 连续失败 ≥2 次时，**本次页面会话内**不再自动重试（手动「重新分析」仍可用）。

### 4.4 重置条件

| 触发 | 动作 |
| --- | --- |
| **强制刷新档案成功**（前端以 `refresh=true` 查询且拿到 `data`） | 清空该 uid 的 `analyzed`（保留会话 → 历史分析仍在，可回看） |
| **解绑 / 换绑 UID** | 清空该 uid 分桶（下一个 uid 从零开始） |
| 用户清浏览器数据 | 自然重置（可接受：最坏情况多花一次体检的 token） |

> ⚠️ 前端只能感知**自己发起的**刷新；跨设备的刷新不会重置计数。若要跨设备精确，
> 需后端在档案里回传快照 `updatedAt` 作 epoch（P1 可选，见 D2）。

### 4.5 手动（重新）分析

面板内的「重新分析」按钮 = 用户显式提问，**不受"每角色一次"限制**（本质是他自己问了一句），
但**不改变** `analyzed` 状态（即不会让"自动体检"重新触发）。

## 5. 上下文与一致性："分析的就是你看到的那套"

- 面板**不发送**任何面板数据；后端按绑定 UID 取**同一份快照**（`Query(uid, false)`，缓存优先）→ 与页面展示同源；
- 提问模板（i18n，**用户口吻**，因为它会作为普通消息出现在会话与后台对话记录里）：

  > 「帮我看看**{角色名}**现在的**养成**度：圣遗物词条对不对、武器和天赋还差什么，按优先级告诉我该先改什么。」

  → 同时命中：① `character_build` 意图（关键词"养成"）② 角色名点名 ③ V2 推荐词条（按角色名命中）✓

- ⚠️ **已知风险（事实 #5）**：目标角色在展柜里排序靠后时，可能因 1500 token 预算被**从尾部裁掉**，
  导致分析对象错位。P0 用"点名 + 该角色通常会被展开"兜底，并按下面这条**实测验收**：
  - 验收：对**展柜最后一个角色**做体检，回答必须正确引用该角色的圣遗物主词条（不能张冠李戴）；
  - 若实测不稳定 → 立刻补 P1 的 `focus`（见 §6.2）。

- 快照若被后端按 TTL 刷新，分析可能基于比页面**更新**的数据。P0 接受（并在面板底部注明"以最新档案为准"）；
  若要严格一致需后端支持"只读当前快照不刷新"（D7）。

## 6. 接口设计

### 6.1 P0：零后端改动（推荐先做）

复用 `POST /api/chat`（`stream=true`），只改前端：**新增一个独立会话** + 自动发送上面那条模板消息。

```
POST /api/chat
{ "sessionId": "<该 uid 的分析会话 id，首次留空>", "message": "帮我看看芙宁娜现在的养成度…", "stream": true }
→ SSE: session / delta* / done
```

### 6.2 P1：请求体加 `focus`（可选，用于"目标角色兜底"）

```jsonc
// dto.ChatRequest 增字段（向后兼容：缺省行为不变）
{ "sessionId": "...", "message": "...", "stream": true,
  "focus": { "characterId": 10000089, "name": "芙宁娜" } }
```

后端改动（小）：
- `dto.ChatRequest` 加 `Focus *ChatFocusDTO`；
- `buildPlayerContext(ctx, userID, question, focus)` → 透传给 `BuildPlayerContext(profile, question, focus)`；
- 在 `ai_context.go` 里：**focus 命中的角色置于列表首位、必定注入明细**（不受预算裁剪影响），
  且当 focus 存在时不再对所有角色展开明细（省 token）。

### 6.3 P1（可选）：新增分析场景 `paimon_analysis`

- 需要 AI 服务侧把该 key 加进 `STABLE_SCENES` 并决定拼接顺序（涉及前缀缓存）；
- 收益：把"体检输出结构"从用户消息里挪到系统侧，回答更稳定、也更容易被运营调优（提示词管理页可改）；
- 在此之前，输出结构先写进消息模板（P0）。

## 7. UI 设计

### 7.1 悬浮按钮（FAB）

| 项 | 取值 |
| --- | --- |
| 位置 | `fixed right-4 z-40`，垂直位置 `bottom-[max(1rem,env(safe-area-inset-bottom))]`（无底部导航，只需避开安全区） |
| 尺寸/样式 | 48~56px 圆形，金色渐变 + `shadow-panel`，内含派蒙/对话图标；`aria-label` 走 i18n |
| 状态 | 未绑定 UID → 置灰（`disabled` + `title` 说明）；面板打开时按钮切换为关闭态 |
| 渲染位置 | **必须放在 Header 之外**（Header 的 `backdrop-blur` 会成为 fixed 后代的包含块）→ 与 `MobileNav` 同级，或 portal 到 `body` |

### 7.2 面板

| 断点 | 形态 |
| --- | --- |
| `< md`（手机） | **底部抽屉**：`fixed inset-x-0 bottom-0 h-[85dvh] rounded-t-2xl`，遮罩点击/Esc 关闭，开时锁背景滚动；输入框 sticky 在底部并处理安全区与软键盘 |
| `≥ md`（桌面） | **右下浮动窗口**：`400 × 600`，距右下各 16~24px，圆角 + `shadow-panel`，可关闭（不做拖拽/缩放） |

结构：`头部`（角色头像 + 名字 + `Lv.` + 「重新分析」+ 关闭）→ `消息区`（复用 `MessageBubble` + 流式呼吸光标）
→ `输入区`（复用 `ChatInput` 的样式，`text-base sm:text-sm` ≥16px）→ `底部说明`（"体检消耗 AI 额度 · 结论仅供参考，以最新档案为准"）。

### 7.3 面板内文案与状态（i18n 键草案）

| 场景 | 文案要点 | key 草案 |
| --- | --- | --- |
| 正在自动体检 | 顶部小字「正在给 {角色} 做养成度体检…」 | `analysis.autoRunning` |
| 已体检过 | 顶部小字「{角色} 的体检报告（{时间}）」 | `analysis.doneAt` |
| 重新分析 | 按钮 | `analysis.rerun` |
| 未绑定 UID | 空态：说明为什么必须先绑定 | `analysis.needBinding` |
| 无展柜角色 | 空态 | `analysis.emptyShowcase` |
| 配额不足 | 直接展示服务端 `message` + 重置时间 | （复用 `chat.quota*`） |
| 失败 | 错误 + 重试 | `analysis.retry` |
| 底部说明 | 额度与免责 | `analysis.footnote` |

### 7.4 无障碍与移动端硬约束（对齐 `02 §5.1`）

- 面板 `role="dialog" aria-modal="true"`；打开时焦点移入输入框，Esc 关闭，关闭后焦点回到 FAB；
- 流式输出容器 `aria-live="polite"`（读屏逐步播报，不打断）；
- 输入元素字号 ≥16px（iOS 不放大页面）；页面高度继续用 `dvh`；375 / 390 / 414 三档回归；
- 不引入新的滚动陷阱：面板内部滚动，锁 `body` 滚动。

### 7.5 选中角色的传递（需要一处小重构）

现状：`selectedId` 在 `PlayerProfileView` 内部（事实 #9）→ 方案：**把选中态提升到 `AccountPage`**（受控 props 下传），
`AccountPage` 同时持有"当前选中角色"供 FAB 使用。不引入新的全局 store（改动最小、无新概念）。

## 8. 成本与配额

| 项 | 说明 |
| --- | --- |
| 单次体检成本 | 与普通提问同量级（上下文多一份该角色的圣遗物明细 + 推荐词条），**计入既有日配额**（默认 10 万 token/人/日） |
| 是否豁免 | **不豁免**（D3）：豁免会让"额度"这一唯一硬闸失效，也让成本不可见 |
| 上限 | 每角色 1 次（自动）+ 每日自动体检 ≤ 20 次（前端软限）+ 服务端配额与并发硬限（429） |
| 可观测 | `chat_messages` 已记 token/降级/耗时，`chat_sessions.has_player` 标记是否注入了玩家档案 → 后台「对话记录」直接可查，**不需要新看板** |
| 失败不计数 | 只有 `done` 才计数，避免"失败也烧一次"变成常态 |

## 10. 分期与验收标准

### P0 · 能用（预计 0.5~1 天，**零后端改动**）

- [ ] FAB + 面板（移动抽屉 / 桌面浮窗）+ 复用流式对话
- [ ] 自动体检（模板消息）+ "每角色一次"门闩 + 刷新重置 + 429/失败不计数
- [ ] 未登录/未绑定/空展柜/配额不足四种空态与错误态
- [ ] 选中角色提升到 `AccountPage`；埋点 4 个事件（含后端白名单）

**验收**：
1. 首次点开 → 自动出字，且**回答里出现该角色的圣遗物主词条**（不是别的角色）；
2. 关掉再点开同一角色 → **不再发请求**（可用浏览器 Network 面板截图证明）+ 能看到上次结论；
3. 切到另一个角色再点开 → 会自动体检一次；再切回来 → 不重复；
4. **勾选"强制刷新"查询成功后**，同一角色可再次自动体检；
5. 把日配额调成 1（或用一个已耗尽额度的账号）→ 面板显示 429 文案，且**不写"已体检"**，次日/恢复后可自动重试；
6. 375 / 390 / 414 三档：面板不溢出、输入框不被软键盘遮、FAB 不被安全区压住；
7. `lint` 0 error / `build` 通过。

### P1 · 更稳更省（预计 1 天）

- [ ] 请求体 `focus`（目标角色必注入 + 只展开该角色，省 token）—— **若 P0 验收第 1 条不稳定则提前**
- [ ] 快照 epoch（后端回传 `updatedAt`，跨设备也能正确重置）
- [ ] （可选）新增 `paimon_analysis` 场景，把输出结构移到系统侧

### P2 · 按需

- [ ] 面板内切换角色（不返回页面）
- [ ] 体检结论生成"改进清单"卡片（需要结构化输出，属产品级改造）
- [ ] 服务端"已体检"记录（跨设备一致 + 成本审计）

## 11. 风险与对策

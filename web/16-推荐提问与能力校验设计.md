## 0. 为什么先做能力校验

推荐提问的失败模式不是"推得平庸"，而是**推了一个我们答不出的问题** ✗ ——用户点进去，得到的是一句「派蒙这边没有查到欸」✓，比不推荐更伤。

现状是**回答阶段才知道有没有资料** ✓，而且只覆盖"整张卡都没有"这一种：

| 层 | 代码位置 | 覆盖 | 缺口 |
| --- | --- | --- | --- |
| 名字命中（数值/词条） | `PlayerService.*ForQuestion` → `BuildAssetSummary`（`server/internal/service/ai_context.go`） | 问题里出现的角色 / 套装名，命中但库里无数值 ⇒ 显式写「本服暂无该角色的资料」✓（V2.3 保险） | 只管**数值与词条**，不管攻略卡；发生在**回答阶段** |
| 整卡存在性 | `character_guide.go` 的 `ForQuestion` | 查不到整张卡 ⇒ 返回空串 ⇒ 上层说"没有查到"✓ | 只判断"有没有卡"，不判断"卡里有没有这一段" ✗ |
| 字段级缺失 | `character_guide.go` 的 `renderGuide` | **无** ✗ —— `if text == "" { continue }` 静默跳过 | 卡存在、某段为空时，模型**看不到"这里没资料"** ✗ ⇒ 用记忆补 ✗ |
| 资源映射未命中 | `missings` 表（259 行） | asset_id（道具 / 图标翻译） | **与"问题能不能答"无关** ✗ |
| 提示词兜底 | `paimon_rules` 第 7 条 | 要求模型对「本服暂无资料」的对象承认不知道 | **软约束**，靠模型自觉 ✗ |

### 0.1 实测覆盖度（2026-10-17，线上库）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| `characters` | 124 | 游戏角色名表（含旅行者形态） |
| `character_guides` | 128 | 攻略卡；「旅行者」占 **8 张**（不同元素） |
| `character_mechanics` | 120 | 机制卡 |
| `team_pick` 为空 | **6** | 「XX 怎么配队」会踩空 |
| `graduation` 为空 | **18** | 「XX 毕业面板多少」会踩空 |
| `weapon_pick` / `relic_pick` 为空 | 0 | 全覆盖 |
| `preset_qas` | 12 | 匿名用户看到的预设，运营手工维护 |

⇒ 推荐「毕业线 / 配队」类问题时，**必须先过覆盖度过滤**，否则 18 / 6 个角色会推出空问题 ✗。

## 1. 能力校验（Capability Gate）

### 1.1 数据源（一条聚合 SQL，零新表 ✓）

```sql
SELECT g.character_id,
       g.name,
       g.team_pick    <> '' AS has_team,
       g.weapon_pick  <> '' AS has_weapon,
       g.relic_pick   <> '' AS has_relic,
       g.graduation   <> '' AS has_grad,
       g.talents      <> '' AS has_talents,
       (m.id IS NOT NULL)   AS has_mech
FROM character_guides g
LEFT JOIN character_mechanics m ON m.character_id = g.character_id;
```

⚠️ **按 `character_id` 关联，不要按 `name`** ✗ ——「旅行者」在 `character_guides` 里有 8 张同名卡（不同元素），按名字拼会串 ✓。

### 1.2 内存结构与刷新

照 `asset.Service` 的现成套路（启动全量载入，零 SQL 查询）：

```go
// service/capability.go（建议命名）
type Coverage struct {
    HasTeam, HasWeapon, HasRelic, HasGrad, HasTalents, HasMech bool
}

type CapabilityIndex struct {
    mu       sync.RWMutex
    byCharID map[uint]Coverage
    byName   map[string]uint   // 名字 → id（旅行者按元素卡名单独收）
    loadedAt time.Time
}
```

- **刷新策略**：TTL **60s** 惰性重载（`loadedAt` 过期才查库）✓ —— 攻略卡本来就"改完立即生效"（`character_guide.go` 顶部注释：不走内存缓存、每问直查库 ✓），TTL 60s 与这个口径不冲突；
- **不阻塞主链路**：重载失败沿用旧索引并打日志（`[capability] reload failed`）✓。

### 1.3 意图映射（唯一真源，写在代码里的一张小表）

| `intent` | 依赖字段 | 对应用户问法（示例） |
| --- | --- | --- |
| `team` | `has_team` | 「玛薇卡怎么配队」 |
| `weapon` | `has_weapon` | 「玛薇卡武器选哪个」 |
| `relic` | `has_relic` | 「玛薇卡圣遗物带什么」 |
| `graduation` | `has_grad` | 「玛薇卡毕业面板多少」 |
| `talents` | `has_talents` | 「玛薇卡天赋先升哪个」 |
| `mechanics` | `has_mech` | 「玛薇卡机制怎么打」 |

> ⚠️ 这张表是**意图定义**，不是业务数据；文案与模板一律走 i18n（见 §2.3）✓。

### 1.4 对外 API

```go
// CanAnswer 判断某角色某意图能不能用现有资料回答。
// 返回 (ok, reason)：ok=false 时 reason 是给人看的短原因（"该角色配队资料暂缺"）。
func (s *CapabilityService) CanAnswer(name string, intent Intent) (bool, string)

// CoverageOf 返回该角色各字段的覆盖情况（资料缺口看板 / 推荐过滤共用）。
func (s *CapabilityService) CoverageOf(name string) (Coverage, bool)
```

判定规则：

1. 角色不在索引里（新角色刚上线、卡还没导）⇒ `false`，reason = `资料暂未收录`；
2. `intent` 对应字段为 false ⇒ `false`，reason = `该角色 XX 资料暂缺`；
3. 其余 ⇒ `true`。

### 1.5 用在哪（两处，按优先级）

| 用途 | 位置 | 行为 |
| --- | --- | --- |
| **推荐候选过滤**（前置 ✓） | TODO-36 的候选生成之后 | `CanAnswer` 不过就丢弃该候选，**不降级成"猜你想问"** ✗ |
| **回答链路显式标注**（可选，需 A/B） | `renderGuide`（`character_guide.go`） | 现在是 `text == ""` 静默跳过 ✗；改成注入一行「· 配队思路：本服暂无该角色的配队资料」✓，让模型老实说"没收录"而不是编 ✓ |

⚠️ 第二项**不要一次全开** ✗：模型可能因此频繁念"没有资料"，先按 §4 的验收门做小流量对比 ✓。

### 1.6 降级与风险

- **fail-open**：索引不可用 ⇒ `CanAnswer` 一律 `true` ✓（宁可少拦，不能把对话卡死 ✗）；
- **与 asset 不是一回事**：前者判"攻略卡字段"，后者判"数值词条"，**不要合并** ✗；
- **旅行者**：8 张卡按元素区分，`name` 相同但 `character_id` 不同 ⇒ 判定必须带 `character_id`（前端推荐只推「旅行者·冰」这种带形态的显示名）✓。

### 1.7 测试（表驱动）

- 有卡无 `team_pick` ⇒ `CanAnswer(team)=false`；
- 整卡缺失 ⇒ 所有意图 false，reason 是「资料暂未收录」；
- 旅行者 8 张卡互不串；
- 索引重载失败沿用旧值。

## 2. 推荐提问（规则化，不含实时 LLM）

> **明确不做** ✗：不新增一次模型调用去"猜你想问"（延迟、成本、以及**编出答不出的问题** ✗）。判断依据见 `ai/07` TODO-36 §6 的调查结论。

### 2.1 现状（完全固定）

| 位置 | 来源 | 问题 |
| --- | --- | --- |
| 登录用户空态 | `web/src/pages/ChatPage.tsx` 里写死 3 条 `chat.emptySample1~3` | 与用户是谁、有什么角色无关 |
| 匿名 | `GET /api/preset-qa` → `preset_qas`（12 条，`sort` 排序） | 运营写什么就展示什么 |
| 回答之后 | 无 | 答完即止，没有"接着问"的引导 |

### 2.2 候选来源（优先级从高到低）

1. **profile**（个性化）：`player_characters` 里该 UID 的展柜角色（`in_showcase=1`，按 `last_seen_at` 倒序）取前 2~3 个，套「角色 × 意图」模板；
2. **followup**（追问）：取最近一轮会话里的角色，推**互补意图** —— 刚问 `team` ⇒ 推 `graduation` / `weapon`；刚问数值 ⇒ 推 `team`；
3. **hot**（兜底）：`preset_qas`（`enabled=1`）＋ 后续的热度池（TODO-37 预留，本期不做 ✗）。

每类候选都必须过 `CanAnswer` ✓，并去掉与最近 N 条已问问题重复的 ✗。

### 2.3 接口契约（草案）

```
GET /api/chat/suggestions?context=empty|after_answer&limit=4
（JWTAuthOptional：匿名也能调，但匿名侧前端不展示这块）

200
{
  "items": [
    { "id": "profile:10000135:team", "reason": "profile",
      "characterId": 10000135, "characterName": "玛薇卡", "intent": "team" }
  ]
}
```

**后端只返回结构化字段，不返回成品文案** ✓ —— 文案在前端 i18n 里拼（`suggestion.{intent}` 模板 + 角色名插值）✓，这样中英文两套都能出，也符合现有 `t()` 口径 ✓。

### 2.4 排序与去重规则

- 同一角色最多 **2** 条，同一意图最多 **2** 条（避免 4 条全是"玛薇卡 XX"）；
- 与最近 **5** 条用户提问做简单包含匹配去重（不引向量库 ✗）；
- 不足 `limit` 条时**回落现有 3 条** `samplers` ✓（保证空态永远有东西可点）；
- 缓存：按 `uid + context` 缓存 **5 分钟**（展柜不会秒变）✓。

### 2.5 前端落点

| 位置 | 组件 | 行为 |
| --- | --- | --- |
| 空态 | `ChatPage.tsx` 的 `samplers` 区块 | 优先渲染推荐，拿不到或用完则回落写死的 3 条 |
| 回答后 | `MessageBubble` 下方（或输入框上方一行 chips） | 只显示 2 条，点一下即发送 |

匿名用户仍是 `PresetQaPanel`（运营可控 ✓），**不改** ✗。

### 2.6 埋点（复用 `usage_events`）

| event | props | 用途 |
| --- | --- | --- |
| `chat_suggestion_exposure` | `context` / `count` | 曝光量 |
| `chat_suggestion_click` | `reason` / `intent` / `index` / `character_id` | 点击率与偏好 |
| `chat_suggestion_sent_to_answer` | `intent` | 点了之后是否真的完成回答（避免"点了但答不出"） |

## 4. 验收口径

**A（能力校验）**
- [ ] 18 个 `graduation` 为空的角色，`CanAnswer(graduation)=false`；
- [ ] 6 个 `team_pick` 为空的角色，`CanAnswer(team)=false`；
- [ ] 索引载入耗时 < 50ms（124 行，内存 map）；
- [ ] DB 故障时 fail-open，对话链路不受影响。

**B/C（推荐）**
- [ ] 推荐**可答率 100%**（这条是硬门 ✓，不达标不许上线 ✗）；
- [ ] 空态永远有 4 条可点（回落生效）；
- [ ] 有绑定用户的推荐里，**≥半数**带着自己展柜里的角色；
- [ ] 点击率对比"写死 3 条"的基线（埋点上线 1 周后看）。

## TODO-01 · 回答中出现 Markdown 标记影响观感

| 项 | 内容 |
| --- | --- |
| **发现时间** | 2026-09-12 |
| **状态** | **待决策**（方案未定） |
| **优先级** | 中（不影响功能，影响观感） |
| **影响范围** | 所有"分点建议"类回答（养成分析、配队建议等长回答） |
| **复现** | 问「帮我看看我的菲林斯」，回答里出现 `**结论先说：…**`、`**1. 普攻只有1级**` 等 |

### 现象

派蒙的回复里大量使用 Markdown 加粗与列表标记，前端按纯文本渲染时显示为字面的 `**`：

```
**结论先说：整体方向对，但有几个地方可以再抠一抠！**

**已经不错的部分：**
- 武器支离轮光精1 Lv.90，拉满了，没问题～
```

### 根因（三层）

| 层 | 问题 | 位置 |
| --- | --- | --- |
| 1 | **规则要求分点，但没规定用什么符号分点** | `paimon_rules` 第 5 条「再给分点建议，按优先级从高到低排」 |
| 2 | **few-shot 缺少"分点"场景的示范** | `paimon_fewshot` 三个示例全是 2~3 句短回答，**都没分点**——而示例比规则更管用 |
| 3 | LLM 默认输出习惯就是 Markdown | 不加约束必然如此 |

> 所以这不是"模型不听话"，而是**我们提出了分点要求，却没说分点用什么形式**。

### 候选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A 提示词收口** | ① `paimon_rules` 加一条明令禁止 Markdown **并给出替代写法**；② `paimon_fewshot` 补一个**分点示例** | 零代码、可热更新、不额外耗 token | 不保证 100%（长回答偶有回退）；改提示词会让前缀缓存 miss 一次 |
| **B 前端渲染 Markdown** | React 引入 `react-markdown`（默认不渲染原始 HTML，XSS 安全） | 观感最好；服务端零改动；历史消息一并生效 | 要改前端；需确认气泡样式能容纳标题/列表/代码块 |
| **C 服务端清洗输出** | 返回前正则剥离 `**` / `#` / `- ` | 服务端一处搞定 | ❌ **流式下做不对**：`**` 会跨 chunk，等发现要删时已显示；且浪费 token、破坏结构、易误伤 `*` 乘号与 URL。**不推荐**（仅适合存量历史消息补救） |
| **D 约定轻量标记** | 模型用固定符号（如行首 `•`），前端做 2~3 条替换 | 比 Markdown 简单、比纯文本有结构、流式安全 | 等于维护一套自定义迷你协议 |

### ⚠️ 关键约束：A 与 B 互斥

| | 方案 A | 方案 B |
| --- | --- | --- |
| 对模型的要求 | **禁止** Markdown | **允许** Markdown |
| 改动位置 | 提示词 | 前端 |

**两者不能同时做**。选哪个取决于产品定位：

> **派蒙是在「陪你聊天」，还是在「给你写攻略」？**
> - 陪伴式对话 → **A**（纯文本更像"在说话"，贴合人设）
> - 结构化攻略助手 → **B**（分点建议渲染出来更清晰）

观察到的事实：实际回答内容「结论先行 + 分档建议」**结构化程度偏高**，从信息传达看 B 更贴合；
但派蒙的人设偏"说话"，从角色感看 A 更统一。

### 倾向建议（待确认）

**先做 A，且重点是 few-shot 补分点示例，而不是那条规则。**

理由：半小时内可验证、零代码、立刻见效；且**无论最终选 A 还是 B，补齐 few-shot 都是有益的**
（示例能同时改善语气一致性与格式）。若 A 试完仍有残留且前端本就该支持 Markdown，再走 B。

### 若选 A，改动清单（待实施时才做）

  11. 输出是"派蒙在说话"，一律用纯文字对话体：
      不要用 Markdown 标记（**加粗、# 标题、- 或 * 列表符号、`代码`）。
      需要分点时，直接写「1. 」「2. 」顺着句子写，或自然地分成几段。

## TODO-02 · 思考过程残留泄漏到最终回答

| 项 | 内容 |
| --- | --- |
| **发现时间** | 2026-09-12 |
| **状态** | **待决策** |
| **优先级** | 中（观感影响比 TODO-01 更直接） |
| **影响范围** | `analysis` 档（开启思考模式）的回答 |

### 现象

回答正文里出现自我推翻式的"思考残留"：

```
…你现在带的是「追忆之注连×1（生之花）」，只有4件套效果吃不满……不对，
你写的是穹境示现之夜×4，那花是散件，套装是齐的，没问题！派蒙看错啦，抱歉抱歉。
```

用户在读一段"没想清楚就说话"的回答，比排版问题更伤体验。

### 根因

- `analysis` 档开启思考模式，模型把推理过程中的修正也写进了最终输出
- 现有 `paimon_rules` 没有约束"不要在正文暴露思考过程"

### 候选方案

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A 提示词约束**（倾向） | `paimon_rules` 加一条：直接给最终结论，不要出现自我推翻表述 | 与 TODO-01 同一版提示词改动能一起做，零成本 |
| B 关闭思考模式 | 全部走 `chat` 档 | ❌ 得不偿失——`analysis` 的推理能力正是养成分析需要的 |
| C 输出过滤 | 检测「不对」「看错啦」等模式并改写 | ❌ 靠关键词判定脆弱，且**流式下同样难做** |

### 若选 A，建议文案

```
12. 直接给最终结论，不要在回答里暴露思考过程、自我更正或前后矛盾
    （不要出现「不对」「派蒙看错啦」这类自我推翻的表述）。
    不确定就说不确定，但说出口的话要一次说清。
```

### 决策记录

```
决策人：本项目   日期：2026-09-15
选定方案：☑ A（提示词约束）  □ B  □ C  □ 其它：________
理由：《说话风格》已要求"先给结论再讲理由"，问题在于没约束"不要把心里的琢磨说出来"；与 TODO-01 同批改最省事。
```

### 实施记录（2026-09-15，方案 A，与 TODO-01 合并为 v3）

`paimon_rules` **v3** 新增【只说结论】两条：10 不要输出自我怀疑 / 自我更正 / 推翻重来的过程，说错了直接在最终答案里改对，不必解释自己改了口；11 想清楚再回答，但只输出结论和依据，不描述思考过程。

`paimon_fewshot` **v3** 补一个「用户记错时直接纠正、不自我更正」的示例（用来演示正确形态）。

实测：`analysis` 档 3 次生成（含配队 / 养成类长回答）**均未出现**「不对」「等等」「看错」「说错」等自我更正表述。

## TODO-03 · 无关问题的判定方式与采样成本

| 项 | 内容 |
| --- | --- |
| **发现时间** | 2026-09-14 |
| **状态** | **已实施**（2026-09-14：按方案 A 落地，默认 `off`；采样与首问必判见下） |
| **优先级** | 中（不影响回答，影响成本与运营可见性） |
| **影响范围** | 每次提问（判定调用本身也消耗 token，且**不计入用户配额**） |
| **背景** | 需要"筛出问无关问题的用户与其对话记录"，但服务端目前**没有任何"这个问题是否与游戏有关"的信号**——`context.goal` 只区分养成 / 配队 / 探索，闲聊与其他领域任务全落在 `general` 里，不可区分 |

需求与落库口径（已定）见 `../shared/05-AI使用边界设计（匿名·配额·内容治理）.md` §3；本条目只解决"**怎么判、判多少**"。

### 候选方案

| 方案 | 做法 | 成本 | 评价 |
| --- | --- | --- | --- |
| **A 随答判定**（倾向） | 生成结束后、`done` 之前，用一次极小分类调用（独立 system、`max_tokens ≤ 16`、输出固定枚举），结果放进 `data` / `done` 的可选字段 `offTopic` / `offTopicReason` | 每次提问 1 次小调用（≈220 tokens） | 不增加跨服务往返、实时；`done` 晚 0.3~1s（用户此时已看到全文） |
| B 独立接口 `POST /v1/classify` | 主服务在回答**之后**调一次 | 同上，多一次 HTTP | 更易灰度、可复用（intent / 敏感词）；主服务多一条链路 |
| C 规则前置 + 离线打标 | 关键词 / 长度规则标明显无关，其余靠每日离线批量跑 | 最低（离线攒批） | 当天看不到、规则误伤明显 |
| ❌ 让主模型自带标记 | 塞进生成提示词 | 0 | 流式自由文本下不可靠，且会污染回答 |

### 采样与成本（粗估，实施前实测）

单次判定 ≈ **220 tokens**（精简 system + 输出 ≤ 16）。按每天 1 万次提问：

| 采样 | 判定 tokens/日 | 说明 |
| --- | --- | --- |
| `all`（全判） | ≈ 220 万 | 最准，成本最高 |
| `sample=0.2` + 每会话首问必判 | ≈ 44 万 + 首问部分 | **倾向起点**：先跑一周看量级与误判率 |
| `off`（默认） | 0 | 不判定 → `off_topic` 全为 `NULL` |

### 落库口径（已定，不需要一起决策）

`chat_messages.off_topic BOOL NULL` + `off_topic_reason VARCHAR(32) NULL`：**`NULL` = 未判定**，`false` = 判定为有关；**必须区分**，否则抽样期的无关率会被系统性低估。

> 判定失败/未覆盖一律 `None`（主服务保持 `off_topic = NULL`）；判定消耗不计入用户配额。

> **仍待定的只剩 D4 的采样率本身**：需要先按 `sample=0.2` 跑一周拿到误判率与量级，再决定是否放开到 `all`。

### 观测记录

**2026-09-15 首日（本地 `sample=0.2` + 会话首问必判）**：3 次判定中**误判 1 次**——「帮我看看我这队还能怎么优化」被判 `other_domain`（应属 `game`）。

根因：分类器 system 只说了"是否与游戏《原神》相关"，**没说清"没点名游戏但明显是游戏语境"也算相关**，于是把「这队」当成了泛指。

修法（当日完成）：加强 `app/llm/classifier.py` 的 `_SYSTEM`——补判定原则（涉及角色 / 武器 / 圣遗物 / 词条 / 配队 / 养成 / 深渊 / 任务 / 地图 / 活动 / 剧情 / 抽卡即算相关；带自己账号、练度、阵容、展柜来问的必算相关；出现「这队」「主C」「深渊」「树脂」「抽卡」等词算相关；**只有确实看不出游戏语境时才从严判无关**），并给出 3 个反例 + 2 个正例。

**回归（4 个用例，真实模型）**：配队优化 → `game` ✅；「我的胡桃还需要提升什么？」→ `game` ✅；写 Python 排序 → `other_domain` ✅；「今天天气真好」→ `chitchat` ✅（**4/4 正确**，真无关仍能抓出）。

> 判定提示词变长后，单次判定 token 由 ≈220 升到 ≈350~400（仍**不计入用户配额**）；按 `sample=0.2` 的采样率，成本影响可忽略。
> 仍缺的是**长期误判率**：需按 `sample=0.2` 继续跑一周，再决定是否放开 `all`、以及是否与配额 / 封禁联动（D5）。

### 现象（原样记录）

问「我想听你讲一下散兵的身世」，回答里出现两处不该有的东西：

1. **自我更正残留**：`代号是「公子」……啊不对，是「散兵」啦，公子是达达利亚！`
2. **免责声明**：`派蒙记的可能不是最新版本的剧情哦……可以去游戏里的传说任务再确认一下～`

用户口径：**① 自我更正过程不该出现在回答里；② "我可能记的不是最新版本"这类话不该出现**（旅行者会默认我们说的是对的）。

### 根因（第 2 条是我们自己的指令）

| 现象 | 根因 |
| --- | --- |
| 免责声明 | **`paimon_rules` v3 第 6 条就是这么写的**：「不确定信息是否过时，主动提醒『这个可能不是最新版本哦』」——模型是**照指令执行**，不是幻觉 |
| 自我更正 | v3 第 10/11 条只泛泛禁止"自我怀疑 / 自我更正"，**没点明专有名词（人名、代号）**，也没有对应示例；`analysis` 档的推理修正因此漏进正文 |
| 更深一层 | v3 第 1～4 条把"只依据资料 + 不确定就说不确定"**笼统覆盖了所有问题**。剧情类问题本来就没有资料块，模型于是既不敢正经讲设定、又必须"说不确定"，只能长出一句免责声明 |

### 候选方案

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **A 提示词**（选定） | 把"资料优先 / 不确定"限定到**数据类**问题；剧情类正常作答；**禁止关于自己记忆的免责声明**；专有名词一次写对 | 与 v3 同款：零代码、可热更新、v4 置 0 即回滚 |
| B 输出过滤 | 正则拦「啊不对」「可能不是最新版本」 | ❌ 流式下难做（跨 chunk）、易误伤正常表达；仅适合存量补救 |
| C 关闭思考模式 | 全走 `chat` 档 | ❌ 得不偿失，`analysis` 的推理正是养成分析需要的 |

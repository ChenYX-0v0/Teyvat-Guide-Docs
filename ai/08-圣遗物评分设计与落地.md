# 08 · 圣遗物评分设计与落地

> 立档：2026-09-27　状态：**P0 + P1 已完成（评分已贯穿 翻译层 → dto → 前端展示 → AI 上下文），2026-09-27 已发版**　关联：`ai/07-待办与问题记录.md` **TODO-08**、`web/06-开发路线图.md` P2
> 起因：社区工具（提瓦特小助手 / miao-plugin）都能给圣遗物打分，用户问"能不能也做"。本文是**施工图**。

## 0. 一句话

**用 miao-plugin 的逐角色权重（MIT）算「单件分 + 套装评级 + 词条数」，服务端算好，前端展示、AI 上下文复用** —— 让派蒙能回答"这套够不够毕业 / 先强化哪件"。

## 1. 目标与产出

| 产出 | 用途 |
| --- | --- |
| 单件分 + 等级（D/C/B/A/S/SS/SSS/ACE/MAX） | 账号页角色卡、图鉴对比 |
| 套装分（5 件平均）+ 评级 + 总词条数 | 一眼判断"毕业了吗" |
| 评分摘要进 AI 上下文 | 支撑"够不够毕业 / 哪件该换 / 短板在哪" |
| 权重可维护（后台） | 版本更新不必改代码发版 |

**边界（重要）**：评分权重 **≠** 现有 `character_stat_weights`（推荐词条）——
后者只有 5 类词条（攻%/暴击/暴伤/充能/白攻）、10 分制，是给**用户/提示词的"推荐"**；
算分需要 **10 维**（含 生命/防御/精通/增伤/物伤/治疗）、0~100 刻度。**两者语义不同，必须分表**。

## 5. 算分设计

### 5.1 换算基础（**可自证**，不依赖别人的表）

```
词条系数 k[stat] = 6.6 ÷ 该词条单次强化均值
  暴击 6.6/3.305 = 2.00 | 暴伤 1.00 | 攻%·生% 1.332 | 防% 1.065 | 充能 1.199 | 精通 0.333
白值（固定数值，社区通用）：小生命 ×0.017 | 小攻击 ×0.2 | 小防御 ×0.22
```
> 这段是"能写进单测的恒等式"（多源交叉验证过：米游社《圣遗物有效分计算》给出 `词条分数 = 6.6 × 词条数 × 收益权重`）。

### 5.2 口径 A：复刻 miao（结果可与它对照）

```
raw     = Σ( k[stat] × weight/100 × 副词条数值 ) + k[stat] × weight/100 × 主词条数值 / 4
单件分   = raw × (1 + fixPct) / 2 ÷ posMax[slot] × 66            -- 满分 66
  fixPct = clamp(主词条权重 / 该部位最高权重)；且 atk/hp/def 权重 ≥ 75 → 1（视为完全契合）
套装评级 = getMarkClass( Σ单件分 ÷ 5 )
  阈值：D<7 | C<14 | B<21 | A<28 | S<35 | SS<42 | SSS<49 | ACE<56 | MAX<70
```
⚠️ `posMax[slot]`（各部位理论上限）**尚未取到** —— 不在 `data.json` 里（那个文件实际是**套装表**），
来源应为 `models/artis/ArtisMarkCfg.js`（`posMaxMark` / `fixWeight` 的构造处）⇒ **P0 第一步**。

### 5.3 口径 B：自算归一化（**建议作主口径**）

```
单件分 = Σ(可用词条 × 角色权重) ÷ Σ(该部位理论最大可用词条 × 角色权重) × 100
```
好处：不依赖第三方常数 ✓、天然按角色适配 ✓、含义直观（"这件达到该角色该部位上限的百分之多少"）✓、改权重不需要重算基准 ✓。
代价：与 miao/小助手的数字**不可直接对照**（需对照时并列显示 A 口径的"参考分"）。

### 5.4 口径 C：双暴分（轻量对照，可选）

`暴击×2 + 暴伤`（+5 件合计）；社区阈值：180 及格 / 210 小毕业 / 262 大毕业。一句话能解释，适合作为辅助展示。

### 5.5 词条数摘要

按社区同款基准（暴击 3.3 / 暴伤 6.6 / 攻生 4.95 / 防 6.2 / 充能 5.5 / 精通 19.8）分别统计
`双暴 / 攻击 / 生命 / 防御 / 精通 / 充能` 词条数 ⇒ **用户能直接与小助手对照**（口径一致时数字才可比）。

**踩坑（值得进 `web/14` 手册）**

1. **PS 5.1 读无 BOM 的 UTF-8 `.ps1` 会按 ANSI 解码** ⇒ 中文全乱、语法报错（同 `web/14` 铁律 13 的 CRLF 一类坑）⇒ 生成器必须存 **UTF-8 with BOM** ✓；
2. **种子键名必须与 `ImportPayload` 的 json tag 完全一致**（`relicWeights` / `relicWeightRules`）✗ —— 不一致时接口**静默导入 0 条**、不报错。已加端到端断言兜住；
3. **`dto` 依赖 `asset`**（`CharacterCard.StatWeights`）⇒ 算分函数**不能** import `dto`（循环）⇒ 入参用自带的 `RelicScoreInput`；dto 侧字符串用 `ParseRelicStatValue` 反解；
4. **`gofmt -l ./...` 目前不是"零命中"，根因是 CRLF** ✗：仓库里 69 个 Go 文件被标记，抽样确认全是 **CRLF**（`handler/asset.go` CRLF=85/LF=0、`config/config.go` CRLF=194、`main.go` CRLF=56），而新建/改写过的文件是 **LF**（`service/asset/service.go` LF=438）⇒ 与 `web/14` 铁律 13（远端 `.sh` 的 CRLF 事故）**同一类问题**。
   ⇒ 结论：`gofmt -l ./...` 在"统一换行符"之前**不能当门禁**；两条路 —— ① 加 `.gitattributes`（`*.go text eol=lf`）并做一次全仓 `gofmt -w`；② 门禁只检查"本次改动的文件"。**建议 ①**（根治，且能顺带防住 `.sh`/`nginx.conf` 那类坑）；
5. 主词条/副词条数值在 dto 层已被格式化成字符串（`"生命值 +4780"`、`"19.4%"`）⇒ 有信息损失风险，**接 dto 时应尽量在 `translate.go` 传原始 float**（P1）。

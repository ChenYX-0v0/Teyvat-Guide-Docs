# 12 · 时效性内容与期次自动化设计（卡池 / 深渊 / 剧诗 / 危战 / 版本前瞻）

> **状态**：⬜ **设计态**（2026-10-18 立）—— 本文只定**口径、边界、表结构与排期**，不含已落地代码 ✓

## 0. 与 `11` 的边界（先划清，否则会做重）

`11` 的核心是**"发现答错 → 补知识"**，服务的是**知识缺口型**问题；本文服务的是**"每两周就变一次"的时效事实**。两者共用"外部数据 → 落库 → 注入"的形状，但**状态机、审核方式、验证方式完全不同**：

| | `11` 定向采集 | **本文 期次内容** |
| --- | --- | --- |
| 数据源 | 搜索 API（`/v1/tools/search`） | **官方公告 / 客户端 Excel 表** |
| 有结构化时间吗 | ❌ 常常没有（`date` 可能 `null`） | ✅ **有**（`start_time` / `end_time` / 期次表） |
| 内容会不会过期 | ⚠️ 会，但没有明确边界 | ✅ **每期固定失效**（这是安全性的来源） |
| 状态机 | `quarantined → pending(人) → effective` | **`draft → active → expired`（时间驱动）** |
| 必须人审吗 | ✅ 是（`11 §4.1`） | ❌ **否**（见 §5，理由见 §5.1） |
| 验证方式 | 逐字校验 + 评测集 | **冻结 fixture**（`11 §8` 的评测集**不许**含具体某期答案 ✗） |

⚠️ **对 `11 §3` 的修正**：那里把"这期深渊打什么怪"列为搜索 API 的第一价值点 ✗ —— 这类内容**有权威结构化源**，用 600~800 字的搜索摘要去替代精确字段是净亏（精度低、每条要人审、还引入"过期数据"）。搜索 API 在这四类里只保留**"某期深渊的社区配队口径"这类主观结论**，且仍走 `11` 的人审通道 ✓。

## 2. 期次模型（全篇的地基）

### 2.1 表结构（主服务库，GORM `AutoMigrate`；本仓无 SQL 迁移文件 ✓）

```text
content_periods
  id            bigint PK
  kind          varchar   -- abyss | theater | stygian | wish_char | wish_weapon | version_preview
  period_key    varchar   -- 深渊期号 / 剧诗幕数 / 卡池 ann_id / 版本号
  game_version  varchar   -- 5.2 / unknown（unknown 只允许出现在 draft）
  start_at      datetime  -- UTC+8 语义，落库按 TIMESTAMP 存
  end_at        datetime
  payload       json      -- UP 名单 / 怪物阵容 / 祝福 / 三星条件 / 前瞻摘要
  source        varchar   -- mihoyo_announce | client_excel | manual
  source_url    varchar
  ann_id        varchar
  fetched_at    datetime
  next_check_at datetime  -- 见 §4.1（调度就靠它，不需要 cron 表达式）
  status        varchar   -- draft | shadow | active | expired | superseded | held | rolled_back
  parse_rule_ver varchar  -- 解析器版本（改规则时必须能回溯是哪版抽的）
  raw_hash      char(64)  -- 源数据 hash：变了 ⇒ 官方改了公告 ⇒ 告警
  UNIQUE(kind, period_key)
  INDEX(next_check_at), INDEX(kind, status, start_at)
```

### 2.2 解析器（唯一读入口）

```text
ResolveActive(kind, now):
    取 start_at <= now < end_at AND status = 'active' 的**至多一条**
    命中 ⇒ 返回该期（含 fetched_at / source / game_version）
    无命中 ⇒ 返回 nil
```

三条口径（**直接照 `../web/06` 已定的"宁空不旧"**）：

1. **绝不回退上一期** ✗ —— 宁可返回空、前端显示「本期数据待更新」，也不显示上期（说错"这期是谁"比说"没数据"更伤）；
2. **不猜、不模糊匹配** ✗ —— 期次是闭集，靠时间字段算，不靠模型推；
3. **时区固定 Asia/Shanghai** ✓ —— 公告字段就是 UTC+8 字符串，比较一律在同一时区做（`end_at` 边界差 8 小时就是错一期）。

### 2.3 为什么不用 `candidate_facts`

`11 §7.1` 的 5 态机是**人签字驱动**（`quarantined → pending → effective`）；期次是**时间驱动**（到点自动上下架）。塞进去会变成"每期卡池都要人点一次通过"（每年约 50 次无意义签字 ✗），且过期要靠人手动 `disabled` ✗。**两种语义必须分表** ✓。

## 3. 周期识别：靠时间字段，不靠模型

| 优先 | 时间源 | 能给什么 | 可靠性 |
| --- | --- | --- | --- |
| ① | **官方公告** `getAnnList` 的 `start_time` / `end_time` | 卡池起止（精确到分，实测 `2026-09-21 12:00:00 ~ 2026-10-13 17:59:00`） | ✅ 高 |
| ② | **客户端 Excel** `TowerScheduleExcelConfigData`（期次枢纽）+ `TowerLevelExcelConfigData`（怪物） | 深渊每期起止 + 怪物 + 层数 | ✅ 高（离线导入） |
| ③ | **版本日历推算** | 大版本约 6 周；`上期 end_at + 周期` | 🟡 只用于**提前加密轮询**，**不对外展示** |

⚠️ **不要用**：`tag_start_time` / `tag_end_time`（实测是占位值 `2000-01-02` / `2030-01-02` ✗）。

⚠️ **模型不参与"现在是哪一期"的判定** ✗ —— 违反 `11 §4.3`（不可复现、会漂移），且是拿不确定的东西替代精确到秒的字段。模型的出场位置见 §5.4 与 §6。

**关键收益**：只要拿到一次 `end_at`，**下一期"该去看一眼"的时刻就是确定的**（`end_at + 5min`）⇒ 调度器可以自续，永不需要人维护日历 ✓。

## 4. 自动拉取：四层刷新（不需要 cron 框架）

### 4.1 层 1 · `next_check_at` 精确触发（主路径）

| 写入时机 | `next_check_at` | 为什么 |
| --- | --- | --- |
| 本期入库时 | `end_at - 10min` | 官方偶尔**提前上架** |
| 本期 `end_at + 5min` 再补一次 | `end_at + 5min` | 抢新一期（切换点） |
| 拿到新一期后 | 新行的 `end_at - 10min` | **自续**，形成链条 |

### 4.2 层 2 · 兜底轮询（防调度器挂 / 官方改期）

| 状态 | 频率 |
| --- | --- |
| 有 `active` 期次 | **每 6 小时**一次 |
| 无 `active`（已过期且没拉到新的） | **每 30 分钟**一次，直到拿到 |
| 连续失败 | 指数退避 30min → 1h → 3h → 6h 封顶 + **每日汇总告警**（对齐 `11 §12-7`） |

> 不用 15~30 分钟轮询（`../web/06` 那条纪律针对的是"别秒级轮询"，这类内容 6 小时足够 ✓）。

### 4.3 层 3 · 请求侧 lazy refresh（最关键的一层）

解决"定时器没跑成 / 进程刚重启"：**没人问就不干活，有人问发现空或陈旧就后台补一次，但绝不阻塞回答**。

```text
收到提问 → 命中 endgame / wish / version 意图（复用 detectGoal）
  p = ResolveActive(kind, now)
  if p == nil || p.fetched_at < now - 24h:
      asyncRefresh(kind)     // singleflight 去重 + 300ms 预算
  → 注入 p；p 为 nil 则注入「本期数据待更新」（宁空不旧）
```

### 4.4 层 4 · miss 驱动按需回源

统计"命中意图但无期次数据"的次数：**同一 `kind` 累计 ≥3 次 / 小时 ⇒ 立刻插队触发一次同步** ✓。这样官方提前开池、我们表里还空时，几分钟内自动补上，不用等兜底轮询。

### 4.5 落地形态（复用现成模式）

`service/usage_stats.go` 的 `aggLoop` 已经是「**进程内循环 + 启动先补一次 + 幂等重算**」（每小时重建 `usage_daily`）✓ ⇒ **同款复制一个 `periodSyncLoop`（5 分钟 tick，查 `next_check_at <= now`）**，不引入 cron 框架 ✓。

| 纪律 | 做法 |
| --- | --- |
| 幂等 | `UNIQUE(kind, period_key)` + upsert；`ann_id` 重复不写 |
| 抓取不进 AI 服务 | 全在 Go 侧后台循环 / 离线脚本（模型侧零工具，`09 §1` 红线 ✓） |
| 多实例 | 现在单实例无需加锁；扩多实例必须加 MySQL `GET_LOCK` 或行锁 ✗ 否则重复抓 + 打架写库 ⇒ 记 TODO |
| 失败不静默 | ⚠️ **与 `11 §10.4` 相反**：搜索失败可静默跳过，**期次是功能数据**，解析失败 / 连拉空必须告警 ✗ |

## 5. 去掉人工审核（本文最核心的一节）

### 5.1 为什么这里可以合法例外（`11 §4.1` 的补丁）

`11 §4.1` 定的是「**永远是 候选 → 人审 → 生效**」，理由是"搜索来的内容直接进 system 等于给资料外编造开后门"。本文不违反该约束，因为**期次数据的安全机制不是"审对"，而是"错了会自己消失"**：

| 错误类型 | 后果 | 会自愈吗 | 能去人审吗 |
| --- | --- | --- | --- |
| 说错"这期 UP 是谁" | 严重度中；用户一眼能看出 | ✅ 下期自动覆盖 | ✅ **可以** |
| 说错怪物 / 祝福 | 中；同样次期失效 | ✅ | ✅ **可以** |
| 把上期当本期 | 高（会连带编错抽取建议） | ✅ 靠"过期即下线"天然挡住 | ✅（**前提是 §2.2 不回退**） |
| 攻略卡 / 机制卡写错 | 极高；**一直错下去** | ❌ | ❌ **不可以**（仍走 `11` 人审） |

⇒ **准入四条（必须同时满足才能去人审）**：

1. **有权威结构化源**（official 公告 / 客户端表 / 后台人工录入）；
2. **有唯一幂等键**（`ann_id` / `period_key`）；
3. **能机器验证**（见 §5.2 四闸，且失败必须能"丢弃"而不是"猜"）；
4. **有时效边界**（`end_at` 明确，过期自动下线）。

四条缺一 ⇒ **回到人审** ✓（例：版本前瞻的"新角色强度结论"缺第 3 条 ⇒ 不主张确定性，只标"前瞻口径"）。

### 5.2 四道机器闸门（替代人签字）

| 闸 | 防的是人审原本在防的什么 | 规则（不通过 ⇒ 丢弃，进 `held`） |
| --- | --- | --- |
| **① Schema 闸** | 字段错位 / 类型错 | 字段白名单；`start_at < end_at`；时间落在 `[now-7d, now+180d]`；UP 名单 1~4 个；`kind` 合法；`game_version` 匹配 `^\d+\.\d+$` 或 `unknown`（仅 draft 允许） |
| **② 闭集闸**（最关键） | 抽错实体 | 抽出的角色 / 武器名**必须解析到 `characters` / `weapons` 的 id**；怪物**必须解析到怪物 id**。解析不到 ⇒ **整条丢弃** ✗，**不做模糊匹配、不留近似值** |
| **③ 交叉闸** | 单一来源抽错 | 公告主接口 vs `hk4e-api-static` 镜像（互备）或 公告 vs 客户端 Excel；一致 ⇒ 生效；不一致 ⇒ `held`，不对外 |
| **④ 回滚闸** | 事后才发现错 | 写入前留上一版快照；生效后 24h 内触发不变式告警（期次重叠 / 解析失败率突增 / `raw_hash` 变了）⇒ **自动回滚**到上一版 + 告警 |

**外加一条单调性**：同一 `kind` 期次**不得重叠**、`period_key` **不得倒退**、`game_version` **不得回退** ⇒ 能挡住绝大多数"抽到了旧公告"类错误 ✓。

> 一句话：**人审在防"不确定"，机器闸门用"不确定就丢弃"来对付它**。丢弃代价远低于审错代价 —— 期次缺这一期还有下一期 ✓。

### 5.3 状态机（`pending` 从必经变成异常出口）

```text
draft ──四闸全过──► active ──到 end_at──► expired
  │                   │
  │                   └──告警 / 不变式违反──► rolled_back（自动回滚 + 告警）
  └──任一闸失败──► held ──自动重试 / 规则修复──► active
                     └──连续 2 次失败──► 告警（人只看 held，**不阻塞**其他 kind）

（shadow = 四闸全过但只落库、不注入；见 §8）
```

对比 `11 §7.1`：**`quarantined` / `pending` / `effective` / `disabled` 这套在这里不用**；后台界面从「待审队列 + 通过按钮」改成「**只读列表 + 一键回滚**」（**不需要"通过"操作** ✓）。

### 5.4 AI 参与抽取时如何也不需要人审：把生成变成**闭集选择**

这是去人审的前提条件，否则模型一定会编：

| ❌ 不要 | ✅ 要 |
| --- | --- |
| 让模型"生成 UP 名单"（自由文本 ⇒ 必须人审） | 让模型**从 `characters` 表的 124 个名字里选出标题中出现的那些**；从 `annList` 条目里选 `ann_id` |
| 让模型读公告正文图片 | 正文是 `<img>` 就**直接跳过**（`../web/06` 已踩过） |
| 让模型输出 `{ "new_characters": ["某新角色"] }` | 输出 `{ "new_characters": [id...] }`（只能是表内 id） |

⇒ 输出是**枚举下标 / id**，天然合法；错误空间只剩"选错了"，而选错会被 ②③ 闸抓到 ✓。

## 6. 注入与回答口径

现有链路是「实时拼 + 动态区 **1500 token** 预算」（`../web/13` / `ai_context.go`），`context.summary` 是现成的自由文本通道（`../shared/03 §6.7`）。

| 规则 | 内容 |
| --- | --- |
| **按意图注入，不常驻** | 复用 `detectGoal(question)`，只在命中 `endgame / wish / version` 时拼 **≤200 token** 的期次文本；常驻会把展柜角色的预算挤掉 ✗ |
| **必须带时间锚点** ✓ | 「今天是 2026-10-18；本期深渊 10-16~10-31（剩 13 天）；本期卡池 10-14~11-04」⇒ 模型自然说对"这期 / 下期"，**比任何"AI 判断周期"都有效且零风险** |
| **必须带来源与口径** | `source` / `fetched_at` / `game_version` 一并注入；前瞻内容一律标「**前瞻口径，以官方公告为准**」 |
| **禁说清单**（沿用 `../web/06`） | ❌ 保底计数 / 水位 / 原石 / 纠缠之缘 / 已抽次数 —— 公开数据没有，也不能索要账号；抽取建议**只能**建立在"卡池 UP × 用户展柜缺口"上 |
| **宁空不旧** | `ResolveActive` 返回 nil ⇒ 注入「本期数据待更新」，**不许**注入上期数据 ✗ |

⚠️ 前端新增卡池卡 / 深渊卡会产生曝光点击 ⇒ 按 `../shared/07` 同步事件字典与主服务 `usageEventProps` 白名单（跨层契约，`../web/06` P3 门禁第 ④ 条）。

## 7. 四类内容的接入细节

### 7.1 祈愿（本期）

| 项 | 做法 |
| --- | --- |
| 源 | `getAnnList`（`hk4e_cn` / `announcement`），镜像 `hk4e-api-static.mihoyo.com` 互备 |
| 解析 | **只用标题 + 时间字段**：`「…」` 正则取 UP 名 → 闭集映射到 id；`start_time` / `end_time` 可直接用；**正文不解析**（常是整张图 ✗） |
| 落库 | `kind = wish_char / wish_weapon`，`period_key = ann_id`，`payload = { items: [{id, name, type, is_up}] }` |
| 刷新 | `end_at - 10min` + `end_at + 5min` + 6 小时兜底 |
| 兜底 | 官方改格式 / 抓不到 ⇒ 后台**手工录入**（`source = manual`，同样走四闸） |
| 纪律 | 只读公开公告；**不碰需 authkey 的祈愿历史** ✗；不整段搬运原文 ✓ |

### 7.2 祈愿（下期）

- 唯一公开来源是**前瞻公告**，且多为图片 / 直播内容 ⇒ **机器不可靠**；
- 做法：单列 `kind = version_preview`，抽取结果**只标"前瞻口径"**，**不作为确定事实**，也不进抽取建议的硬依据；
- 抽取仍走 §5.4 闭集（只能从 `characters` 表里选），选不出就留空 ✓。

### 7.3 深渊（每期）

| 步 | 做法 |
| --- | --- |
| 期次 | `TowerScheduleExcelConfigData`（把"本期"关联起来的枢纽） |
| 内容 | `TowerLevelExcelConfigData`（怪物）+ 祝福 + 三星条件 |
| 导入 | 离线脚本（照 `cmd/assetimport` 的形状）→ 写 `content_periods`，`source = client_excel` |
| 更新的关键 | 客户端表**随版本更新**（约 6 周一次）⇒ 导入器做成"读一个版本的 Excel 目录 ⇒ 补齐未来 N 期"，天然满足"每期会变"（`07` TODO-07 的原始顾虑 ✓） |
| 工作量 | 半天（`07` 已估过 ✓） |

### 7.4 剧诗 / 危战（每期）

- 客户端表名**仍未确认**（8 个候选全 404 ✗）⇒ 先做**侦察任务**（换社区数据仓 / 客户端解包思路），不阻塞其他三类；
- 过渡期：只做"玩家进度 + **版本周期推算**"的期次边界，界面标「口径为版本周期推算」，**不进确定结论** ✓。

### 7.5 版本前瞻

- 源：公告分类（版本更新 / 活动公告 / 前瞻直播）；
- 落库 `kind = version_preview`，`payload = { version, start_at, end_at, new_characters[], new_banners[], highlights }`；
- 模型抽取 ⇒ 闭集校验 ⇒ **自动生效但只展示为"前瞻口径"**（不主张确定性 ⇒ 错误代价降到可接受）✓；
- 顺带解决 `../web/06` 记的"下期卡池没有数据源" → 从 ❌ 变成 🟡（低置信、带来源）。

## 8. 上线方式与观测（去人审 ≠ 不验证）

### 8.1 shadow 模式（一次性验证，不是长期人审）

1. 自动拉、自动过闸、自动落库，但 `status = shadow`（**不注入、不展示**）；
2. 每期人工抽查 5~10 个字段（一次约 10 分钟；一个月 2~3 次）；
3. **机器判定与抽查一致率 ≥ 99%** ⇒ 切 `active`；
4. 切完后人只在收到告警时出现 ✓。

> 也可以跳过 shadow 直接上（靠 §5.2 ④ 回滚兜底），但 shadow 能给解析器版本一个**客观准入线**，以后改规则用同一口径复验 ✓。

### 8.2 必须保留的三个异常出口（不能全自动）

| 场景 | 处理 |
| --- | --- |
| 某 `kind` **首次上线** / **解析规则版本变更** | 自动降级 `shadow`，**跑满一期**再切 `active`（不需要人，但要跑满） |
| 官方**改版式**（`start_time` 消失 / 标题正则命中率骤降 / `raw_hash` 变了） | 自动 `held` + 告警，**不继续猜**；前端照常显示"本期数据待更新" |
| 前瞻类（图片 / 直播） | 不主张确定性 ⇒ 展示但标口径，**无所谓对错**，无需审核 |

### 8.3 观测指标（这几项比审核有效）

| 指标 | 阈值 |
| --- | --- |
| 解析失败率 | > 5% 告警 |
| 闭集映射失败率（名字解析不到 id） | > 10% 告警 |
| `held` 条目数 | > 0 且超 6h 告警 |
| **线上「本期数据待更新」文案命中次数** | 最真实的数据健康度指标 ✓（用户看到的空窗比库里 `status` 更准） |
| 期次空窗时长（`expired` 且无新 `active`） | > 12h 告警 |

## 11. 明确不做

| ❌ 不做 | 原因 |
| --- | --- |
| 让模型判断"现在是哪一期" | 不可复现、会漂移，且是拿不确定替代精确字段（`11 §4.3`） |
| 让模型在请求链路里抓取 | 违反 `09 §1`（模型侧零工具）✗ |
| 期次数据进 `11 §8` 的评测集 | 每 2~3 周一变 ⇒ 评测不可复现（`11 §15` 要求同版本两次结论一致） |
| 无命中时回退上一期 | 说错"这期是谁"比说"没数据"更伤（`../web/06` 已定） |
| 用搜索 API 采卡池 / 深渊 | 有权威结构化源，摘要替代精确字段是净亏 |
| 抽取时做模糊匹配 / 留近似值 | 错得无声无息；**丢弃优于猜** ✓ |
| 期次数据失败静默 | 与搜索不同，这是功能数据，必须告警 |
| 解析公告正文图片（多模态 OCR） | 不稳定且成本高；正文是图就跳过 ✓ |

## 12. 验收标准

**S1 期次底座**
- [ ] `ResolveActive` 在"过期且无新一期"时返回 nil，**不回退上一期**
- [ ] `next_check_at` 能自续：连续模拟 3 期切换，无需人工干预
- [ ] 四闸各构造 1 条反例（字段越界 / 名字不在闭集 / 两源冲突 / 期次重叠），全部进 `held` 且**不对外可见**

**S2 公告导入**
- [ ] 同一 `ann_id` 重复抓取**不产生新行**（幂等）
- [ ] 主接口挂掉时自动切镜像，仍在 1 个周期内拿到本期
- [ ] 官方改版式（人为删掉 `start_time`）⇒ `held` + 告警，前端显示"待更新"

- [ ] 未命中意图时**完全无期次 token**（预算不被动用）
- [ ] 命中时注入文本 ≤200 token，且含时间锚点、来源、`game_version`

**S4/S6 内容**
- [ ] 深渊每期怪物 / 祝福能覆盖 ≥2 个连续期次
- [ ] 前瞻抽取的角色名 **100% 命中 `characters` 表**（否则为空）

**S7 可回滚**
- [ ] 一键回滚后 ≤1 分钟线上恢复上一版
- [ ] 回滚动作有记录（谁 / 何时 / 从哪版到哪版）

## 2. 背景：前 AI 时代的推荐机制（速查）

> ⚠️ 先说清一个前提：**"没有 AI 的年代"并不存在** —— 协同过滤与矩阵分解**本身就是机器学习** ✓，只是当年叫"数据挖掘"✗ 不叫 AI ✓。
> 真正的分野是**有没有深度学习 / 大模型**。

### 2.1 四个时代

| 时期 | 主力方法 | 代表 |
| --- | --- | --- |
| 1995–2003 | 人肉运营 ＋ 规则 ＋ 协同过滤萌芽 | Amazon 1998「买了还买」；GroupLens（1994） |
| 2003–2012 | **Item-based 协同过滤 ＋ 矩阵分解** | Amazon 2003 论文；Netflix Prize（2006–2009） |
| 2010–2016 | **特征工程 ＋ CTR 预估** | LR、GBDT+LR（2014）、FM / FFM |
| 2016+ | 深度学习 | Wide&Deep、DeepFM、DIN、双塔 |

### 2.2 三块基石

**① 编辑运营与规则**（最原始也最耐用）
- 人肉榜单（热销 / 新品 / 编辑推荐）、硬编码规则（`买了 A → 推 B`）、时间衰减热度（Hacker News `score = (votes-1)/(t+2)^1.8`）
- 优点：冷启动能跑 ✓、完全可控 ✓、可解释 ✓
- ⇒ 至今仍是任何推荐系统的**兜底层** ✓

**② 关联规则挖掘**（零售业购物篮分析，本项目直接可用）
- 算法：Apriori、FP-Growth
- 三个指标（**核心，见 §4.4 算例**）：

```
支持度  supp(A→B) = P(A ∩ B)   = 同队次数 / 队伍总数
置信度  conf(A→B) = P(B | A)   = 同队次数 / A 出现的队伍数
提升度  lift(A→B) = conf(A→B) / P(B) = (同队次数 × 队伍总数) / (A 队数 × B 队数)
```

- ⭐ `lift > 1` 才是**真正的协同** ✓；`lift ≈ 1` 只是"B 本来就人人都用" ✗
- 注：著名的"啤酒与尿布"是营销故事，学界基本认定**是编的**（真实沃尔玛数据未复现）✗，但关联规则本身是真在跑的 ✓

**③ 协同过滤（CF）**（前 AI 时代的绝对主力）

| 类型 | 做法 | 优劣 |
| --- | --- | --- |
| User-CF | 找"和你相似的人"，推他们喜欢而你没见过的 | 用户多、变化快 ⇒ 在线计算贵 ✗ |
| **Item-CF** | 找"和这个商品相似的商品" | ✅ **Amazon 的翻身仗**：item 少于 user、相似度可**离线预计算**、线上只查表、天然可解释成"买过这个的人也买了" |

```
余弦相似度  sim(i,j) = Σ_u r_ui·r_uj / ( √Σ_u r_ui² · √Σ_u r_uj² )
```

> 关键工程思想（至今没变）：**把重的计算搬到离线，线上只做查表和排序** ✓。

CF 的四大绝症（至今没根治）：**冷启动**（新用户 / 新品无数据）、**数据稀疏**、**长尾淹没**、**羊群效应**。

### 2.3 之后怎么演进

1. **矩阵分解（2006–2012）**：把用户-物品矩阵拆成隐向量 ⇒ 本质是降维 ＋ 填缺失；FunkSVD 在 Netflix Prize 一战成名
2. **特征工程 ＋ LR（2010 前后）**：**思路变了** —— 从"猜你喜欢什么"变成"**预估点击率再排序**" ✓
3. **GBDT+LR / FM / FFM**：树做自动特征交叉；FM 用隐向量内积自动学二阶交叉，专治稀疏
4. **多路召回 ＋ 粗排 ＋ 精排 ＋ 重排**：工业界标准漏斗 —— 召回保多样性、精排保准确率、重排处理打散 / 去重 / 业务规则

### 2.4 那些"看起来像 AI 其实是规则"的东西

| 看着像 AI | 实际是 |
| --- | --- |
| "看过还看过" | item-CF 或**共现统计** |
| "猜你喜欢"（早期） | 类目热销榜 |
| "为你推荐" | 热门榜 ＋ 几条个性化规则的混合 |

## 3. 映射：电商 → 配队

**配队在数学上的同构物是电商的「组合 / 搭配推荐」（bundle recommendation）** ✓ —— 与"整机搭配""穿搭推荐""套餐推荐"同一个问题 ✓。

| 电商概念 | 配队对应 | 本项目已有？ |
| --- | --- | --- |
| 购物篮 = 一次订单的商品集合 | **一支真实队伍 = 一个 basket** | ✅ `character_teams` 每行就是 |
| 支持度 `P(A ∩ B)` | 两角色**同队**的比例 | ✅ 可由现有表聚合 |
| 置信度 `P(B \| A)` | 带 A 的队里有多少带 B | ✅ 同上 |
| **提升度 lift** | ⭐ 筛掉"人人都带"的角色，找出**真正的协同** | ⬜ 待实现 |
| Item-CF 相似度 | 角色-角色相似度（共同队友越多越像） | ⬜ 待实现 |
| 类目内推荐 | **先按体系 / 槽位分桶**再桶内推荐 | ⬜ 待实现 |
| Content-based（冷启动） | 按元素 / 武器 / 定位画像的相似度 | ⬜ 待实现（可选） |
| 召回 → 排序漏斗 | 含 X 召回 → 约束筛选 → lift 排序 | 半成品（只有召回 ＋ id 排序） |

**⚠️ 与电商最大的不同**：电商推错一件是"没兴趣"；配队**有硬功能约束** ⇒ 纯 CF 会推出「四个主C」这种烂队 ✗。
解法就是电商"整机搭配"的做法：**先定骨架、再填件** ✓（见 §4.3）。

## 4. 设计

### 4.1 三层结构

```
① 召回（Recall）      含角色 X 的队伍（现有 SQL ✓）
                     ＋ 与 X 高 lift 的角色所在的队（共现扩展 ✓）
        ↓
② 筛选（约束 Filter） 按槽位 / 体系分桶 ⇒ 剔除骨架不成立的组合
        ↓
③ 排序（Rank）        队伍级得分 = lift 加权 ＋ 时效 ＋ confidence
        ↓
                     取前 3 支 → 渲染进「推荐配队」段（需发版 ✗）
```

### 4.2 共现矩阵从哪来（⚠️ 零额外采集成本）

**这是本设计最划算的一点** ✓：`character_teams` 一旦落库，**每支队伍就是一个 basket** ⇒ 共现矩阵只是它的一张**聚合视图** ✓，**不需要任何新爬虫** ✓。

```
co(a,b) = count( 队伍 t | a ∈ t.members ∧ b ∈ t.members )
cnt(a)  = count( 队伍 t | a ∈ t.members )
N       = 队伍总数
```

> 聚合视图的物化方式（离线落表 vs 在线聚合）见 §7 待决策 1。

### 4.3 约束分桶（解决"四个主C"）

用 `members[].role` 字段（`07` TODO-29 的数据形状里**已经有** ✓，值如「站场输出」✓）：

| 约束 | 判据 | 对应电商做法 |
| --- | --- | --- |
| 骨架完整 | 至少 **1 名输出** ＋ 至少 **1 名生存**（治疗 / 护盾） | 整机搭配"先定主板再填件" |
| 体系一致 | 按元素反应体系分桶（蒸发 / 永冻 / 绽放 / 超导 …），桶内推荐 | **类目内推荐** |

⚠️ **实测 `role` 很脏 ✗**（2026-10-16 ✓）：值有「减抗」「后台/护盾/增益」✓，也有「1号后台水」「6命200精通」「祭礼弓/连E」✗；且清洗阶段**已丢掉**「增益生存副C」这类**位置词** ✗（它被误当人名 ✓）⇒ **别指望它直接判骨架** ✗ ⇒ 更倾向 ② 人手标签 ✓。
⚠️ 判据来源需拍板：是用 `role` 字段自动判定，还是**人手给角色打体系标签**（`role` 由识图抽取得到，可能不稳定 ✗）—— 见 §7 待决策 3。

### 4.4 指标与算例（⭐ 这段是设计里最有说服力的部分）

**队伍级得分**（拟）：

```
score(t | X) = w₁ · lift均值( X → t.members \ {X} )   // 协同强度
             + w₂ · recency(t)                        // 时效（现有 id 降序的连续化 ✓）
             + w₃ · confidence(t)                     // 多篇一致 → 高
```

**算例（数字为示意，非实测）**：设 N = 1000 支入库队伍。

| 候选队友 B | `cnt(B)` | `co(那维莱特, B)` | `conf` | **`lift`** | 解读 |
| --- | --- | --- | --- | --- | --- |
| 芙宁娜 | 200 | 108 | 0.90 | **4.5** | ⭐ 强协同 —— **那维莱特的特化队友** ✓ |
| 钟离 | 400 | 72 | 0.60 | **1.5** | ⚠️ 弱协同 —— 钟离**人人都带**（`P(B)` 本来就高 ✓），`conf` 看着高其实是**基数陷阱** ✗ |

> ⇒ 这就是**只看置信度会踩的坑** ✓：钟离的 `conf`（0.60）也很高，但它不是"因为那维莱特才出现"✗。
> **`lift` 能把它压下去** ✓ —— 这是本层相对现有 id 降序排序的**核心增量** ✓。

### 4.5 与 LLM 的分工（口径与 `07` TODO-29 的实测一致 ✓）

`07` TODO-29 已实测**推理路线被否**的三条理由，正好界定分工边界：

| 能力 | 统计层 | LLM |
| --- | --- | --- |
| 哪支是**当前主流** | ✅ 从真实队伍统计得来 | ✗ 它是推理，不是社区事实（`07` 实测被否 ✓） |
| **强度排序** | ✅ lift / 使用率 | ✗ 自评几乎全是"中"，没有伤害系数（`07` 实测 ✗） |
| 输出**体量** | ✅ 查表，毫秒级 | ✗ 4 支队 = 1.8 万 output token / 116 秒（`07` 实测 ✗） |
| **解释"为什么这么配"** | ✗ 只能说"87% 的队带它" | ✅ 这是 LLM 的强项 ✓ |

⇒ **统计层给"事实"，LLM 给"解释"** ✓ —— 与电商"召回-排序"漏斗同构 ✓，只是排序层换成了大模型 ✓。

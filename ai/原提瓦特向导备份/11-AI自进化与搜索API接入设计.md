## 1. 现状：进化需要什么 vs 我们有什么

| 进化需要的零件 | 现状 | 事实依据 |
| --- | --- | --- |
| **可回滚的"基因"**（提示词 / 数据版本化） | ✅ **很强** | `ai_prompts` 表多版本共存、启用即生效、置 0 即回滚（`shared/03 §5`）；`paimon_rules` 已迭代到 **v21** |

## 2. 先拆一个误区：搜索 API ≠ 自进化

"自进化"在工程上的真实形态不是"模型改写自己"，而是一条**闭环流水线**：

```
发现答错  →  定位原因  →  生成候选补丁  →  回归验证  →  灰度/发布  →  出问题回滚
（P1 缺）    （靠人）      （靠人）        （P2 半自动） （已有 ✓）    （已有 ✓）
```

搜索 API 只可能出现在**"生成候选补丁"那一步**，而且**只对"知识缺口型"的错有用**。把错误按类型拆开看：

| 错误类型 | 本项目真实案例 | 搜索 API 有用吗 |
| --- | --- | --- |
| **知识缺口（长期）**：库里没收录 | 攻略卡覆盖不到的新角色 / 冷门玩法 / 外服角色 | ✅ **有用**（这正是它的位置） |
| **知识缺口（时效）**：每期都会变 | 版本活动 / 卡池 / 深渊 / 剧诗 / 危战 | ❌ **不用搜索** ✗ —— 归 `12` 的期次表（官方结构化源更准更便宜）|
| **资产文案缺漏** | `07` TODO-15 / TODO-23 的 198 条 | ❌ 要 **textmap hash**，搜索给不了 |
| **推理幻觉**：模型自己拼出来 | `07` **TODO-21**：造出不存在的「月超导」（按"月感电 ↔ 月超导"的对称性编的） | ⚠️ **半用**：能当**独立校验器**，不能当答案源 |
| **规范 / 风格**：规则没写清或有冲突 | `07` **TODO-24**：攻略卡里明明有推荐武器，规则第 4 条却让模型答"不清楚" | ❌ **完全没用**，只能改规则 |

后两类占本项目历史 TODO 的**绝大多数**。⇒ 把搜索 API 当"自进化引擎"会严重跑偏 ✓。

## 3. 搜索 API 的正确位置：第三路数据源

现有数据供给是两路，搜索 API 是**第三路**（不改任何在线契约）：

| 路 | 内容 | 权威性 | 时效性 | 落地方式 |
| --- | --- | --- | --- | --- |
| ① 自建语料 | 攻略卡 / 机制卡 / 词条权重 / 套装效果（`character_guides`、`character_mechanics`、`character_stat_weights`…） | 高（人工提炼 + 原文出处） | 低（手动导入） | 离线 ETL（`07` TODO-18 / TODO-20 / TODO-29） |
| ② 第三方资产 | Enka / API-docs 的 `characters` / `loc` / `weapons` / `affixes` | 高（游戏数据本身） | 中（随快照更新） | `cmd/assetimport` |
| ③ **搜索 API** | **网页检索 + 正文抓取** | **中**（看 `authority`，需人工复核） | **高**（`after:` / `date`） | **本文设计** |

**它在本项目里真正值钱的四件事**：

1. **长尾时效兜底**——`site:` + `after:` 的检索对"我们表里还没收的临时活动"有一手价值；⚠️ **但定期内容（每期深渊 / 剧诗 / 卡池 / 版本前瞻）不走这里** ✗ —— 它们有官方结构化源（公告 `start_time` / 客户端 Excel），用 600~800 字摘要替代精确字段是净亏 ⇒ 归 `12`（期次表 ＋ 自动刷新）✓；
2. **事实溯源**——每条结果自带 `url` + `date` + `authority`，正好补上"机制卡每条要带原文出处"（`07` TODO-20）的缺口；
3. **交叉校验**——给 TODO-21 那类"按名字对称性编造"的错误做**独立第二意见**（只打标，不直接进答案）；
4. **长尾采集**——`site:biligame.com` + `after:2026-06` 比手写爬虫省事，返回的是**结构化摘要**而非裸 HTML。

**它做不到的事（必须写进设计，防止用错）**：

- ❌ **判断对错**——搜索相关性 ≠ 游戏事实正确性，权威站点也可能过时；
- ❌ **替代已建语料**——攻略卡的结论式短文比搜索摘要更适合喂模型（长度、口径、可审计）；
- ❌ **当"自我评估"信号**——不能让模型用搜索结果给自己判分（见 §4.3）。

### 3.1 在本项目里到底用在哪（用途地图，2026-10-18 补 ✓）

> 一句话：**自进化解决"我们怎么知道自己变差了"，搜索 API 解决"缺的那块料能不能找到线索"**；两者交集只有一处 —— 找到料 ⇒ 人审 ⇒ 变成评测题 / 攻略卡，而那一步的价值**远低于**前两步 ✓。

#### A. 自进化：真正有收益的是 P1 + P2，不是 P3 ✗

| 落点 | 现状痛点 | 能做什么 | 价值 |
| --- | --- | --- | --- |
| **`chat_*` 失败样本** | 数据缺口一直**靠人肉发现**（`07` TODO-15 的 93→198 条、TODO-23、TODO-18），每次盘点要重新筛一遍日志 | **P1 回流**：自动捞 `degraded=true` / 空回复 / 60s 内重问 ⇒ 产出「缺口清单 ＋ 候选评测题」 | ⭐⭐⭐ 最高，**不花钱不动线上** |
| **改提示词的回归保护** | prompt 已到 **v21**，每次改都靠人眼复跑 50 条；`../web/06` 记的"一天三次新改动伤旧功能"就是这病 | **P2 评测门**：50 → ≥100 条 ＋ 断言（平均字数 / 拒答 / "没有这个角色"一票否决 / 出戏词 / Markdown）＋ 硬指标不过退出码非 0 | ⭐⭐⭐ **刚需**，直接接 `preflight.ps1` 全档 |
| **发版验收** | `deploy/verify-release.ps1` 的 golden 断言只覆盖面板（12/12 行、丝柯克 61.6%） | 把模型侧指标也做成 golden，与面板断言并排 | ⭐⭐ 顺手 |
| **few-shot / 规则建议（P4）** | — | 提案制 | ⭐ **基本用不上**：规则层不许自动改（§4.4），few-shot 提案仍要人看 ⇒ 省不了多少 |

⇒ **"自进化"在本项目的真实形态 = 把已经答错的问题变成可复跑的回归用例**，而不是"模型学到新知识" ✓。

#### B. 搜索 API：四个窄场景，其中只有一个最靠谱

| # | 场景 | 落在项目哪里 | 允许进答案吗 | 建议 |
| --- | --- | --- | --- | --- |
| **①** | **机制 / 反应名的独立第二意见** | `07` TODO-21（模型编出「月超导」）、TODO-27（星烁体系只记了桑多涅） | ❌ **只打标，不进答案** | ✅ **最先做**（最符合 `09 §1` 零工具红线）|
| **②** | **未收录角色的兜底** | `character_guides` 只有 128 位，新角色 / 外服角色问进来只能答"没有查到" | 🟡 仅人审通道 | 与 ③ 同一条流水线 |
| **③** | **攻略卡出处回填** | `07` TODO-20「每条机制事实要带原文出处」 | 🟡 仅人审通道 | `source_url` + `date` + `authority` 正好是现成字段 |
| **④** | **表里没收的限时活动** | 当期内容已被 `12` 的期次表接管 | 🟡 | 只剩"社区口径"，边际收益 |

**明确用不上的四类**（不要在这上面花时间 ✗）：

| ❌ | 原因 |
| --- | --- |
| 资产文案缺漏（`07` TODO-15 / TODO-23 的 198 条） | 缺的是 **textmap hash**，要游戏文本表，搜索给不了 |
| 配队主流度（`07` TODO-30 / TODO-31 的收录篇数 / 点赞 / lift） | 要**帖子元数据**，不是搜索摘要 |
| 圣遗物权重 / 毕业线数值（`07` TODO-08） | 要精确数字，摘要不可用 |
| 自动生成评测题 | 自出题自判卷 ⇒ §4.3 明令禁止 |

#### C. 按性价比排的顺序（覆盖 §11 的原始排期）

| 顺序 | 做什么 | 成本 | 收益 |
| --- | --- | --- | --- |
| 1 | **P1 失败样本回流** | 0.5~1 天，¥0 | 替代人工盘点，直接喂 TODO-15 / 18 / 23 |
| 2 | **P2 评测门** | 2 天 | 每次改 prompt 有网兜 |
| 3 | **搜索试点 P3a**（模板 ① ② 各 10 次） | 半天，¥0.5 | 只验证"值不值得进流水线" |
| 4 | **机制名校验器**（场景 ①，只打标） | 1~2 天 | 防"月超导"类幻觉 |

## 4. 四条硬约束（不守住，自进化会变成自退化）

### 4.1 永远是「候选 → 人审 → 生效」，不允许自动入库

沿用 `ai_prompts` 已验证的模式：**内容不可变、新增版本、启用即生效、置 0 即回滚** ✓。
数据侧同理 —— 新表 `candidate_facts`，状态机见 §7。**搜索来的内容直接进 system，等于给"资料外不编造"开后门** ✗。

### 4.2 每条采集结果必须带 `source_url` + `fetched_at` + `game_version`

`paimon_rules` 明确**禁止**回答里出现"可能不是最新版本"这类免责声明（v4 起的口径）⇒ **过期数据比没有数据更危险** ✗。
没有日期的搜索结果，毒性大于收益，一律不进库。

### 4.3 判分不能由"生成补丁的那个模型 / 同一个 agent"来做

自进化循环最常见的死法：自己出题自己判卷，指标一路涨、体验一路跌 ✗。
- 通过线必须是**人定的、写死的**（沿用 `07` TODO-17 已定的口径，见 §8）；
- 评测集必须是**留出集**（held-out）：调提示词时看过的题，不能同时当验收题；
- 生成候选与判分**必须用不同的 prompt**（或不同轮次），不得同轮自评。

### 4.4 规则层不自动改

`paimon_base` / `paimon_rules` / `paimon_fewshot` 里的**安全与边界条款**（越界话术、防注入、不否认角色存在、不出戏）**任何自动化都不许动** ✗。
可自动化的只有：**数据表增补、few-shot 示例扩充、评测题补充**；其中 few-shot 与评测题仍需人点确认（§9）。

> 与 `ai/09 §1` 的关系：09 的红线是「**不给模型工具**」。本文的搜索调用全部发生在**主服务 / 离线脚本**里，模型侧依然零工具 ✓ ⇒ **不违反 09**。

## 5. 进化分层

把"进化"拆成三层，各自的可自动化程度不同：

| 层 | 进化什么 | 载体 | 验得了吗 | 自动化程度 |
| --- | --- | --- | --- | --- |
| **L-data 数据层** | 事实、词条、攻略结论、时效内容 | `character_*` / `candidate_facts` | ✅ 可对着原文逐字比对 | 🟡 **半自动**（流水线自动，生效要人审） |
| **L-behaviour 行为层** | few-shot 示例、回复风格、分点格式 | `paimon_fewshot` | 🟡 靠评测集 + 人的观感 | 🟠 **提案制**（自动生成候选，人批） |
| **L-rule 规则层** | 人格、边界、安全 | `paimon_base` / `paimon_rules` | ❌ 评测集测不出来（见 TODO-17：指标能过、体验能崩） | 🔴 **人写死，不自动** |

**为什么 L-rule 不自动**：本项目有现成的反例 —— `07` TODO-17 里"平均字数上去了、拒答却没降"这种情况，任何自动化都识别不了；靠的是人读回复。

## 6. 闭环设计（总图）

```
【P1 发现】 线上 chat_* 表（只读）
   │  捞三类可疑样本：① 降级回复（degraded=true / aiDegradeReply）② 空回复 ③ 用户短时间内重问
   ▼
【P1 分类】 人工 / 规则分类 → knowledge_gap | hallucination | rule_conflict | style
   │  · 只有 knowledge_gap 进 P3；hallucination 走"校验器"路线；rule_conflict / style 走人改规则
   ▼
【P3 采集】 定向检索（site: + after: + count≤5 + need_content=false）
   │  → 抽事实（模型抽取 + 原文逐字校验）
   ▼
【P3 候选】 写 candidate_facts（source_url / fetched_at / game_version / 原文摘录 / 抽取模型版本）
   │
   ▼
【人审】   待审队列（后台面板或 CLI）→ 通过 / 驳回 / 修改后通过
   │
   ▼
【P2 验证】 run_eval.py + 通过线断言 + 与基线 diff → 不过就不发
   │
   ▼
【发布】   数据进正式表 / few-shot 新增版本（走 /internal/v1/admin/ai-prompts）
   │
   └─► 出问题：置 enabled=0 回滚（已有机制 ✓）
```

**关键点**：P1 与 P2 **完全不需要搜索 API、不花钱、不动线上**，却能拿到本设计 80% 的收益 ✓。

## 7. 状态机与表结构（候选事实）

### 7.1 状态机（照 `ai_prompts` 的回滚语义抄）

```
quarantined ──人审通过──► pending ──发布──► effective ──置 0──► disabled
     │                        │                                   │
     └──驳回──► rejected       └──校验失败──► rejected              └──可重新启用──► effective
```

| 状态 | 含义 | 谁能改 |
| --- | --- | --- |
| `quarantined` | 刚采集、未经人看，**任何情况下不进回答** ✗ | 流水线写 |
| `pending` | 人已核对原文、待发布 | 人 |
| `effective` | 已进正式表 / 已注入 | 人 |
| `disabled` | 曾生效、已下线（保留可回滚） | 人 |
| `rejected` | 驳回（保留理由，防止重复采） | 人 |

### 7.2 `candidate_facts`（拟，主服务库）

> 为什么放主服务库：AI 服务**无状态、不碰业务库**是硬约束（`AGENTS.md §2`）✓；采集与审核都不属于模型推理。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | — |
| `kind` | varchar | `character_guide` / `mechanic` / `relic_set` / `text_map`（⚠️ 已删去 `timeliness` ✗ —— 期次类内容**不进本表**，走 `12` 的 `content_periods`，两者状态机语义不同：本表人签字驱动、期次表时间驱动 ✓） |
| `subject` | varchar | 角色名 / 套装名 / hash / 主题词 |
| `field` | varchar | 落哪个字段（如 `team_pick` / `cannot` / `effects`） |
| `proposed_value` | text | 候选内容（结论式短文，不抄原文长段） |
| `source_url` | varchar | **必填** |
| `fetched_at` | datetime | **必填** |
| `game_version` | varchar | 采集时对应的游戏版本（**必填**，不知道就填 `unknown` 且**必须人补**）✓ |
| `excerpt` | text | 原文摘录（逐字，用于逐字校验） |
| `authority` | int | 搜索结果的 `authority`（0~4，`-1` 未知） |
| `status` | varchar | 见 §7.1 |
| `reviewer` / `reviewed_at` / `remark` | — | 审核痕迹 |
| `dedupe_key` | varchar UNIQUE | `kind+subject+field+proposed_value` 的 hash（防重复采） |

**一条硬规则**：`proposed_value` **必须能被 `excerpt` 支撑**，支撑不了就是"模型转述"，退回重采 ✗。

## 8. 评测门（P2）：先把"证明变好了"做出来

### 8.1 现状与通过线

现有评测集：解释类 **20 条** ＋ 机制 **30 条**。通过线沿用 `07` TODO-17 已定的口径（同口径复跑）：

| 指标 | 通过线 | 来源 |
| --- | --- | --- |
| 平均字数 | **≥ 350 字** | TODO-17 验收 |
| ≤150 字的条数 | **≤ 2 条** | 同上 |
| 拒答条数 | **≤ 2 条** | 同上 |
| 出现"没有这个角色 / 没有叫这个名字的角色" | **0 次**（一票否决） | 同上 |

**另外加两条本项目特有的**：出现「资料 / 资料库 / 系统 / 和资料一致」这类**出戏词** ⇒ **0 次**（v5 起口径）；出现 Markdown 标记（`**` / `#` / 行首 `-`） ⇒ **0 次**（v3 起口径）。

### 8.2 前置：评测集扩到 100+

20 + 30 条**不够当自动卡门**：误杀/漏放都能很明显 ✗。
- 扩集方式：**从 P1 的失败样本回流**（`07` TODO-17 的 questions.json 前 8 条就是线上真实提问）；
- 扩集目标：**≥100 条**，且按「配队 / 毕业线 / 天赋顺序 / 机制 / 词条 / 剧情 / 越界 / 注入」分桶；
- 每条必须带 `expected_keywords`（至少 1 个必须出现的实体词）与 `must_not`（禁止出现的词），否则无法自动判。

### 8.3 验证方式

```powershell
# 改前（基线）与改后（候选）用同一口径各跑一次
.\.venv\Scripts\python.exe tests\eval\run_eval.py --out before.json
# …改提示词 / 数据…
.\.venv\Scripts\python.exe tests\eval\run_eval.py --out after.json
# 断言 + diff（P2 待实现）
.\.venv\Scripts\python.exe tests\eval\check_gate.py --before before.json --after after.json
```

`check_gate.py` 的规则（**待实现**）：任一硬指标不过 ⇒ 退出码非 0 ⇒ 阻断发布；软指标下降 >10% ⇒ 打印警告但仍可发（由人拍板）。

## 10. 搜索 API 接入细节

### 10.1 接口速查（2026-10-17 开放）

| 项 | Search | Fetch |
| --- | --- | --- |
| 端点 | `POST https://api.deepseek.com/v1/tools/search` | `POST https://api.deepseek.com/v1/tools/fetch` |
| 鉴权 | `Authorization: Bearer <DeepSeek API Key>`（**与对话同一把 key，无需新开通** ✓） | 同 |
| 计费 | **5 元 / 1000 次成功请求**（按次，不按 token、不按条数） | 同 |
| 不计费 | HTTP 200 但 `results` 为空 / 失败 / 超时 | 未取到正文 |
| 限速 | 每账号 **5 QPS** | 每账号 **5 QPS**（另有目标域名级 QPS） |

**Search 请求字段**：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `query` | ✅ | 1~128 字符，支持搜索语法 |
| `count` | — | 1~50，默认 10（**只改条数不改价格**） |
| `ori_question` | — | 触发搜索的用户原始问题（帮它理解意图） |
| `localization` | — | 用于优先本地化结果的 IP |
| `need_content` | — | `true` 才在 `content` 返回正文（**默认 false，省 token**） |

**Search 返回**（`results[]`）：`rerank_score`（0~3，**≥1.5 优质**）、`title`、`url`、`snippet`（100~200 字，给前端）、`summary`（600~800 字，**给模型**）、`content`、`site_name`、`site_icon`、`date`（UTC RFC3339，可 null）、`authority`（0~4，**≥3 极权威**，`-1` 未知）。

**搜索语法**：`site:` / `-site:` / `-词` / `-"短语"` / `"精确短语"` / `lang:zh,en` / `after:2025-01-01` / `before:2026-06-01`。

### 10.2 本项目的三条查询模板

```text
① 攻略结论补录（对应 07 TODO-18 / TODO-28）
   "角色名 配队 OR 毕业线 OR 天赋顺序 site:biligame.com after:2026-01"
   count=5, need_content=false

② 机制 / 反应名核对（对应 TODO-21 的校验器路线）
   "角色名 机制 OR 反应名 site:biligame.com OR site:mihoyo.com"
   count=5, need_content=false  → 只取 site_name 与 url 做第二意见，不采正文

③ 时效性内容（新版本 / 卡池 / 活动）
   "原神 版本 活动 site:mihoyo.com after:2026-09"
   count=5, need_content=false
```

**参数取值纪律**：

- `count ≤ 5`：`summary` 一条 600~800 字，5 条已接近一次注入预算；
- **默认 `need_content=false`** ✗：正文动辄数千字，注入成本远高于搜索本身（§10.3）；
- `rerank_score < 1.5` 与 `authority < 2` 的结果**直接丢**，不进入候选队列；
- `date` 为 `null` ⇒ 不做时效类结论，只能进"待人工确认"。

### 10.3 成本（真实大头不在搜索）

| 项 | 粗估 | 说明 |
| --- | --- | --- |
| 搜索调用 | 5 元 / 千次 ⇒ 一次版本迭代 100 次 ≈ **0.5 元** | 可忽略 |
| 抽事实（模型抽取） | 每次 1~2k token 输出 ⇒ 100 次 ≈ **几元** | 低频，可忽略 |
| **注入对话（若 `need_content=true`）** | 一条正文 3~5k token × 每次对话 | ✗ **这才是贵的**，所以默认只要 `summary` |

> ⇒ **搜索 API 本身的成本可以忽略，真正的成本约束在"注入多少进 system"** ✓。

### 10.4 失败与降级（沿用现有原则）

| 失败 | 处理 |
| --- | --- |
| 网络 / 429 / 5xx | 重试 ≤1 次，之后**跳过本批**，不阻塞任何提问链路 |
| 空 `results` | 记为"未覆盖"，**不计费**，写入采集日志便于下次重试 |
| 抓取正文为空 | 降级为只用 `summary`；`summary` 也为空 ⇒ 丢弃 |
| 整条链路挂掉 | **静默跳过、照常回答** ✗（与 `07` TODO-19 对 RAG 的要求同一口径：**外部增强挂了绝不能导致答不出来**） |

### 10.5 ⚠️ 计费过渡期（必须记住）

| 时间 | 状态 |
| --- | --- |
| 现在 ~ 2026-10-31 | 在 **DSH / Claude Code / Codex** 里用 DeepSeek API 时，服务端工具调用已能访问 Search/Fetch，**暂不计费** |
| **2026-11-01 00:00（北京时间）起** | **开始按次收费**（5 元 / 千次） |

⇒ 本设计的采集流水线**是自建脚本直连**，不走"模型工具调用"这条路，所以**不受该过渡期影响**：从第一天起就按次计费 ✓（也因此金额可控）。

## 11. 实施顺序（排期建议）

| 阶段 | 内容 | 依赖 | 估时 | 是否花钱 |
| --- | --- | --- | --- | --- |
| **P1** | **失败样本回流**：只读 `chat_*`，按"降级 / 空回复 / 追问"捞样本，人工分类 → 产出**候选评测题清单**与**数据缺口清单** | 无 | 0.5~1 天 | ❌ |
| **P2a** | **评测扩集**：从 P1 结果扩到 ≥100 条，给每题补 `expected_keywords` / `must_not` | P1 | 1~2 天 | ❌（跑评测要 token） |
| **P2b** | **评测门**：`check_gate.py` + 通过线断言 + 与基线 diff；接进发布前脚本 | P2a | 0.5 天 | ❌ |
| **P3a** | **搜索试点**：用 §10.2 的三条模板各打 10 次，人工评质量 → 决定值不值得进流水线 | 无（可与 P2 并行） | 半天 | ✅ ≈ 0.5 元 |
| **P3b** | **`candidate_facts` + 采集脚本**：检索 → 抽取 → 逐字校验 → 写 `quarantined` | P3a 通过 | 2~3 天 | ✅ 少量 |
| **P3c** | **人审入口**：先做 CLI `review_facts.py`（列表 / 通过 / 驳回 / 改内容），后台面板后补 | P3b | 1 天 | ❌ |
| **P4** | **提案制**：自动生成"建议新增 few-shot / 建议补评测题"的 diff，人点确认 | P3c + P2b | 2 天 | ✅ 少量 |

**为什么 P3a 可以并行**：它只是一个"值不值得投"的验证，不依赖 P1/P2，且成本几毛钱；但**不允许跳过 P2 直接上 P3b** ✗ —— 没有评测门，采回来的数据无法判断是变好还是变坏。

> ⚠️ **2026-10-18 补**：本表是**能力顺序**，不是**开工顺序** ✓。按项目实际收益重排后的顺序见 **§3.1-C**（P1 → P2 → P3a 试点 → 场景 ① 校验器 → P3b 缓）✓。

## 13. 明确不做

| ❌ 不做 | 原因 |
| --- | --- |
| 让模型自己改自己的提示词并自动发布 | 无人工签字 ⇒ 必然漂移；且违反 §4.3 |
| 用同一模型给同一轮回答打分当"自评" | 指标会涨、体验会跌（§4.3） |
| 把搜索正文整段注入 system | token 成本 + 污染"资料外不编造"约束（§4.1 / §10.3） |
| 给 AI 服务接搜索工具（`bind_tools`） | 违反 `ai/09 §1` 长期红线（工具质变威胁模型） |
| 自动改 `paimon_base` / `paimon_rules` / `paimon_fewshot` | 规则与风格必须人写死（§4.4） |
| 用搜索替代自建攻略语料 | 结论式短文比搜索摘要更适合喂模型（§3） |
| 采"没有日期 / 没有出处"的内容 | 过期数据比没有数据更危险（§4.2） |

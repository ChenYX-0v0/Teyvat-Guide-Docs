**关键设计（三条，改动前先读）**：
1. **资料与登录态无关**：`asset_*` 是公开数据，因此 `buildContext` 对**匿名请求**也会注入资料（V1 的玩家档案仍要求登录 + 绑定 UID）。
2. **预算独立**：玩家档案用 `ctxTokenBudget=1500`，资料另设 `referenceTokenBudget=400` 且最多注入 `maxReferenceCharacters=2` 个角色 —— 两者共用 AI 服务的 1500 上下文预算，不分开算会把面板挤掉（AI 服务超出预算时会**整条丢弃末尾角色**）。
3. **命中即"权威"**：库里有的照它答；库里没有的角色会显式渲染成「本服暂无该角色的资料（不得凭记忆给出数值）」——**这条是 V2.3 生效的前提**，模型对热门角色有记忆，不说明清楚它会用旧数据作答。

**实测（2026-09-12，匿名单轮）**：问「胡桃推荐什么圣遗物词条」→ 回答的副词条顺序（百分比生命值 > 暴击率 > 暴击伤害 > 充能效率 > 生命值）与主词条（时之沙 生命值 / 空之杯 火元素伤害加成 / 理之冠 暴击伤害）**与库内 payload 逐项一致**；服务端日志 `ai asset reference attached {"matched": 1}`；单轮 tokens 1136（改前同口径闲聊基线 625~673，含回复长度差异）。
覆盖率：库里 **124** 个角色 / 124 条推荐词条（2026-09-26 补芙宁娜与两个 7.1 新角色后），当前 **100% 命中**，所以「暂无资料」分支只能靠单测覆盖。

| 结构化查表 | ❌ | ❌ | 100%（精确匹配） |
| 向量 RAG | ✅ 另找供应商 | ✅ | 取决于检索质量 |

**验收方式（2026-09-15 实测）**：

## 6. 阶段 P4：可观测、成本与配额

> **优先级说明（2026-09-12）**：本阶段在"单机 + 自用"阶段可以往后放；但**一旦推上云、C 端用户变多，它应提到 V2 之后的第一位**——
> 它是唯一"持续流血"的风险点：AI 服务侧只有并发闸门（`llm_max_concurrency` 信号量），**没有按用户限流**，一个用户刷量就能占满闸门让其他用户排队；主服务侧也没有任何频率限制，而 token 是花钱的。
> 数据基础已经具备：`chat_messages` 已按条落库 `tokens_input / tokens_output / tokens_cached`（2026-09-12，见 `admin/06` §10），做聚合与配额**不需要再改表**。
> 注意：这与「中转网关」（`admin/05`，管理面工程化）是两条线，别混为一谈。

| # | 交付物 | 验收 |
| --- | --- | --- |
| P4.1 | 用量落库/上报：按**用户 + 会话**聚合 token | 管理端可看每用户消耗 |

| P4.4 | 告警接入（见 `04-部署运维接入说明.md §8.3` 六项） | ✅ **2026-09-17 完成**：5 条规则（提示词来源兜底 / 提示词接口失败 / 服务 5xx 突发 / 上游 5xx 占比 / 前缀缓存失效）在 AI 服务进程内评估，**日志 + webhook 双通道投递**（含冷却与恢复通知），`GET /metrics` 暴露指标与规则状态；"进程整体挂掉"明确留给外部探针 |

**2026-09-14 补充：P4.3 已出设计，本阶段拆成三件事**（口径真源 `../shared/05-AI使用边界设计（匿名·配额·内容治理）.md`）：

1. **匿名禁用 AI**（改预设问答 + `preset_qa` 表）——止血项，让额度消耗全部有归属、可审计；
2. **每用户每日 10 万 token 配额 + 单用户并发 ≤2**（P4.3 的落地口径），超 5 万进后台观察名单；
3. **无关问题标记**：本服务侧新增一次极小分类调用（`AI_CLASSIFY_MODE=off|sample|all`，默认 `off`），结果经 `done` / `data` 的可选字段回传。
   ⚠️ 该项每次提问多消耗 ≈**350~400 tokens**（2026-09-15 实测；分类器提示加强后由初估 220 上修）（平台成本，**不计入用户配额**）：全判按 1 万问/日 ≈ 350~400 万 tokens/日，`sample=0.2` ≈ 70~80 万。

**粗估**：**2~3 人天**（其中第 3 项另加 0.5 天）

## 10. 明确不做 / 不建议做

| 事项 | 原因 |
| --- | --- |
| ❌ AI 服务直连业务库（MySQL） | schema 变更会跨服务断裂，破坏"完全独立"；提示词走内部接口，资产走导出/查表 |
| ❌ AI 服务里做用户体系 / 会话持久化 | 职责在主服务；AI 服务必须无状态才能随意重启扩容 |
| ❌ 为了省钱换掉 DeepSeek | 成本大头是对话输出 token；embedding 是零头。换平台迁移成本 > 多管一个 key |
| ❌ 先做向量 RAG 再做结构化查表 | 顺序反了：查表零依赖、准确率 100%；RAG 要新供应商且依赖语料 |
| ❌ 同步链路叠加"重试 + 长超时" | 硬约束：重试 ≤1 次，总耗时有上限 |
| ❌ 用 `ALLOW_INSECURE_DEV=true` 绕过启动自检 | 等于 `/v1/*` 裸奔 |
| ⚠️ 引入 LangChain 的 Memory 类 | AI 服务无状态，会话归主服务；用了就破坏边界 |
| ⚠️ 把动态内容（时间戳/随机值）塞进人格提示词 | 会让 DeepSeek 前缀缓存整段失效，缓存命中价差 50 倍 |

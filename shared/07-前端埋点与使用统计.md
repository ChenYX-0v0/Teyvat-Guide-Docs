## 1. 目标与非目标

### 1.1 要回答的四个问题

| # | 问题 | 用途 |
| --- | --- | --- |
| Q1 | **哪些功能有人用、哪些没人用**（功能使用度排行） | 决定后续把精力投在哪、砍掉什么 |
| Q2 | 从"进来"到"用上核心功能"的**漏斗**（首页 → 对话页 → 首次提问 → 二次提问） | 找流失点 |
| Q3 | **失败与空态发生在哪**（流式失败、UID 查询失败、空展柜） | 找体验/质量问题 |
| Q4 | **移动端 vs 桌面端**差异 | 决定移动端是否值得继续投入 |

### 1.2 明确不做（先把边界钉住，避免蔓延）

| 不做 | 原因 |
| --- | --- |
| 不引第三方 SDK（GA / 神策 / Sentry 起步阶段） | 外链与合规成本；自研 <2KB 足够，且数据留在自己库 |
| **不采集对话正文 / 提示词内容** | 这些已在 `chat_messages` / `ai_prompts` 里；埋点重复采集只会放大隐私面 |
| 不采集密码、UID 原值、IP 明文 | UID 只记 `has_uid` 布尔；IP 仅用于服务端限流、**不落库** |
| 不做用户画像 / 广告归因 / 跨站追踪 | 与产品无关，且触碰合规红线 |
| 不做秒级实时大盘 | 按天聚合足够；实时性 = 成本 |
| **不用埋点替代服务端事实** | 提问数、会话数、token 消耗已有落库数据，直接算更准（见 §2） |

## 2. 核心取舍：先看「哪些指标能白拿」（本方案最重要的一节）

**已有落库数据（零成本、口径最准，不要重复采集）**：

| 指标 | 现成来源 |
| --- | --- |
| 提问数 / 会话数 / 消息数 | `chat_messages` / `chat_sessions` |
| 登录用户数 / 活跃 | `users` / `user_sessions` |
| 每日 token 消耗、缓存命中、降级 | 用量落库（`../ai/05` 已完成，后台「对话记录」页可查） |
| 无关问题占比 | `chat_messages.off_topic` / `off_topic_reason` |
| 被删会话（用户主动清理） | `chat_sessions.deleted_at` |

**结论**：埋点只补「**服务端看不到的部分**」——
① 页面浏览与停留；② 入口点击（哪个 CTA 被点）；③ 空态/失败发生在前端时；④ 前端性能与错误；⑤ 移动端占比。

> 按这条原则，事件清单能压到 **13 个**（§5），而后端几乎不需要动业务逻辑。

## 3. 数据模型

**放业务库 `teyvat_guide`**（不是管理库），理由：
① 写入方是主服务，它本来就连业务库；
② 管理库 `teyvat_admin` 只放运营配置（用户 / 项目注册表）；
③ 后台读统计走**主服务内部接口**，与「用户管理」同一模式（`shared/04 §4.4`）→ **不需要给后台开跨库权限**。

### 3.1 明细表 `usage_events`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint PK | |
| `event` | varchar(64) | 事件名（**必须在白名单内**，否则丢弃） |
| `event_version` | smallint | 口径版本（默认 1；口径变更时 +1，便于新旧对比） |
| `user_id` | bigint NULL | 登录用户；**匿名为 NULL** |
| `anon_id` | char(16) NULL | 匿名设备标识（前端 localStorage 随机串，见 D1） |
| `session_id` | varchar(64) NULL | 会话 id（chat 相关事件带） |
| `page` | varchar(32) | 页面 key（`home` / `chat` / `account` / `wiki` / `login`） |
| `platform` | varchar(8) | `mobile` / `desktop`（UA + 屏宽判定） |
| `props` | json NULL | 事件属性（**只保留白名单键**，单条 ≤2KB） |
| `client_ts` | bigint | 客户端时间（ms） |
| `created_at` | datetime | **服务端时间（统计一律以它为准**，防客户端改时间） |

索引：`(event, created_at)`、`(created_at)`、`(user_id, created_at)`

### 3.2 聚合表 `usage_daily`（看板只读它，不扫明细）

| 字段 | 说明 |
| --- | --- |
| `day` (date) + `event` + `dim_key` + `dim_value` | 主键；`dim` 用于按页面/平台下钻（如 `page=chat`、`platform=mobile`） |
| `pv` | 次数 |
| `uv` | 去重用户数（登录用 `user_id`，匿名用 `anon_id`） |
| `users` | 登录用户数 |

**保留策略**：明细 **90 天**（可配 `usage.retention_days`）自动清理；聚合表**永久保留**。

## 4. 接入方式

### 4.1 传输：`POST /api/events`

- **允许匿名**（否则看不到匿名行为；匿名访问已是产品事实，见 `shared/05 §1`）；
- 批量提交：单请求最多 **20 条**；优先 `navigator.sendBeacon`（**页面卸载也能发出**），回退 `fetch(..., { keepalive: true })`；
- **永不影响主流程**：不 `await`、失败静默丢弃、不重试、不弹错误提示。

### 4.2 前端（自研 `src/lib/track.ts`，<2KB）

- 队列 + 触发时机：每 5 秒 / 满 20 条 / `visibilitychange` 隐藏时 flush；
- `track(name, props)` 为唯一入口；事件名用**常量**（前后端共用一份清单，避免拼写漂移）；
- 开关：仅生产构建 + 服务端配置开启时才真正发送；本地 dev 默认只 `console.debug`；
- 埋点位置：路由变化（`AppLayout` 监听 location）、关键交互（CTA / 提交 / 查询）、异常（错误边界 + 请求失败）。

### 4.3 后端

| 环节 | 做法 |
| --- | --- |
| 鉴权 | 匿名可访问（不带 Token 也可）；带 Token 时解析出 `user_id` |
| 限流 | 每 IP 60 次/分钟、每用户 300 次/分钟；**超限静默丢弃**（不回错误，避免被探测） |
| 校验 | 事件名不在白名单 → 丢弃并计数（指标 `usage_events_dropped`）；`props` 只留白名单键 |
| 写入 | channel + 单 worker **批量 INSERT**，不阻塞请求；写失败只记日志（**埋点不能影响业务**） |
| 聚合 | 主服务内定时任务（每日 03:30，幂等 upsert；实现方式对齐 `ai/04 §8.3` 现有告警任务） |

## 5. 事件字典 v1（13 个）

命名规范：`域_对象_动作`，全小写下划线（与后端字段风格一致）。

| 事件名 | 触发时机 | 关键属性 | 对应问题 |
| --- | --- | --- | --- |
| `page_view` | 路由进入 | `page`、`referrer_page`、`is_logged_in`、`platform` | Q1/Q4 |
| `page_leave` | 路由离开 / 页面隐藏 | `page`、`dwell_ms` | Q1（哪页留不住人） |
| `home_cta_click` | 首页 CTA 点击 | `target=chat\|wiki` | Q2 |
| `chat_message_sent` | 提问发出（成功进入流式） | `source=input\|sample_chip`、`has_uid`、`is_first_in_session` | Q1/Q2 |
| `chat_stream_failed` | 流式失败 / 中断 / 走兜底 | `reason=network\|timeout\|http_4xx\|http_5xx\|fallback`、`elapsed_ms` | Q3 |
| `chat_new_session` | 点「新对话」 | — | Q1 |
| `chat_session_opened` | 历史会话被打开 | `index`（列表第几个） | Q1 |
| `chat_session_deleted` | 删除会话 | — | Q1 |
| `chat_preset_expanded` | **匿名**展开预设问答 | `index` | Q1（匿名看到什么才有价值） |
| `account_uid_query` | UID 查询完成 | `result=ok\|empty\|failed`、`force_refresh` | Q1/Q3 |
| `account_uid_bind` / `account_unbind` | 绑定 / 解绑 | — | Q1 |
| `auth_login` | 登录提交 | `result=ok\|failed` | Q2/Q3 |
| `web_error` | 错误边界捕获 | `message_hash`（**只存哈希，不存原文**） | Q3 |

> 与既有能力互补：**"提问总数 / token 成本 / 无关问题占比"不要埋点**，直接从 §2 的表算。

## 7. 分期与验收

### P0 · 先把数据收准（0.5~1 天，**必须在上线前落地**）

内容：明细表 + `POST /api/events` + 前端 `track()` + 8 个核心事件
（`page_view`、`page_leave`、`home_cta_click`、`chat_message_sent`、`chat_stream_failed`、`account_uid_query`、`auth_login`、`web_error`）。

**验收**：
① 页面点一次 → 库里出现一行；
② **埋点接口打成 500 / 断网时，主流程完全不受影响**（实测一次）；
③ 未知事件名被丢弃并计入 `usage_events_dropped`；
④ 超限被**静默**丢弃（客户端无感、无报错弹窗）；
⑤ 本地 dev 默认不发送（只 `console.debug`）。

### P1 · 看板能用（1~2 天）

内容：聚合表 + 每日聚合任务 + 后台「使用统计」面板（概览 / 排行 / 趋势）+ CSV 导出。

**验收**：① 面板每个数字与 SQL 直查**逐项对账一致**；② 趋势曲线无断点（无数据日显示 0）；③ 导出可打开且行数与面板一致。

### P2 · 按需

漏斗与留存、匿名→登录转化（`anon_id` 关联）、异常事件与告警联动（告警已有，见 `ai/04 §8.3`）、事件明细下钻对比。

## 8. 合规与隐私（大陆运营必须落实）

1. **最小化采集**：不采集对话正文、密码、UID 原值、IP 明文（§1.2）；
2. **隐私政策**：上线前在 `../web/11-上线准备（域名·备案·HTTPS）.md` §7 的合规清单里**加一条**——声明"收集匿名使用统计及用途"；
3. **可远程关停**：服务端下发 `usage_collect: bool`，前端以此为准（出问题可立即关）；
4. **保留与清理**：明细 90 天自动清理；聚合表不含任何个人标识；
5. **访问控制**：看板走后台既有鉴权；导出操作建议后续接入后台操作日志（当前后台无操作日志，列为 P2 可选）。

## 9. 风险与取舍

| 风险 | 对策 |
| --- | --- |
| 明细表膨胀 | 明细 90 天 + 按天聚合；批量写入 |
| 影响主流程性能 | 不阻塞、失败丢弃、`sendBeacon`、批量 |
| 事件名 / 口径漂移 | §5 字典 + 前后端共用常量清单 + `event_version` |
| 脏数据与被刷 | 限流 + 白名单 + props 键白名单 + **以服务端时间为准** |
| **上线后才想起埋点 → 早期数据永久缺失** | **P0 排在上线前**（本方案唯一的硬性时序要求） |
| 过度采集引发合规风险 | §8 最小化原则 + 可远程关停 |

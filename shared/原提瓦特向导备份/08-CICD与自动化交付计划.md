### 1.1 为什么现在做（四条硬理由）

1. **手工发版有 7 个易错环节**：`构建 → save → scp → load → 改 .env → up -d --no-build → 自检`（`06:84`）。任一环出错都要人工介入，且**没有自动兜底**。
2. **已经出过三次"新改动伤到旧功能"**（`../web/06:108` 原文记载）：词条同名冲突让面板少一行、残留枚举行让冰伤显示 `0.0%`、CRLF 让远端脚本报错。→ 说明**缺的是门禁，不是勤奋**。
3. **零测试是最大短板**：`web` 与 `demo-app` **两边都是零测试、零测试框架**（`../web/06:95`）。⚠️ **流水线接上去如果没有测试可跑，只是把 `build` 搬到了服务器上，等于没做 CI**——所以测试地基必须排在流水线之前。
4. **后台还没上云**（`06:78` 实证：本机 `npm run dev:3000`），且上云早已在排期里（`../ai/06 §1.2`、`../ai/05 §8 O5`）。→ 这是一个**现成的、有价值的**改造靶子，不是为练而练。

### 1.2 双目标（明写，避免做成"演示工程"）

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | **真实交付链路自动化**：把手工 7 步变成一条可复现、可回滚的流水线 | 三条流水线跑在真实仓库上，发布与回滚全程无人手干预 |
| G2 | **补齐两套技术栈的实战经验**：自建型 Jenkins（Groovy / Shared Library / Agent）与云平台型阿里云云效（Flow / ACR / RAM / SLS） | 同一条流水线用两套实现各做一遍，产出**取舍对比结论**（见 §8.2） |

> G2 是"两套都学一遍"的落地方式：**不是各搭一个 hello-world，而是同一条真实流水线做两遍**——这样才能讲出"为什么选它"，而不是"我会用它"。

## 2. AS-IS：现在发一次版要经过什么

| 环节 | 现在怎么做 | 问题 |
| --- | --- | --- |
| 触发 | 人判断"该发了" | 无固定节奏，无记录（**部署频率不可测**） |
| 校验 | 靠开发者自己记得跑 `gofmt` / `go vet` / `go test` / `tsc` / `eslint` / `vite build` | 靠自觉 ⇒ 漏跑无人拦 |
| 构建 | 本机 PowerShell：`deploy/out/release.ps1 -Service server\|web` | 构建环境=开发机，**不可复现** |
| 传制品 | `docker save` → `scp` → `docker load`；或 `deploy/push-images.ps1` 推 ACR 后 `docker compose pull` | 两条路并存，口径不统一 |
| 记制品 | 打 tag（`teyvat-guide-server:20260928-0031`），台账在主仓 `deploy/README.md §3.9` | 台账在**手写文档**里，不自动生成 |
| 上线 | SSH 到 ECS → 改 `.env` 三行 `*_IMAGE` → `docker compose up -d --no-build` | 手改生产 `.env`，**无一键审批/记录** |
| 自检 | 手动跑 `deploy/smoke-ecs.sh`（2026-09-20 首跑 6/6 通过） | 是人跑的，不是流水线跑的 |
| 回滚 | 手动把 `.env` 里 tag 改回上一版 → `up -d --no-build`；脚本留 `.env.bak-<tag>` | **需人工发现失败 + 人工回退**（MTTR 取决于人醒着没有） |

**当前线上 tag**（`../web/06:118`，2026-10-11 复核）：`teyvat-guide-web` = `20261011-2316` ／ `teyvat-guide-server` = `20260928-0031` ／ `teyvat-ai` = `20260927-1610`。

## 3. TO-BE：目标交付链路

### 3.1 一张图（目标态）

```
  开发者 push / 开 MR
        │
        ▼
┌──────────────────────────────────────────────────────────────────┐
│ P1 · 校验流水线（CI）          触发：push / MR                     │
│   preflight 全档：gofmt -l / go vet / go test / 前端 tsc+eslint+   │
│   build / 种子 JSON 校验 / 密钥扫描 / 跨层契约比对                  │
│   ✗ 失败 ⇒ 阻断合并，不产制品                                       │
└───────────────────────────┬──────────────────────────────────────┘
                            │ ✓ 通过
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ P2 · 制品流水线                触发：主干 tag / 手动参数            │
│   docker build（⚠️ 加 --provenance=false --sbom=false）           │
│   → 推 ACR 个人版 crpi-...cn-shanghai.personal.cr.aliyuncs.com     │
│   tag = YYYYMMDD-HHMM（沿用现有规则）                              │
│   产物：三镜像 + 自动生成 tag 台账（替代手写 §3.9）                 │
└───────────────────────────┬──────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ P3 · 发布流水线（CD）          触发：手动参数（选服务 + 选 tag）     │
│   ① 写 ECS /opt/teyvat-guide/.env（自动留 .env.bak-<tag>）        │
│   ② docker compose pull && up -d --no-build                       │
│   ③ 跑 deploy/smoke-ecs.sh 全量自检                               │
│   ④ ✗ 自检失败 ⇒ 自动切回上一 tag 并告警                           │
└───────────────────────────┬──────────────────────────────────────┘
                            │
                            ▼
                  回填度量：构建时长 / 失败率 / 部署频率 / MTTR
```

### 3.2 三条流水线的定义

| 编号 | 名称 | 触发 | 关键内容 | 失败时怎么办 |
| --- | --- | --- | --- | --- |
| **P1** | 校验（CI） | push / MR | `preflight.ps1` 全档 + 跨层契约比对（前端 `EVENTS` ↔ 主服务 `usageEventProps` ↔ 后台 `EVENT_LABELS`） | 阻断合并；不产制品 |
| **P2** | 制品 | 主干 tag / 手动 | 构建三镜像 → 推 ACR（`--provenance=false --sbom=false`）；tag = `YYYYMMDD-HHMM` | 不产制品；告警 |
| **P3** | 发布（CD） | 手动参数（生产**必须有人工审批闸门**） | 改 `.env` → `pull && up -d` → `smoke-ecs.sh` 自检 | **自动切回上一 tag** + 告警 |

> **口径统一**：`save/scp/load` 这条老路**保留为应急手段**（`06:77` 记载首部署时 ECS 尚未 `docker login`），但**日常发布一律走 ACR pull**（`../ai/06:326-333` 已定"ECS 不编译，只 pull"）。避免两条路并存造成口径分裂。

## 7. 边界与风险

| # | 风险 | 处置 |
| --- | --- | --- |
| 1 | **拿生产机做实验** | ⚠️ 线上 ECS 是 `8.159.154.246`（`06:19`）。**P1/P2 全部在本地或靶机跑**；P3 只对靶机练，**确认无误后才考虑对生产开** |
| 2 | **密钥进仓库 / 进日志** | 凭据一律走 Jenkins Credentials / 云效变量组；`Jenkinsfile` 里**不得出现明文**，且用 `withCredentials` 避免回显。延续 `05-密钥与凭据管理` 的口径与 `check-secrets.ps1` 防呆 |
| 3 | **用主账号 AK** | 全程 RAM 子账号 + 最小权限 + 审计（`ActionTrail`）。这本身就是 B4 要学的"凭据治理" |
| 4 | **ACR 个人版限制** | 不认 provenance / SBOM ⇒ 构建必须加 `--provenance=false --sbom=false`（`../ai/06:335-341` 已记） |
| 5 | **AWS 式误以为"上了流水线就有测试"** | A1 排在 A2 之前，**强制顺序**。测试地基不完成不进 A2 |
| 6 | **容器内 `docker.sock` 权限** | Docker Desktop 的 socket 属 root ⇒ compose 需 `user: root`（**仅本地实践**，勿套到生产） |
| 7 | **Windows 路径 / 权限** | 用 Docker agent 时 `jenkins_home` 必须是**宿主 bind mount**（容器内外同路径），否则 workspace 在宿主不可见 ⇒ 挂空目录 |
| 8 | **P3 自动回滚的"回滚也失败"** | 回滚本身可能失败（如镜像已被清理）⇒ P2 保留**至少 N 个历史 tag 不被清理**，且回滚失败时**必须告警到人**（不许静默） |
| 9 | **生产无人审批** | P3 对生产**强制人工审批闸门**；自动回滚是**失败兜底**，不等于可以无人发布 |

## 8. 验收与度量

### 8.1 指标（对齐 DORA）

| 指标 | 现状 | 目标 | 采点 |
| --- | --- | --- | --- |
| 部署频率 | 不定期、人决定 | 可随时发（P3 一次点击） | P3 运行记录 |
| 变更前置时间 | 从提交到上线含人工排期，不可测 | 主干合并 → 可发布制品 ≤ 15 min | P2 结束时间 − 合并时间 |
| 变更失败率 | 未统计（已知至少 3 次事故） | 有统计、且门禁拦截的计入"未到达生产" | P3 失败次数 / 总次数 |
| **MTTR（回滚耗时）** | 人工发现 + 人工改 tag，估计 5~15 min | **≤ 3 min 自动回滚** | P3 自检失败→回滚完成 |

**流水线自身指标**：P1 时长、构建失败率、缓存命中率、排队时长。

### 8.2 Jenkins vs 云效 Flow 对照（收尾时补完）

| 维度 | Jenkins（自建） | 云效 Flow（云平台） |
| --- | --- | --- |
| 初始化成本 | 高（镜像、插件、Agent、权限） | 低（开箱） |
| 私有化 / 网络受限场景 | ✅ 强 | ✗ 依赖云 |
| 与阿里云生态（ACR/RAM/SLS）集成 | 要自己写 | ✅ 原生 |
| 可定制性 / 插件生态 | ✅ 极强 | 受限 |
| 维护成本 | 高（自担升级与稳定性） | 低（托管） |
| 并发与资源弹性 | 自建 Agent，需自己调度 | 托管弹性 |

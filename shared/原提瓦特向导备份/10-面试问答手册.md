## A. 开场与叙事（4 题）

### A1 · 这个项目最难的地方是什么？
**考点**：会不会把"难"说成"工作量大"。他要听的是**判断**。

**答**：不是写功能，是**让模型说的话可控**。功能层面加个接口就有，但模型会编——我们真出过一条：它按"月感电"的对称性造了个「月超导」，还说得出哪个角色走这一挂。
后来我没加"不许编造"这种话（没用），而是把攻略长文拆成**结构化机制卡**（120 张、3000+ 条事实、每条带原文出处），提示词只允许"从数据块里推出结论"。这才是根治。

**追问**：怎么验证有效？→ 机制评测 30/30；且错误类型被分桶（知识缺口 / 推理幻觉 / 规则冲突），只有第一类才值得补数据。

**陷阱**：别答"并发高、数据量大"——这项目没有那个量级，一问就露。

### A2 · 你一个人做完了哪些？哪些不是你做的？
**考点**：诚信 + 边界感。

**答**：需求、架构、数据建模、前后端、AI 侧、部署、备案是我做的；具体文案与部分语料是模型+人工抽取的（我定抽取规则与校验）；**没做的**也说清楚：CI/CD 还是手工、前端零测试、向量 RAG 只有设计没实现。

**陷阱**：含糊其辞最致命。面试官一旦发现你在"打包"，后面所有数字都会被怀疑。

### A3 · 为什么选这个方向？有用户吗？
**答**：自己玩，发现通用大模型答原神问题时"看着对、细看错"（数值、配队、版本时效都不准），而精细数据在游戏公开数据里能拿到。用户量我**没有可信数据**（埋点刚上线），这也是我下一步要补的。

**加分**：主动说"我不拿用户数当卖点，我拿工程约束当卖点"。

### A4 · 如果让你给非技术的人介绍，怎么说？
**答**：一个"看得懂你账号的 AI 助手"——你把游戏 ID 绑上，它就知道你有哪些角色、圣遗物什么水平，然后告诉你先练谁、这件要不要留。

## B. 架构与选型（6 题）

### B1 · 为什么拆成三个服务，不做一个单体？
**考点**：拆分动机是不是"为了简历好看"。

**答**：拆的是**权限边界**，不是性能。AI 服务拿不到数据库、拿不到用户 Token，只接受主服务预渲染好的上下文——这样即使模型被注入，它能触碰的东西也只有一段文本。单体做不到这个隔离。
代价是链路变长、要维护契约（`/v1/complete` 的信封与错误码），所以我把它写成了契约文档，改字段必须同步。

**追问**：那为什么后台是另一个仓？→ 后台读写业务库，但**只读影子实体**、写操作走 Server Actions + 网关注入凭证，跟 C 端不是一套鉴权。

**陷阱**：别说"为了微服务架构"——这是三进程，没有服务发现、没有网关治理。

### B2 · AI 服务为什么必须无状态？具体约束是什么？
**答**：三条硬约束：**不建用户体系、不写 `chat_*`、不直连 MySQL**。会话持久化、配额、鉴权全在主服务。
好处是重启零影响、可水平扩容、出问题不影响数据；代价是每次都得把上下文整理好传过去，主服务侧要控制 token 预算。

**追问**：那 AI 服务怎么知道用户是谁？→ 不需要知道。它只看到 `context.player / goal / summary`，没有 userID 语义。

### B3 · 为什么不用 LangGraph / 不给模型工具？
**答**：工具是**能力质变**——能调工具就能被诱导调工具，注入面从"一段文本"变成"一双手"。我现在的能力靠"把数据整理好再问它"，而不是"让它自己去查"。
LangChain 只用 core + openai 适配层，编排逻辑在我自己代码里，出问题能一眼看到。

**追问**：那未来要检索怎么办？→ 在主服务做检索，把结果作为上下文注入，模型侧依然零工具（`ai/09` 的长期红线）。

### B4 · 为什么不用微服务 / K8s / Redis / MQ？
**答**：当前是单机三容器、单库，量级远没到。**加一个组件就要多一份值班成本**：Redis 要处理一致性、MQ 要处理重复消费、K8s 要处理调度与网络——收益却是我现在用 60 秒缓存 + singleflight 就能拿到的。
我的判断标准是：**当"进程边界"能解决问题时，就不引入网络边界**。

### B5 · admin 为什么不直接连库改数据？
**答**：后台是独立 Next.js 应用，用 TypeORM 连业务库但 `synchronize: false`、只映射**影子实体**（读为主），写操作一律走 Server Actions + 主服务接口。
理由是**职责与留痕**：业务规则（校验、事务、审计）只在主服务里，后台绕过去就等于有两套写入路径，早晚不一致。

### B6 · 为什么禁止 service 层引用 `gin.Context`？
**答**：`gin.Context` 把 HTTP 细节（Header、状态码、请求体）带进业务层，导致业务无法脱离框架测试、也无法被别的入口（定时任务、CLI）复用。
我的分层是 `router → handler → service → repository → model`，单向依赖；service 只接收普通结构体，返回 `(result, error)`。

**加分**：这条在真实项目里的价值是——后来加"定时任务批量导入"时，直接复用 service，没有复制粘贴。

## C. AI 应用工程（10 题，AI 岗重点）

### C1 · 怎么防模型编造？
**考点**：这是 AI 应用岗的分水岭。答"加一句别编造"= 不及格。

**答**：四层，**没有一层是靠"求它别编"**：
1. **数据侧**：把结论式攻略换成**可组合事实**（`provides/shreds/cannot/needs/scaling/conflicts`），每条带原文出处；
2. **提示词侧**：只允许"结论必须能从 facts 推出"，反应名/机制名**只照数据块写**，不许按名字对称性拼；
3. **产品侧**：**不专门强调"没有 XX 这种东西"**——越强调越把错名词种进用户脑子里，直接用正确名字回答即可；
4. **回归侧**：机制评测 30 条，答案全部来自原文。

**追问**：那用户用错名字问怎么办？→ 用正确名字回答，但不纠正他的叫法（`triggers` 里保留错别名，保证能命中）。

### C2 · 提示词怎么管理？为什么不用 git？
**答**：`ai_prompts` 表，`scene_key + version + enabled`，内容不可变，**生效 = 最高启用版本，回滚 = 置 0**，内存 TTL 60 秒热生效。
理由是**频率**：人格与规则迭代了 21 版，走代码发布每次都要构建、发版、回滚，太慢；而且产品同学改文案不该碰代码。
代价是必须解决"库里没有时用什么"——所以代码里保留默认值，库不可用时回退文件模式并告警。

**追问**：怎么防止改坏？→ 改前跑评测基线 JSON，改后同口径对比（目前靠人看，`check_gate.py` 还没写，这是已知短板）。

### C3 · 上下文是怎么组装的？token 怎么控？
**答**：动态区有硬预算：玩家档案 **1500**、资产资料 **800 且最多 2 个角色**、历史 **20 条 + 1200**。
超预算的处理是**整条丢弃**（从尾部丢角色），并显式写"其余 N 个角色已省略"——**不给半个角色**，因为半个角色的面板会让模型自行补全数值，那比不提供更危险。
另外点名角色会被置顶；用户问的是哪个角色，就先展开哪个。

**追问**：怎么知道预算准不准？→ 用 token 计数实测，12 位满配上下文实测 5932 tokens。

### C4 · 提示词前缀缓存是什么？你怎么利用？
**答**：DeepSeek 对**相同前缀**有 KV 缓存，命中部分按更低价计费、且首字更快。所以我把 prompt 排成"稳定 → 易变"：`base`（身份）→ `rules`（规则）→ `fewshot`（示例）→ `request_system` → 动态段（玩家档案/资产）。
只要前面不动，每次请求都能吃到缓存。实测一轮 778 tokens 里**缓存命中 512**。

**陷阱**：别把它说成"我实现了缓存"——这是**供应商能力**，我做的是**排序**让它命中。

### C5 · 怎么评估"改了 prompt 有没有变差"？
**答**：50 条评测集（20 条解释类 ＋ 30 条机制类），跑之前存基线 JSON，改完同口径再跑，对比平均字数、过短条数、拒答条数、以及"不得出现『没有这个角色』"。
通过线是人定的、写死的：平均 ≥350 字、≤150 字 ≤2 条、拒答 ≤2 条、否认角色存在 **0 次（一票否决）**。
**诚实的部分**：目前是人工看报告，`check_gate.py` 断言还没写，所以它还不是"门"，只是"参照"。

### C6 · 资料里没有的问题，模型该怎么答？
**答**：分两种：
- **真的没有**（新角色、冷门玩法）→ 明说"本服暂无该角色的资料"，**不用常识补**；
- **有料但规则堵嘴**（曾经出现过：攻略卡有推荐武器，规则却让答"不清楚"）→ 这是**规则 bug**，改规则而不是改模型。

这条分桶很重要：**知识缺口可以补数据，规则冲突只能改规则**；把它们混在一起，就会不停往库里塞垃圾。

### C7 · 为什么把攻略长文改成结构化机制卡？
**答**：长文让模型只会"照背结论"——问"班尼特能进魈队吗"，它只能找到一句现成答案，找不到就编。
改成 facts 后，模型可以推理：班尼特提供攻击力加成 → 魈是攻击力倍率输出 → 适配；希诺宁不能减风抗 → 风系主队不适合。**结论可推导，而且能逐条追溯原文**。
代价是抽取成本（120 张卡、3000+ 条事实）和质量控制（"结论必须能被原文支撑"）。

### C8 · 流式输出还要不要做输出守门？
**答**：要，但成本不同。流式下你无法"先审完再发"，只能在流中做增量检测（命中越界特征就切断并发固定话术）。
我目前的现状是：**输入侧很强、输出侧还没有**（L3 未做）。这也是我知道的风险点——现在的防线是"输入已经拦掉大部分"。

### C9 · 为什么分四档模型参数？
**答**：四档：`chat`（temp 0.85 / 1024，闲聊与解释）、`analysis`（thinking high / 4096，账号分析要长推理）、`tool`（0.2 / 2048，结构化调用）、`json`（0.1 / 2048，要确定性输出）。
分档是为了**不让所有请求都付最高成本**：闲聊不需要 4096 token 和高温思考。

### C10 · 上游超时/失败怎么处理？
**答**：上游 **55s、重试 ≤1 次**；主服务超时必须 **65s**（必须大于 55s，否则上游还在跑你已经判死了）；**禁止"长超时 + 多次重试"叠加**——那会把一次慢请求放大成三次；4xx 不重试。
流式场景特殊：已经吐字之后再失败，只能发 `error` 帧，**不能假装正常结束**。

## D. 后端深度（8 题，后端岗重点）

### D1 · SSE 在 Go 里怎么透传？为什么不封统一信封？
**答**：主服务收到前端请求后调 AI 服务的流式接口，**边读边转发**，帧类型固定四类：`session → delta* → (done|error)`，`done` 带 `sessionId/tokens/elapsedMs`。
不封信封是因为：普通 JSON 接口需要信封（code/data/message）表达"整体成功/失败"，而 SSE 的**每一帧本身就是一个事件**，再包一层既增加解析成本，又会让"流中断"和"业务失败"混在一起。错误仍然用 `error` 帧，语义与 HTTP 错误码对齐。
工程上还有一个坑：**Nginx 必须关 `proxy_buffering`**，否则缓冲区会把流攒成一次性输出，看起来像"没流式"。

**追问**：为什么不用 WebSocket？→ 这里是单向推送，SSE 走普通 HTTP、过代理更简单；双向需求（协作、输入中提示）才值得上 WS。

### D2 · 配额与限流怎么设计的？
**答**：三层，且都在主服务强制（AI 侧只管并发信号量）：
- 用户维度：日 **100 万 tokens**、并发 **≤2**；
- 全站维度：每分钟 **20 次**、日预算（默认关）；
- 超限统一 **429**，带 `reason=daily|concurrent|global` 让前端能给出不同提示。

细节：**软上限**（超了拒绝新请求但不中断已开始的），按 **UTC+8 自然日滚动**，**没有定时任务**——读时按窗口聚合，避免"依赖定时器才能重置"的脆弱设计。
**检查发生在建会话之前**，否则会留下一堆空会话。

**追问**：为什么并发是 2？→ AI 侧上游并发是 32，单用户 2 是防止一个人占满；这是资源公平性，不是技术限制。

### D3 · 缓存为什么是 60 秒 + 5 分钟负缓存 + singleflight？
**答**：数据源是第三方公开接口，有频率限制：
- **60s 正缓存**：与上游刷新节奏对齐，再短没意义；
- **5min 负缓存**：不存在的 UID 也缓存，否则扫号能把上游打穿；
- **singleflight**：同一 UID 并发请求合并成一次，避免缓存击穿。

**追问**：为什么不用 Redis？→ 单实例，进程内足够；扩多实例时这会变成必须改的点（缓存不一致 + singleflight 失效）。

### D4 · 快照 TTL 10 分钟，为什么发版还要手动清？
**答**：快照存的是**整份档案 JSON**。给 DTO 加了新字段后，旧快照里没有这个字段——不清理的话用户看到的永远是"新功能没生效"。
所以发布清单里有一条 `POST /api/admin/assets/reload?purgeSnapshots=true`。这是**结构性变更的必要运维动作**，不是缓存 bug。
教训是：**加字段必须连带清理策略**，否则"代码上线了但功能没生效"这种问题极难排查。

### D5 · 累积角色池为什么"只增不删"？
**答**：游戏展柜一次只能放有限角色，用户会轮换。如果按"当前展柜"覆盖，用户之前展示过的角色就永久丢失。
所以设计成：每轮 `upsert` 本轮角色、`first_seen_at` 不覆盖、不在本轮展柜的只把 `in_showcase` 置 false、**永不 DELETE**。
另外两条边界：**只有查询"自己绑定的 UID"时才累积**（防止替别人存数据、防刷表）；与档案快照**刻意分表**——清缓存不该清用户资产。

**加分**：面板上会给移出展柜的角色标"数据截至 X"，因为它的数据确实不会再刷新。**能承认"这份数据可能过时"，比假装新鲜更重要。**

### D6 · 重复采集怎么保证幂等？
**答**：靠唯一键 + upsert：`player_characters` 用 `(uid, character_id)` 联合主键；期次/卡池类用 `(kind, period_key)`。重复跑不产生新行。
测试里专门覆盖了四个面：换展柜不丢、同角色会刷新、重复采集幂等、换回来能复活标记。

### D7 · 25 张表怎么分的？
**答**：按职责分六组：用户与会话（users / sessions / messages / preset_qa）、资产映射（characters / weapons / relics / affixes / text_map…）、内容资料（攻略卡 / 机制卡 / 全局规则 / 权重表）、玩家数据（快照 / 累积角色池）、观测（events / usage_daily / feedbacks）、治理（invite_codes / prompts）。
原则是**按生命周期分表**：会过期的（快照）和不该被清的（用户角色池）绝不放一张表。

### D8 · 用 AutoMigrate 有什么风险？
**答**：三个：① 没有版本化，改不回去；② 只会加不会删，字段废弃了还得手工处理；③ 多实例同时启动可能有竞争。
我现在的约束是**只做加法**（加表加列加索引），破坏性变更手工执行并写进运维文档；正式项目应该上 `golang-migrate`，这条我已经明确记在路线图里，属于**已知短板**。

## E. 数据与算法（4 题）

### E1 · 圣遗物评分怎么算？为什么有多个口径？
**答**：三口径并存：
- **miao 口径**：社区通用，单件满分 66，分档 D/C/B/A/S/SS/SSS/ACE/MAX，玩家看得懂、能对上攻略；
- **归一化口径**：自算 0~100，便于排序和展示进度；
- **双暴分**：`暴击×2 + 暴伤`，快速筛选用。
角色加权是 **121 角色 × 10 维权重（0~100）**，外加 9 条覆盖规则处理特例。默认展示归一化，miao 分作参考。

**追问**：权重哪来的？→ 社区开源权重表（MIT）+ 覆盖规则，种子 96.6 KB，导入后有 14 条测试。

### E2 · 怎么证明你的重构没改变结果？
**答**：行为等价验收——重构前后对**同一批角色逐件输出分数、档位、总分**做全量比对，要求 **12/12 完全一致**。
一次数据清洗动过 122 个角色的白值词条（补 54 行、规整 86 行、删 5 行），前后**分数零变化**才算过。这条比"代码看起来没问题"可靠得多。

### E3 · 数据缺失怎么处理？
**答**：这里踩过坑：渲染攻略卡时对空段是 `if text == "" { continue }`——**静默跳过**。结果模型看不到"这里没资料"，就凭记忆补，比明确说"没有"更危险。
正确做法是**显式注入"本服暂无该角色的 XX 资料"**。我把它记成了 TODO（配合能力校验 `CanAnswer`，先判断答不答得出，再决定推不推荐这个问题）。

### E4 · 如果模型和资料冲突，听谁的？
**答**：听资料，且**不解释"资料和你说的不一样"**——那会把用户的错误说法带进回答。直接用正确名字说结论即可。
但有个前提：资料必须带日期与来源，否则"过期资料"比"没有资料"更危险（这正是我给每张卡标来源+日期的原因）。

## F. 前端（5 题）

### F1 · 前端怎么做流式渲染？
**答**：乐观更新——用户一发送就先插一条 `pending` 占位，然后用 `fetch` + `ReadableStream` 逐行解析 SSE（**axios 拿不到浏览器流**，这点踩过），按 `session → delta* → done` 追加内容。
关键细节：**中断时保留已产出的内容**，不清空；`done` 帧带 `tokens/elapsedMs`，直接用于埋点。

### F2 · 前端体积怎么控？
**答**：目前 441.71 kB / gzip 143.66 kB，每次发版记录变化。
手段是：按需引入图标（lucide 可 tree-shake）、不自建大依赖、i18n 用普通对象不走大库。
**短板**：还没做路由级 code splitting——首屏把所有页面都打进去了，这是下一步最直接的优化点。

### F3 · 移动端踩过哪些坑？
**答**：四个：
1. `100vh` 在 iOS 地址栏收起时跳动 → 换 `h-dvh`；
2. 底部输入框被 Home 指示条盖住 → `env(safe-area-inset-bottom)`；
3. 输入框字号 <16px 会触发 iOS 自动放大 → 强制 `text-base sm:text-sm`；
4. 抽屉放在带 `backdrop-blur/transform` 的祖先里，`fixed` 定位会失效 → 抽屉必须挂在根节点。
另外导航抽成**唯一数据源** `navItems.ts`，桌面侧栏和移动抽屉共用，避免"加了个页面只有桌面能看到"。

### F4 · i18n 怎么做的？
**答**：自研，`zh-CN.ts` 是基准，`t()` 的 key 是**编译期穷举的字面量联合类型**——少写一个 key 直接构建失败。
好处是把"漏翻译"从运行时问题变成编译期问题；代价是动态拼 key 不行（曾踩过 `t(\`home.roadmap.${key}.title\`)` 直接类型报错）。

### F5 · 前端有多少测试？
**答**：**目前是零**，只有 lint + build 作为提交前门禁。这是明确的短板，计划接 vitest + testing-library，先覆盖纯逻辑（埋点上报、分析状态机、格式化函数），再做组件冒烟，最后进 preflight 全档。
我不想说"有测试"然后被要求现场打开。

## G. 运维 / 上线 / 安全合规（6 题）

### G1 · 上线流程是什么？怎么回滚？
**答**：`release.ps1 -Service server|web`：本地构建 → `docker save` → scp → 远端 `docker load` → 改 `.env` 的镜像 tag → `up -d --no-build` → 自检。
镜像 tag 是 `YYYYMMDD-HHMM`，每次发版前备份 `.env.bak-<tag>`，回滚就是把它拷回来再 `up -d`。
发版后跑 smoke 脚本（首跑 6/6 通过）+ 关键接口断言（固定 UID 的面板行数、某个角色的圣遗物分数）。

**陷阱**：别说"自动化发布"——现在是手工的，CI/CD 只有方案。

### G2 · 为什么 Nginx 必须关 `proxy_buffering`？
**答**：默认 Nginx 会把上游响应攒进缓冲区再发给客户端。对普通 JSON 没影响，但 SSE 会被攒成"最后一次性吐出来"——用户看到的是转圈几秒然后整段出现，**流式白做**。
同时要放宽 `proxy_read_timeout`（我配 120s），否则长回答会在网关层被切断。

### G3 · 密钥怎么管？
**答**：四类相互独立：用户 JWT、资产后台 `admin_key`、内网 `internal_key`、AI 服务 `X-AI-Key`。全部走环境变量注入，不入仓、日志不打印；`.env` 在服务器上单独权限管理，轮换流程写在文档里。
网关层直接把 `/api/admin/` 和 `/internal/` 打成 404——**内部接口不暴露在公网**，减少一层风险。
另外 `preflight` 里有一步**密钥扫描**，防止误提交。

### G4 · 防注入做了什么？
**答**：分层，重点在"能不调模型就不调"：
- **L0 架构**：模型无工具、服务无外网；
- **L1 输入侧**：昵称白名单字符 + 16 字上限，NFKC 归一 + 去掉零宽/双向控制符（这类字符能藏指令），命中注入短语一票否决；
- **L2 事前短路**：命中特征**直接固定话术返回，`tokens=0`、`model=guard`** —— 既安全又省钱；
- **L5 观测**：分类器采样打标（`NULL` 表示未判定 ≠ 安全）+ 红队集，33 例回归里 10 例是"不许误伤"。
**没做的**：L3 输出守门、L4 处置闭环——我知道这是缺口。

### G5 · 备案与合规怎么做的？
**答**：域名在国内注册商买（否则不能备案）→ 提交 ICP → 通过后 30 日内做公安联网备案 → HTTPS 用 certbot 自动续期。
AI 侧还有两件事：**用户须知版本化强制确认**（`users.terms_version` 落库，改条款要重新确认）、**每条 AI 回答带生成内容标识**。
调用已备案模型的应用属于**登记**（不是备案），这块我还在推进，不宣称完成。
另外三处默认关收录：`robots.txt`、`robots` meta、Nginx `X-Robots-Tag`。

### G6 · 线上出问题怎么定位？
**答**：四样东西：结构化 JSON 日志（带请求 id）、5 条告警规则（提示词回退、存储失败、5xx 突增、上游 5xx 比例、缓存退化；窗口 300s / 冷却 1800s，走日志 + webhook + `/metrics`）、`docker logs` 实时看、以及发版 golden 断言做"是不是这次改动"的判定。
**短板**：没有接 APM / 链路追踪，跨服务定位还靠日志串。

## H. 质量与工程习惯（3 题）

### H1 · 你的门禁脚本都查什么？
**答**：一条 `preflight.ps1`：`gofmt -l` / `go vet` / `go test` / 前端 `tsc` + `eslint` + `build` / 种子 JSON 校验 / **密钥扫描** / 格式检查 / **跨层契约比对**（前端事件字典 ↔ 主服务白名单 ↔ 后台标签表）。
分快档（提交前）和全档（发版前）。它的由来很具体：有一天连续三次"新改动伤到旧功能"——词条同名让面板少一行、残留枚举行让冰伤显示 0.0%、CRLF 让远端脚本报错。**每次都是"改 A 坏 B"，靠人眼根本盯不住。**

### H2 · 测试策略是什么？
**答**：优先测**纯逻辑与不变式**：评分算法 14 条、昵称清洗 16 例、guard 33 例、注册短信 19 条、反馈 5 条、历史 5 例。
排序原则是"出错代价高 + 不需要起服务"。Go 侧 60+ 条、Python 85 条。
**没做的**：前端零测试、没有覆盖率统计、没有集成测试——都写进路线图了。

### H3 · 48 份文档是不是过度设计？
**答**：不是为了好看，是因为**四个仓 + 一个 AI 服务，契约不写下来一定会漂**。实际收益有三条：
① 接口契约（信封、错误码、SSE 帧）写在文档里，改字段前先看冲突；
② 每份改动都带"为什么这么定 + 代价"，三个月后自己还能想起来；
③ 文档仓用 Junction 挂到四个仓，改一处四处生效，避免副本腐化。

**代价**：写文档确实占时间，所以我的原则是"**只写会变的东西**"——代码能表达的不写。

## I. 反思与压力题（5 题，必考）

### I1 · 如果重做，你会改什么？
**答**：三件，按顺序：
1. **先接 CI**（现在全手工，最容易出错也最无聊）；
2. **数据层先做"期次"抽象**（每期卡池/深渊数据现在没有表，靠人工，这是我最近补的设计）；
3. **评测门提前**——`check_gate.py` 应该在第一版 prompt 就存在，而不是迭代 21 版之后才补。

### I2 · 这个项目最大的短板是什么？
**答**：**没有真实用户反馈闭环**。埋点刚上线，失败样本还躺在库里没人捞；而产品最需要的恰恰是"用户到底在哪一句放弃了"。
技术上第二短板是前端没测试、CI 没接。

**加分**：说完补一句"所以我下一步先做失败样本回流，而不是继续加功能"——体现优先级判断。

### I3 · 没有用户量，你怎么证明它有用？
**答**：不靠用户数，靠**可验证的断言**：
- 机制评测 30/30，答案是原文；
- 圣遗物评分重构前后 12/12 分数零变化；
- 12 位满配角色的上下文能被模型正确引用（实测 5932 tokens 内）；
- 关键接口有 golden 断言（固定 UID 的面板行数、某角色分数）。
这些比"日活多少"更能说明系统是不是真的在工作。当然，长期还得看真实留存。

### I4 · 明天上线一个新需求，你能保证不出事吗？
**答**：不能保证"不出事"，但能保证**出事能定位、能回滚**：
- 发版前跑全档门禁 + 评测对比；
- 镜像 tag 固定、`.env` 有备份，回滚 1 分钟；
- 发版后跑 smoke + golden 断言，失败就切回上一 tag；
- 结构性变更（加字段）会同步清快照，否则会出现"上线了但没生效"。

### I5 · 这个项目让你学到最重要的一件事？
**答**：**"约束"比"能力"值钱**。给模型加工具很容易，难的是让它**不越界**；加功能很容易，难的是让 25 张表、36 个接口在半年后还能改得动。
所以我现在做设计的第一个问题不是"能做什么"，而是"**出错时它会怎么坏、我怎么知道、怎么退回去**"。

## J. 被问住时怎么办（三条应急）

1. **不知道就说不清边界**："这块我没做过，我的理解是……（讲思路）…… 不确定的地方在于……" —— 比硬编好；
2. **把问题拉回你熟的相邻领域**："这个我没直接做，但类似的问题我在 X 上处理过，思路是……"；
3. **主动给验证方式**："如果要验证，我会先……再……"，面试官要的是**方法论**，不是标准答案。

## 1. 三类角色与信任域

| 角色 | 归属服务器 | 鉴权 | 数据 |
| --- | --- | --- | --- |
| **C 端用户**（原神玩家） | web 服务器（teyvat-guide `:8080`） | 用户 JWT（`Authorization: Bearer`） | `teyvat_guide` 库：users / chat_* / UID 绑定 |
| **后台管理员**（运维人员） | 运维/后台系统（demo-app） | Session/Cookie（`admin_session`） | `teyvat_admin` 库：users（permission_level=0） |
| **服务间调用** | —— | `X-Admin-Key`（管理动作）/ `X-Internal-Key`（内网只读管理）/ `X-AI-Key`（主服务↔AI 服务） | —— |

**结论**：C 端登录由 **web 服务器**唯一负责；后台管理员登录由 **后台系统**独立负责；AI 服务器**不参与任何登录**（规格禁止）。

> 三类鉴权密钥**必须各自独立**，禁止复用。

## 2. 为什么用户中心不放后台

- C 端登录要暴露给公网前端（web 承载），后台不面向 C 端用户；
- 用户身份/会话/UID 绑定/聊天记录都贴着 `teyvat_guide` 库，用户中心内聚在此；
- 后台当用户中心会引入额外故障链路，违背业务/运维解耦；
- AI 服务无状态，不得持有用户数据。

## 2.5 手机号注册（2026-09-27 上线 ✓）

**注册 = 手机号 + 短信验证码 + 设置密码**；注册成功后自动登录，**账号名就是手机号** ⇒ 登录链路零改动 ✓。

| 项 | 口径 |
| --- | --- |
| 接口 | `GET /api/auth/config`（入口可用性，公开）/ `POST /api/auth/sms/send`（发码，公开）/ `POST /api/auth/register`（注册，公开）⇒ 契约见 `web/04` §3 |
| 验证码 | 由**阿里云 Dypnsapi**（`SendSmsVerifyCode` + `CheckSmsVerifyCode`）生成与校验 ⇒ **我们不落库验证码** ✓（自带有效期 5 分钟 + 一次性 ✓）|
| 限速（我们的） | 同号 **60s** 间隔 / 同号每日 **10** 次 / 同 IP 每小时 **20** 次 —— 进程内滑窗（本项目**没有 Redis** ✗），口径同 `quota` ✓；阿里云侧 `Interval` 再拦一道 ✓ |
| 成本闸门 | `auth.allow_register=false` 时**连验证码都不发**（403 ✓）—— 否则"不公开部署"仍会被刷短信费 ✗ |
| 开关 | `sms.enabled` **默认 false**（没配好绝不误发短信 ✗）；`sms.mock=true` 只把验证码打日志（仅本地/联调 ✓）|
| 前端 | 入口由 `/api/auth/config` 决定，**不硬编码** ✗（否则会出现"点了才发现 403"的死按钮 ✗）|
| 隐私 | 日志与默认昵称一律**脱敏**（`138****5678` ✓）；手机号列可空（后台代建账号为 `NULL` ✓，指针类型 ⇒ 多个 NULL 不撞唯一索引 ✓）|
| 顺序 | **先验码、再查重**：反过来的话"某号是否已注册"就成了不需持码即可探测的信息 ✗ |
| **邀请码**（第二道门，2026-09-28 已实现 ✓） | 表 `invite_codes`（`code` 主键 / `enabled` 可停用 / `used_at`+`used_by`+`used_phone` 留痕 ✓）。口径：**不填不发短信** ✓、**填错也不发** ✓（发码前先验码 ✓，错的码连短信都不发、不产生费用 ✓）；**一次性** —— 在**注册事务**里原子占用 ✓（`UPDATE … WHERE used_at IS NULL` + 建号同一事务 ⇒ 并发不会两号共用一个码 ✓，且**注册失败（短信码错/手机号重复）不会把码烧掉** ✓✓）。开关 `auth.require_invite_code`（默认 false ⇔ 行为不变 ✓），前端按 `/api/auth/config` 的 `requireInviteCode` 决定是否显示该栏 ✓（**不硬编码** ✗）。码由内网接口管理：`GET/POST /internal/v1/admin/invite-codes` + `PUT /internal/v1/admin/invite-codes/:code`（生成/列表/停用 ✓，停用=收回但**不删行**留痕 ✓）|

> ⚠️ 部署提醒：本项目 compose 用 **environment 白名单**（不是 `env_file` ✗）—— 新增 `TEYVAT_*`
> 必须同时写进 `docker-compose.yml`，只写宿主机 `.env` 容器里看不到 ✗（2026-09-27 踩到 ✓）。

> —— 实测**容器内**能直接取到实例元数据的 STS 临时凭据 ✓（`AccessKeyId: STS.NZ***`、SecurityToken 644B ✓），
> 于是 `.env` 里 AK 保持留空即走凭据链 ✓（密钥不进环境变量、不进仓库 ✓）。`sms.mock=false` +

## 3. 后台"管理用户"的方式：内网管理接口（方案 A）

```
浏览器 → 后台 Server Action →（服务端直连，X-Internal-Key）→ web 服务器 /internal/v1/admin/*
```

- 内网接口**只对内网开放**，浏览器与公网都接触不到；
- 密钥 `PROJECT_TEYVAT_GUIDE_INTERNAL_KEY` 只存后台服务端；
- 封禁等写操作在 web 服务器侧执行（可联动会话失效）。

**为什么不对用户用"直连数据库"**：用户是核心实体、写操作带业务规则（封禁需踢会话），直连会绕过校验；直连仅适用于**低风险、读多写少**的资产映射（见 `02`）。

## 4. web 服务器接口契约（teyvat-guide，已实现）

统一信封 `{code, message, data}`，`code === 0` 为成功；鉴权请求头 `X-Internal-Key`；仅内网可达。
`auth.internal_key` 未配置时**该组路由不注册**（安全默认）；请求头缺失/错误一律 401。

### 4.1 用户列表

`GET /internal/v1/admin/users?keyword=&page=1&pageSize=20`

用量与无关问题筛选（**2026-09-14 新增并已实现**）：
`GET /internal/v1/admin/users?usageDate=2026-09-14&minDailyTokens=50000&onlyOffTopic=true&offTopicMin=1`

```json
{
  "code": 0, "message": "ok",
  "data": {
    "items": [
      {
        "id": 1, "username": "traveler", "displayName": "旅行者",
        "genshinUid": "100000001", "status": "active",
        "createdAt": "2026-09-01T10:00:00+08:00",
        "lastLoginAt": "2026-09-10T20:00:00+08:00",
        "totalTokens": 123456,
        "todayTokens": 52310, "todayInput": 21030, "todayOutput": 31280,
        "todayCached": 40210, "todayRequests": 18,
        "offTopicCount": 3
      }
    ],
    "total": 42, "page": 1, "pageSize": 20
  }
}
```

- `status`：`active` / `banned`；`genshinUid` / `lastLoginAt` 可为 `null`；
- `keyword` 匹配 用户名 / 昵称 / 游戏 UID；
- `totalTokens`：该用户**累计**消耗（web 服务器落 `chat_*` 聚合）。

**新增入参**（设计见 `05-AI使用边界设计（匿名·配额·内容治理）.md` §2.5 / §3.4）：

| 参数 | 说明 |
| --- | --- |
| `usageDate` | 当日用量统计的日期（`YYYY-MM-DD`，缺省 = 今天，**本地时区**） |
| `minDailyTokens` | 只返回 `usageDate` 当天消耗 ≥ 该值的用户（`50000` = **5 万观察线**） |
| `onlyOffTopic` | `true` 时只返回**有无关提问**的用户 |
| `offTopicMin` | 无关提问数 ≥ N（与 `onlyOffTopic` 同时传则取交集） |

**新增字段**：

| 字段 | 说明 |
| --- | --- |
| `todayTokens` / `todayInput` / `todayOutput` / `todayCached` | `usageDate` 当天用量（按 `chat_messages` 聚合；`cached` 单独给，便于按 ~50 倍差价折算成本） |
| `todayRequests` | 当天请求条数（assistant 消息数） |
| `offTopicCount` | **累计**无关提问数（`role='user' AND off_topic=1`）；判定未开启时为 0 |

> 组合用法：`minDailyTokens=50000&onlyOffTopic=true` = 「今日用量高**且**问无关问题」的名单——后台用户管理页的 M3-d。

### 4.2 封禁 / 解封

`POST /internal/v1/admin/users/status`

```json
{ "id": 1, "banned": true }
```

→ `{ "code": 0, "message": "ok", "data": null }`

- 服务端需在封禁时使该用户既有会话/JWT 失效；
- 幂等：重复设置同一状态不报错。

### 4.3 错误码

| code | HTTP | 含义 |
| --- | --- | --- |
| 0 | 200 | 成功 |
| 401 | 401 | 缺少/错误的 `X-Internal-Key` |
| 404 | 404 | 用户不存在 |
| 400 | 400 | 参数错误 |

### 4.4 新建用户（邀请制下的唯一开户入口，2026-09-15 新增）

`POST /internal/v1/admin/users`

```json
// 请求
{ "username": "traveler", "password": "至少 6 位", "displayName": "可选，缺省与用户名相同" }
// 响应 data
{ "id": 7, "username": "traveler", "displayName": "旅行者", "createdAt": "2026-09-15T02:15:21+08:00" }
```

**为什么需要它**：本项目当前是**不公开 / 邀请制**部署——主服务 `auth.allow_register=false` 时
`POST /api/auth/register` 一律 **403**（`本站为不公开邀请制，已关闭注册；请联系管理员开通账号`），
于是"账号从哪来"的答案就是这里：**后台「用户管理 → 新增用户」代建，再把用户名与密码转达受邀用户**。

| 要点 | 说明 |
| --- | --- |
| 校验 | 与公开注册**共用同一套规则与实现**（`service.createUserWithPassword`）：用户名 3~32 字符、去首尾空白、唯一性检查、bcrypt 哈希；`displayName` 缺省 = 用户名 |
| 错误码 | **400** 参数不合法（`账号参数不合法：用户名长度需为 3~32 个字符`）/ **409** 用户名已存在 / **404**（其它接口） |
| 与开关的关系 | **不受 `auth.allow_register` 影响**——关掉的是"自己注册"，不是"管理员开号"（否则邀请制部署没法开户） |
| 不回传密码 | 密码由管理员在弹窗里设定；接口不回传明文，也不生成随机密码 |
| 不做 | 不做邮件/短信邀请、不做一次性邀请链接、不做批量导入（要再做） |

> **红线**：邀请制的关键在于**关掉公开注册入口**，而不只是"在 C 端隐藏注册按钮"——隐藏 UI 挡不住直接调
> `POST /api/auth/register`。两者要一起做（前端去入口 + 后端拒注册）。

## 7. 安全基线

- 内网接口**不暴露公网**，仅内网可达；
- `X-Internal-Key` 独立生成，禁止复用用户 JWT / `X-Admin-Key` / `X-AI-Key`；
- 后台管理员账号与 C 端账号**不同表、不同鉴权**，后台不可用 C 端账号登录；
- 封禁等写操作在 web 侧执行并联动会话失效；
- **AI 对话仅登录用户可用**（2026-09-14）：`/api/chat` 强制 JWT，未登录 401；匿名只能看预设问答（`GET /api/preset-qa`）——避免无归属、不可审计的额度消耗；`/api/genshin/*` 只读接口保持匿名可用；
- **额度与并发在主服务侧强制**（2026-09-14）：每用户每自然日 token 配额（`quota.daily_tokens_per_user`）+ 单用户同时进行中的请求 ≤2，另留全局日预算熔断；密钥/配额口径都不放在 AI 服务侧（它只认 `X-AI-Key` 一把钥匙，无法区分用户）；
- **不公开部署关闭公开注册**（2026-09-15）：`auth.allow_register=false` → `POST /api/auth/register` 一律 **403**，账号只能由后台经内网接口代建（§4.4）；前端登录页同时只留登录入口 + 邀请制说明。**"谁能开号"是一个独立的权限面**——不能只靠在 C 端隐藏注册按钮（那样可被直接调接口绕过）。

> 以上两条的口径真源、契约与验收见 `05-AI使用边界设计（匿名·配额·内容治理）.md`（§1 匿名策略、§2 用量配额）。

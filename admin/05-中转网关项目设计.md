# 05 · 中转网关项目设计

> 状态：设计已评审，**暂缓（未启动）** —— 启动触发条件见 §2.1（2026-09-12 结论）
> 前置阅读：`01-多项目管理平台总体设计.md`、`03-AI派蒙服务运维接入.md`、`04-用户体系与鉴权边界设计.md`
> 一句话：把散落在后台里的「访问业务项目」的能力（转发、鉴权注入、响应归一化、通知重试、健康聚合）收敛为一个**独立的内部中转网关服务**，让后台退化回纯管理界面。

---

## 1. 为什么需要它（现状痛点）

当前「后台访问其它项目」的能力散在后台（Node/Next）里，且有多种形态：

| 形态 | 位置 | 问题 |
| --- | --- | --- |
| 浏览器→后台→项目 代理 | `src/app/api/gateway/[project]/[...path]` | 后台成了代理瓶颈，且持有全部密钥 |
| 服务端直连项目库 | `src/lib/teyvat/assets.ts` | 同类逻辑若复制到别处难以维护 |
| 服务端直连内网接口 | `src/lib/teyvat-users.ts` | 内网密钥散落在消费端 |
| 通知 + 重试 | `project_notifications` + admin 页 | 投递与重试绑在后台进程，后台不开就发不出 |
| 健康探测 | 各面板各自 fetch | 无统一聚合、无法对多项目统一告警 |

随项目数/消费者数增长，会出现：**密钥分散、协议重复实现、审计缺失、后台"越权"承载基础设施职责**。

## 2. 目标与非目标

### 目标
1. **单一入口**：所有「管理面 → 业务项目」的调用统一经网关，消费者不再各自实现协议。
2. **密钥收口**：各项目凭证只存网关，消费者只持有"访问网关"的凭证。
3. **统一契约**：转发 + 响应归一化（业务项目 `{code,message,data}` → 统一 `{success,message,data}`）。
4. **可审计**：每次跨服务调用落审计日志（谁/何时/哪个项目/哪个接口/结果/耗时）。
5. **通知可靠投递**：把通知与重试从后台迁到网关（后台关闭也能重试），后台只读投递记录。
6. **健康聚合**：`GET /gw/health` 汇总所有项目状态，供后台与告警共用。
7. **横向扩展消费者**：CLI、定时任务、告警系统都能复用同一网关。

### 非目标（边界）
- ❌ 不承载 **C 端流量**（用户请求走 web 服务器，与网关无关）。
- ❌ 不做业务逻辑（不解析业务语义，只做转发/编排/审计）。
- ❌ 不做用户体系（用户登录仍归 web 服务器，见 `04`）。
- ❌ 不替代各项目的业务接口，只做访问侧收敛。

### 2.1 启动触发条件（2026-09-12 结论：暂缓）

**结论：本项目暂缓，不在当前阶段启动。**
现在只有 **1 个接入项目 + 1 类管理面消费者（后台）**，§1 列的痛点大多尚未真实发生，此时实施正落在 §9 自己标注的「过度设计」风险上。

**它解决的是"管理面工程化"，与线上稳定性、C 端用户规模无关**（§2 非目标已声明不承载 C 端流量）。所以别把两件事混在一起：

| 你想要的 | 该做的 |
| --- | --- |
| 线上稳、用户变多也不垮 | `ai/05` 的 **P4**（按用户限流 / 配额熔断 / 成本观测）+ 主服务水平扩展 + 可观测 |
| 管理面整洁、密钥收口、可审计 | 才轮到本项目 |

满足以下任意 **两条** 即可启动 G0（抽 `relay-core`）：

| # | 触发条件 | 现状 |
| --- | --- | --- |
| T1 | 接入项目 ≥ 2 个 | ❌ 1 个（teyvat-guide） |
| T2 | 管理面消费者 ≥ 2 类（后台之外增加 CLI / 定时任务 / 告警系统） | ❌ 1 类（后台） |
| T3 | 需要回答「谁在什么时候调了哪个项目的哪个接口」（审计） | ❌ 无此需求 |
| T4 | 通知重试必须不依赖后台进程存活 | ⚠️ **技术上已成立**（通知投递与重试现绑在后台进程），但当前只有一人在用后台，影响很弱 |
| T5 | 密钥散布到 ≥ 2 个部署单元，需要收口 | ❌ 只有后台一个持有方 |

> 补充两点：
> 1. 后台的 `src/app/api/gateway/[project]/[...path]/route.ts` **已经是一个轻量网关**（注入凭证 → 转发 → 归一化），本项目只是把它抽成独立服务并补审计/通知/健康聚合 —— 所以"暂缓"不等于"没有网关"。
> 2. `admin/01` 的「多项目统一管理平台」定位仍是长期方向，本项目是它的基础设施底座；暂缓只影响实施时机，不影响该定位。

### 2.2 与阿里云部署的关系（2026-09-12 澄清）

**部署到阿里云不需要自研这个网关。** 两类"网关"职责不重叠：

| | 中转网关（本项目） | 阿里云相应产品 |
| --- | --- | --- |
| 服务对象 | **内部消费者**（后台 / CLI / 定时 / 告警） | 外部流量入口（SLB/ALB）或 ECS 出网（NAT 网关） |
| 职责 | 密钥收口、**业务信封归一化**、审计、通知重试、健康聚合 | TLS / 域名 / 认证 / 限流 / 路由 / 出网 |
| 关系 | 纯自研工程化 | 配置即可 |

单机部署下每条链路的实际做法（详见 `../ai/06-阿里云部署方案.md` §2.5）：浏览器 → 主服务走 Nginx/ALB；后台 → 主服务内网接口服务端直连 `127.0.0.1:8080`；主服务 → AI 服务走回环 `127.0.0.1:8090`。**没有一处需要自研网关。**

> ⚠️ 名称混淆：阿里云的「**NAT 网关**」是出网产品，与本项目的「中转网关」毫无关系（且 `ai/06` §2.1 明确单机场景要避免它）。

## 3. 架构

```
   后台(admin) ─┐                     ┌─ web 服务器 teyvat-guide (:8080)
   CLI/定时任务 ─┼─► 中转网关(:8091) ─┼─ AI 服务器 teyvat-ai (:8090)
   告警系统     ─┘   · 路由/鉴权注入    ├─ (teyvat_guide 库，供资产映射 API)
                      · 响应归一化      └─ 未来其它项目
                      · 审计 / 通知队列 / 健康聚合
```

- 网关**仅内网可达**，不暴露公网。
- 网关是"南北向"入口：北向面对内部消费者，南向访问各业务项目。
- 项目注册表复用 `teyvat_admin.managed_projects`（单一真相），网关只读。

## 4. 核心职责

| # | 职责 | 说明 |
| --- | --- | --- |
| 1 | 路由 | `/{project}/**` → 项目 `base_url` |
| 2 | 鉴权注入 | 按 `auth_type` + `auth_header` 注入 `X-Admin-Key` / `X-AI-Key`；内网接口注入 `X-Internal-Key` |
| 3 | 响应归一化 | 业务信封 → 统一信封；错误码归一 |
| 4 | 审计日志 | 结构化落库/日志：caller、project、path、status、ms |
| 5 | 超时 / 降级 | 统一超时、失败降级，不把上游错误透传 |
| 6 | 通知队列 | 投递失败入队，定时/手动重试（迁自 `project_notifications`） |
| 7 | 健康聚合 | 并发探测各项目 health，聚合返回 |
| 8 | 限流 / 熔断（后置） | 按 caller / project 限流，上游故障熔断 |

## 5. 技术选型（待决策）

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **Node/TS**（推荐起步） | 可**直接复用**现有 `gateway.ts` / `projects.ts` / `notifications.ts`，落地最快、与后台同栈 | 与 Go 主服务栈不同 |
| Go | 与主服务同栈、单二进制、运维一致 | 需重写现有 TS 逻辑 |

> 建议：**先 Node/TS 落地**（把现有 lib 抽成独立服务/共享包），若后续要统一后端栈再评估迁移 Go。网关是 I/O 编排型服务，语言性能不是瓶颈。

## 6. 消费者鉴权（网关自身的安全）

- 消费者 → 网关：使用**网关访问凭证**（如 `GW_TOKEN` 或 mTLS），与业务项目密钥完全分离。
- 网关 → 项目：使用项目密钥（`managed_projects` 配置 + 网关侧 env）。
- 网关仅内网监听；调用方按身份归类（admin/cli/scheduler）写入审计。

## 7. 与现有实现的迁移路径

1. **抽公共层**：把 `src/lib/gateway.ts`(待抽)、`projects.ts`、`notifications.ts` 抽为共享包 `packages/relay-core`，同时被后台与网关依赖。
2. **后台改造**：后台的 `/api/gateway` 改为调用网关（或后台浏览器直连网关）；`teyvat-users.ts`、`assets.ts` 的直连收敛到网关 API。
3. **通知迁移**：`project_notifications` 的写入/重试移入网关；后台改为只读展示。
4. **健康聚合**：后台状态页改为读 `GET /gw/health`。

> 迁移期间保持**双写/兼容**，避免一次性大改。

## 9. 风险

| 风险 | 对策 |
| --- | --- |
| 网关成为单点 | 无状态、可水平复制；健康检查 + 快速重启 |
| 网关持有全部密钥 | 仅内网、最小权限、密钥走 env/vault、不入仓 |
| 迁移期双路径不一致 | 共享包保证同一实现；灰度切换 |
| 过度设计 | 严格按 §2 边界，先做转发/鉴权/归一化/审计四项 |
